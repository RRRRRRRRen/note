# 单元测试

*类型：knowledge ｜ 难度：进阶 ｜ 标签：yudao、单元测试、JUnit、Mock、测试规范*

**yudao 项目的单元测试围绕「Service 层逻辑可独立验证」展开：JUnit 5 提供测试框架与断言，Mockito 隔离 Mapper 与外部依赖，Spring Boot Test 支持需要完整上下文的集成测试。该主题的专题源码笔记暂为空，本篇梳理单元测试在项目中的定位、常用栈与基本写法，配合「Maven 相关实践」篇的 surefire 插件理解测试的执行时机。**

## 单元测试在项目中的定位

- 单元测试验证最小可测单元（通常是 Service 方法）的业务逻辑正确性，是重构的底气来源。
- 与 Maven 构建流程绑定：`mvn test` 在 default 生命周期的 test 阶段执行（由 surefire 插件驱动），`mvn package` 默认会跑测试，`-DskipTests` 只是临时排障手段。
- 测试代码位于 `src/test/java`，编译产物进入 `target/test-classes`，与主代码类路径隔离（见「项目通用问题和设计」篇）。

## 技术栈构成

| 组件 | 角色 |
| --- | --- |
| JUnit 5 | 测试框架：`@Test`、`@BeforeEach`、断言 API |
| Mockito | Mock 框架：隔离 Mapper、RPC 等外部依赖 |
| Spring Boot Test | 集成测试：`@SpringBootTest` 加载完整上下文 |
| H2 / Testcontainers | 集成测试的数据库支撑（按需） |

依赖声明（测试作用域，不污染生产 classpath）：

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.mockito</groupId>
    <artifactId>mockito-core</artifactId>
    <scope>test</scope>
</dependency>
```

## 基本写法

### 纯单元测试：Mock 隔离依赖

```java
@ExtendWith(MockitoExtension.class)
class UserServiceTest {

    @Mock
    private UserMapper userMapper;

    @InjectMocks
    private UserServiceImpl userService;

    @Test
    void findById_shouldReturnUser_whenExists() {
        // given：约定 mock 行为
        UserDO mockUser = new UserDO();
        mockUser.setId(1L);
        mockUser.setNickname("ren");
        when(userMapper.selectById(1L)).thenReturn(mockUser);

        // when：调用被测方法
        UserVO result = userService.findById(1L);

        // then：断言结果
        assertNotNull(result);
        assertEquals("ren", result.getNickname());
        // 验证交互：mapper 被调用了一次
        verify(userMapper, times(1)).selectById(1L);
    }

    @Test
    void findById_shouldThrow_whenIdInvalid() {
        // 参数非法时快速失败，不触碰 mock
        assertThrows(IllegalArgumentException.class, () -> userService.findById(0L));
    }
}
```

- given-when-then 三段结构让测试意图清晰。
- 一个测试方法只验证一个行为，方法名表达「条件 + 期望」。
- 只 mock 直接依赖，不 mock 被测对象内部逻辑。

### 集成测试：需要完整上下文时

```java
@SpringBootTest
class UserIntegrationTest {

    @Autowired
    private UserService userService;

    @Test
    void contextLoads_andServiceWorks() {
        // 走真实 Bean 装配链路，验证模块间协作
        assertNotNull(userService);
    }
}
```

- `@SpringBootTest` 启动成本高，仅在验证装配、事务、AOP 等框架行为时使用。
- 大量业务逻辑验证优先用纯单元测试，保持反馈速度。

## 命名与执行

- 测试类命名：被测类名 + `Test`，与被测类同包放置。
- 与构建的配合：

```bash
# 运行全部单元测试
mvn test

# 只运行匹配的测试类（-Dtest 支持通配）
mvn test -Dtest=UserServiceTest

# 打包时跳过测试（临时排障用）
mvn clean package -DskipTests
```

## 实践建议

- 优先覆盖三类逻辑：边界条件、异常分支、核心业务规则。
- 断言要具体（assertEquals 比 assertNotNull 更有价值），避免「不报错就算过」。
- 测试之间不共享状态，不依赖执行顺序。
- 数据库相关逻辑优先通过 mock Mapper 验证 Service 编排，真实 SQL 验证交给集成测试或本地验证。
