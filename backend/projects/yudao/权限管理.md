# 权限管理

*类型：knowledge ｜ 难度：进阶 ｜ 标签：yudao、权限管理、RBAC、Spring Security、数据权限*

**yudao 的权限管理是 RBAC 模型（用户-角色-权限）的完整落地：功能权限控制「能不能调这个接口、看不看得到这个菜单」，数据权限控制「能看哪些行的数据」，两者叠加构成完整的访问控制。该主题的专题源码笔记暂为空，本篇从项目架构角度梳理权限体系的分层与关键机制。**

## 权限体系在项目中的定位

权限管理纵贯项目各层：

- 前端：菜单渲染、按钮级权限控制（根据权限码显隐按钮）。
- 网关/拦截层：登录态校验、Token 解析。
- 应用层：接口权限校验（方法级注解）。
- 持久层：数据权限拼接 SQL 条件。

## RBAC 核心模型

```text
用户（AdminUser）
  ↓ 多对多
角色（Role）
  ↓ 多对多
菜单/权限（Menu：目录、菜单、按钮，携带 permission 权限码）
```

- 用户通过角色获得权限集合，权限粒度到按钮级（权限码形如 `system:user:create`）。
- 角色是权限的分组单元，新增用户只需分配角色，不需要逐项配权限。

## 功能权限：接口与菜单

### 接口权限校验

基于权限码的方法级校验，典型实现是 Spring Security 的 `@PreAuthorize`（配合 SpEL 引用方法参数，见「Spring 相关实践」篇）：

```java
// 用户必须拥有 system:user:create 权限码才能调用
@PreAuthorize("@ss.hasPermission('system:user:create')")
@PostMapping("/create")
public CommonResult<Long> createUser(@Valid @RequestBody UserSaveReqVO reqVO) {
    // ...
}
```

- `@ss` 是注册到容器中的权限校验 Bean，内部查询当前用户的权限集合并比对权限码。
- 校验失败由全局异常处理统一转换为 403 响应。

### 登录与鉴权链路

```text
登录：账号密码校验 → 生成 Token（JWT）→ 返回前端
    ↓
请求：携带 Token → 拦截器解析 → 还原登录用户（LoginUser）→ 放入上下文
    ↓
鉴权：方法级注解比对权限码 → 通过则执行业务
```

- 登录用户信息与权限集合通常缓存在内存或 Redis，避免每个请求查库。
- 退出登录通过使 Token 失效实现。

### 菜单权限

- 前端菜单由后端按用户角色过滤后返回（与 vue-vben-admin 的动态路由思路一致，见其「路由配置」篇）。
- 按钮级权限：前端根据权限码列表控制按钮显隐，后端接口校验兜底——前端控制只是体验优化，安全边界永远在后端。

## 数据权限

数据权限解决「同一个接口，不同角色看到的数据范围不同」：

| 范围 | 语义 |
| --- | --- |
| 全部数据 | 不做限制 |
| 本部门及以下 | 拼接部门树条件 |
| 仅本部门 | 拼接 dept_id 条件 |
| 仅本人 | 拼接 creator/user_id 条件 |

常见实现是基于 MyBatis-Plus 的 SQL 改写：拦截器根据当前用户的数据权限配置，自动为 SQL 追加 where 条件，业务代码无感知。

## 实践要点

- 权限校验放在 Service 之上统一处理，不在业务方法内散写「判断有没有权限」。
- 权限码命名按「模块:资源:操作」规范，与前端按钮一一对应。
- 数据变更操作要校验数据归属（比如改订单前校验订单属于当前用户可见范围），不能只依赖列表过滤。
- 超管角色作为特例短路所有校验，但要防止权限码误挂到超管专属接口上。
- 权限相关表数据的变更要有审计记录（谁在什么时候改了谁的角色）。
