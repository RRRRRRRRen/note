# 闭包与作用域

## 作用域与作用域链

### 变量是怎么被找到的：作用域与作用域链

*难度：入门 ｜ 标签：作用域、作用域链、let/const、var*

**核心结论**：作用域是变量的有效访问范围，JS 采用词法作用域——作用域在函数定义时就确定了，跟在哪里调用无关。查变量时沿作用域链由内向外逐级查找，命中即停，直到全局，找不到才抛 `ReferenceError`。三个推论：内层能看外层、反之不行；同名内层变量遮蔽（shadow）外层；`var` 只有函数/全局作用域，`let/const` 才有块级作用域。

> **前置：** 本篇的「作用域链」就是执行上下文环境记录里的 `outer` 引用串成的链——先有登记，才有查找。

**技术对照：DNS 逐级解析**

作用域链的查找过程就是 DNS 的逐级解析：你要解析一个域名（访问变量），先查本机缓存与 hosts（当前作用域）；没有，问本地 DNS 服务器（外层函数）；再没有，逐级上报到根域名服务器（全局作用域）；根上也没有，返回 NXDOMAIN（`ReferenceError`）。

关键点：你的解析线路（作用域链）在配置生效时（函数定义时）就已经确定，之后无论从哪个网络发起查询（函数在哪里被调用），逐级向上问的顺序都不会变——这就是词法作用域。它和 DNS 一样是「配置静态、查询动态」：链路写死，查询按需。

**作用域的三种类型**

**全局作用域**：页面打开时创建、关闭时销毁，是整条查找链的最后一站。它存在的意义是提供一个所有人都能到达的兜底命名空间——任何函数一路向外查，终点都是它；反过来说，任何往里写的东西都是潜在的命名冲突源，这也是「少用全局变量」的机制依据：它不是风格洁癖，是链路终点的污染半径最大。

机制上有个细节：浏览器的全局词法环境其实有两个登记处——对象记录（`var/function` 声明直接挂到 `window` 上，成为全局对象的属性）和声明式记录（`let/const/class` 只登记在记录里，不挂 `window`）。两者都在全局层、查找时都会被查到，所以 `window.globalLet` 是 `undefined`，但裸读 `globalLet` 完全正常。Node 不同：顶层 `var` 属于模块作用域，不挂 `globalThis`——同一条规则，宿主落地不同。

```javascript
// 浏览器（Chrome 140）经典脚本中实测：
var globalVar = 'I am global';
console.log(window.globalVar); // 'I am global' —— var 挂到全局对象

let globalLet = 'I am also global';
console.log(window.globalLet); // undefined —— let 不挂
console.log(globalLet);        // 'I am also global'（全局可访问不受影响）
```

**函数作用域**：每次调用函数都会创建一个全新的、独立的作用域，这是函数级隔离的来源：同一函数递归调用一百次，就有一百份互不干扰的局部变量——没有这个设计，递归根本写不了。「内部可以访问外部，反之不行」是单向阀：外层看不见内层，内层沿链看得见所有外层。

引擎层面，函数上下文创建时新建一个环境记录，它的 `outer` 指向函数定义处的环境（不是调用处）——这一条就是词法作用域的物理实现，也是闭包的全部基础。作用域的销毁跟着环境记录的可达性走：没有闭包引用，随调用结束回收；被闭包引用，则活得比调用更久。

**块级作用域**：ES6 引入，为的是修 `var` 的两个经典事故：循环变量被异步回调共享成同一个、块内声明泄漏出去覆盖外层同名变量。事故的根源都是 `var`「无视代码块」——代码块只是语法装饰，登记位置全在函数/全局层。`let/const` 把登记粒度降到块，代码块第一次成了真正的边界。

机制上，进入块时压入一个新的块级环境记录，退出即弹出；TDZ 也是它的产物——声明语句执行前，绑定已在块记录里但未初始化。而 `var` 的登记发生在所在函数/全局的变量环境里，块退出后依然活着，这就是「逃出」代码块的真相：不是它穿越了边界，是它压根没被边界登记过。

```javascript
{
  let blockVar = 'I am in block';
}
console.log(blockVar);
// ReferenceError: blockVar is not defined

{
  var noBlockVar = 'I escape the block';
}
console.log(noBlockVar); // 'I escape the block'
```

输出解读：

```text
ReferenceError: blockVar is not defined
  let 登记在块级环境记录里，块退出记录销毁；外层查找沿链走完全程也没命中
  ——是「未定义」而非 TDZ（TDZ 报错发生在块内声明之前）
'I escape the block'
  var 不参与块级登记，直接登记在全局的变量环境里；块只是它的书写位置，不是它的管辖边界
```

**var vs let/const 对比**

| 对比项 | var | let / const |
|-------|-----|-------------|
| 作用域层级 | 函数级（块只是语法装饰） | 块级（每对花括号一个记录） |
| 提升初始化 | 登记即初始化为 undefined | 登记但不初始化（TDZ） |
| 重复声明 | 合法，后者覆盖前者 | SyntaxError，脚本不执行 |
| 全局挂载 | 浏览器中挂到 window | 不挂 window，仅声明式记录 |
| 循环迭代绑定 | 整个循环共享一个绑定 | 每轮迭代创建一个新绑定 |

**动手验证：词法作用域**

```javascript
var value = 1;

function foo() {
  console.log(value);
}

function bar() {
  var value = 2;
  foo();
}

bar();     // 输出: 1（不是 2!）
const obj = { value: 99, foo };
obj.foo(); // 输出: 1（方法调用也不走动态作用域）
```

- 第一处输出 `1`：foo 定义在全局，创建时 outer 已指向全局环境；在 bar 里被调用也只沿「foo → 全局」这条链找，永远不会路过 bar 的作用域。JS 若采用动态作用域（它没有）这里才会输出 2。
- 第二处输出同样是 `1`：`obj.foo()` 只改变 this，不改变作用域链——方法调用不会把 obj 的属性拉进查找路径。词法作用域由定义位置决定，this 是唯一的动态角色。

回扣 DNS 对照：`foo` 的解析线路（`foo → 全局`）在它被定义的那一刻就已配置完毕，`bar()` 的调用、`obj.foo()` 的方法调用都只是「换一个网络发起查询」，逐级向上问的顺序分毫不变。如果这份代码换成动态作用域语言，输出就会随调用方漂移——正因为 JS 不是，这类代码才可以只读不跑地给出确定答案。

**作用域链的查找顺序**

```javascript
var globalVar = 'global';

function outer() {
  var outerVar = 'outer';

  function inner() {
    var innerVar = 'inner';
    console.log(innerVar);  // 'inner' - 当前作用域命中
    console.log(outerVar);  // 'outer' - 上一级命中
    console.log(globalVar); // 'global' - 全局命中
  }

  inner();
}

outer();
```

查找链：`inner → outer → 全局`。命中即停，不会继续向外；全部落空抛 `ReferenceError`。这也解释了为什么内层变量会遮蔽（shadow）外层同名变量——不是外层消失了，是查找在命中处提前返回。遮蔽是单向的：内层读不到外层被遮蔽的值，除非显式起不同的名字。

工程含义接着机制来：既然没有「向上穿透查找」的语法，需要访问被遮蔽的外层变量时，唯一的正路是在遮蔽发生之前把它提取到别名（或改掉内层命名）。反过来，遮蔽也可以当特性用：函数内部临时变量故意与外层同名以声明「这里我说了算」，前提是读者能一眼看出层级——命名相同而层级不同的代码，永远是排查时的噪音源。

**边界陷阱**

`var` 与块级作用域的组合最容易出事，坑的共同点是：**声明生效的范围比你以为的代码块大一号**。第一个坑是块内 `var` 泄漏——写在块里，登记却在函数/全局层：条件块里的 `var` 声明在块外照常可读（没执行到时是静默的 `undefined`，逻辑错误被掩盖）；若外层已有同名 `let`，则升级为 `SyntaxError`，整个脚本拒绝执行。排查这类问题时盯着块看会一无所获，因为声明压根没被块登记过。

错误写法：

```javascript
function handler(needInit) {
  if (needInit) {
    var config = load(); // 本想块内私有
  }
  return config;
  // needInit 为 false：返回 undefined
  // 不抛错——var 泄漏到函数级，
  // 「漏初始化」被静默掩盖
}
handler(false); // undefined
```

正确写法：

```javascript
function handler(needInit) {
  if (needInit) {
    let config = load(); // 真正的块内私有
  }
  return config;
  // ReferenceError:
  // config is not defined
}
// 需要跨块共享时，把声明提到块外，
// 让共享成为显式决定
```

`var` 无视块边界：登记在函数级，块退出后照常存活——边界错误被静默的 undefined 掩盖。`let` 把管辖范围收窄到块：误用当场抛 `ReferenceError` 而不是返回 undefined——把作用域当最小权限来用。

第二个坑更隐蔽：**块内函数声明的行为跨引擎不一致**。规范正文里块内函数声明属于块级，但为了兼容存量网页，ECMA-262 又以附录 B（Annex B）标准化了一套「宽松语义」：非严格模式下，块内的函数声明会把一个绑定泄漏到外层函数/全局作用域。实测 Node v22：非严格函数内 `typeof f` 得到 `"function"`（泄漏成功），ES Module（严格）里得到 `"undefined"`（块级，未泄漏）。同一行代码换一个环境结论就反转——这种代码不该写。

错误写法：

```javascript
function test() {
  {
    function f() { return 'in-block'; }
  }
  return typeof f;
  // 非严格：'function'（Annex B 泄漏）
  // 模块/严格：'undefined'（块级）
}
```

正确写法：

```javascript
function test() {
  let f;
  {
    f = () => 'in-block'; // 赋值语义，无歧义
  }
  return typeof f; // 永远 'function'
}
```

**经典追问链**

**Q1：作用域链是定义时确定还是调用时确定？**

*考察点：词法作用域的一句话结论人人会背，看你能不能落到函数内部槽的层面。*

定义时确定。函数对象创建的那一刻，`[[Environment]]` 内部槽就记住了定义处的外部环境引用；调用时新建的环境记录 outer 指向它，查找沿这条固定链进行——与调用位置、调用方式都无关。箭头函数捕获 this 用的也是同一套机制。

延伸：动态作用域语言（如 bash 的局部变量、Emacs Lisp 动态绑定）才是「调用时确定」——函数行为随调用方变化，无法只读代码做静态分析，这正是 JS 没有选它的原因。

**Q2：var 和 let 在 for 循环里的本质区别？**

*考察点：答「一个函数级一个块级」只是第一层，面试官想听每轮迭代的绑定机制。*

var 在整个循环外只创建一个绑定，所有迭代共享，循环结束后它是最终值；let 按规范每轮迭代创建一个新绑定，并把上一轮的值复制进来。配合异步回调时：共享绑定的回调读到循环结束后的最终值，独立绑定的回调各自记着当轮的值。

延伸：「每轮新绑定」发生在 for 头的 let 上——这不是 let 的一般行为，是循环语句的特判逻辑（CreatePerIterationEnvironment）。手写 while 循环模拟 for-let 时不会有这个待遇。

**Q3：变量查找越远越慢，这个说法对吗？**

*考察点：性能直觉的辨析力——方向正确但机制停留在 ES3 时代，说得出引擎优化才是及格线。*

方向正确但结论过时。词法上更远意味着多走几跳 outer，但 V8 等引擎用内联缓存把「沿链查找」优化成带形状校验的常数时间命中，热点代码里链长差异通常被抹平。真正贵的查找是 with、eval 这类让作用域静态不可分析的写法——它们让缓存失效。不要为「链短」牺牲代码清晰度。

延伸：全局作用域是例外：它跨过脚本边界且可能被动态扩展（var 挂 window），查找成本确实略高——超热循环里把全局引用提前存进局部变量仍有微弱收益，属于最后的微优化。

**Q4：全局作用域和全局执行上下文是一回事吗？**

*考察点：概念区分题——「作用域」和「上下文」被混用的笔记到处都是，这题筛掉只会背名词的人。*

不是。执行上下文是运行时概念：一段代码执行所需的环境记录（含 this、词法环境），全局上下文只有一个、伴随程序全程；作用域是词法结构层面的访问规则，写在代码里、分析代码就能确定。两者的连接点是外部环境引用：作用域链正是通过上下文环境记录的 outer 链条物理串起来的——词法结构决定了链怎么连，上下文提供了链的实体。

延伸：浏览器全局词法环境内部还有对象记录与声明式记录两套登记（var 挂 window、let/const 不挂），说明「全局」在规范层面也是分层设计——一个概念，两种登记路径。

延伸阅读：this 到底指向谁、闭包到底是什么：词法环境的快照（见本章后文）。

## 执行上下文

### 变量提升是怎么发生的：执行上下文

*难度：进阶 ｜ 标签：执行上下文、调用栈、变量提升、暂时性死区*

**核心结论**：执行上下文是代码执行前的环境准备：绑定 this、登记所有声明、建立作用域链。全局上下文只有一个；函数每次调用都新建一个压入调用栈，执行完弹出。「变量提升」不是代码被移动，而是创建阶段先扫描登记的副产品——`var` 提升且初始化为 `undefined`，函数声明整体提升，`let/const` 提升但不初始化（TDZ）。上下文弹出后，堆上的环境记录是否回收只看还有没有闭包引用。

> **前置：** 本篇讨论「一段代码被执行时环境怎么准备」，与「回调排进哪个队列」（事件循环）互补——调用栈是事件循环图里的那条主轨道。

**技术对照：调试器里的 Call Stack 面板**

执行上下文栈就是调试器里的 Call Stack 面板，永远只执行栈顶那一帧：程序启动时压入一个常驻的栈底帧（全局上下文）；每调用一个函数，就把新帧压到栈顶；函数返回帧弹出，露出下面的帧继续执行。在 Chrome DevTools 的 Sources 面板里打断点，右侧那个 Call Stack 列表就是它的实时快照——每一行对应一个待续的上下文。

栈是有限资源：叠得越深（递归越深），离引擎上限（各实现约万层量级）越近，压爆了就是栈溢出。ECMA-262（ES2015 起）曾把「正确的尾调用（PTC）」写进规范——尾位置的递归调用可以复用当前栈帧、深度恒定——但只有 JavaScriptCore（Safari/WebKit）默认实现了它；V8 做过实验性实现（`--harmony-tailcalls`）后从未默认启用并最终移除，SpiderMonkey 也没有跟进。所以写跨引擎代码不能依赖 PTC：深递归请改写为循环，或用 trampoline 手动展平。

**执行上下文的类型**

**全局上下文**：程序启动时创建，唯一一个，浏览器中 `this` 指向 `window`。唯一意味着它不需要「创建参数」——没有调用方，环境就是宿主给定的全局环境。**函数上下文**：每次调用创建一个，数量不限。每次调用都新建，才让递归成为可能——第 N 层递归的局部变量和第 N+1 层互不干扰，因为它们住在两个不同的上下文里。（`eval` 也有自己的上下文，但不要用它。）

```javascript
function first() {
  console.log('Inside first function');
  second();
  console.log('Again inside first function');
}

function second() {
  console.log('Inside second function');
}

first();
console.log('Inside global execution context');

// 真实输出（Node v22.17.0 实测）：
// Inside first function
// Inside second function
// Again inside first function
// Inside global execution context
```

栈的变化：`[global]` → `[global, first]` → `[global, first, second]` → `[global, first]` → `[global]`。注意 first 的后半段要等 second 弹栈后才能继续——这就是「栈顶优先」：任何一个上下文在任意时刻只可能被挂起（因为调用了别人），绝不会被插队。

**单个上下文的生命周期**

1. 函数被调用：新上下文压栈
2. 创建阶段：绑定 this、登记所有声明
3. 执行阶段：逐行赋值与调用；期间调用新函数时本帧挂起
4. return / 执行到底：出栈，等待 GC

**上下文的三个阶段**

**创建阶段**：为什么要有独立的创建阶段？因为「声明登记」和「执行赋值」被设计成两件无关的事：引擎在执行任何一行代码之前，先静态扫描整个作用域，把所有声明一次性登记进环境。声明语句写在第 100 行还是第 1 行，登记结果完全相同——「提升」就是这个设计的副产品，而不是引擎搬运了你的代码。它换来的好处是：函数可以互相引用、先后书写不受限（函数声明互相调用很自由），引擎也不必在执行中途反复停下来处理「这里出现了一个新声明」。

机制上，创建阶段做三件事：绑定 `this`；创建词法环境（环境记录存 `let/const` 声明 + 指向定义处外部环境的 `outer` 引用）；创建变量环境（专门存 `var` 声明，登记即初始化为 `undefined`；函数声明在这里整体登记，声明加赋值一步到位）。`let/const` 存在词法环境里，登记但不初始化——存放位置与初始化时机的差异，就是提升行为差异的全部根源。

`first()` 执行中的内存布局：

```text
调用栈（栈帧）                             堆（环境记录）
┌───────────────────────────┐            ┌─────────────────────────────┐
│ first() 上下文（栈顶）       │            │ first 的环境记录              │
│   [[LexicalEnv]] ─────────┼──┐         │   outer ──────┐             │
│   this: undefined         │  │         │   second: <function>        │
├───────────────────────────┤  ├───────→ └───────────────┼─────────────┘
│ 全局上下文（栈底）           │  │                         │
│   [[LexicalEnv]] ─────────┼──┘         ┌────────────────▼────────────┐
└───────────────────────────┘            │ 全局环境记录                  │
                                         │   outer: null               │
   栈帧只保存指向环境记录的引用              │   first / second: <function>│
                                         └─────────────────────────────┘
```

说明：栈帧只保存指向环境记录的引用，声明确实登记在堆上的记录里；outer 引用把记录串成作用域链（作用域链的物理载体）。first 弹栈后若没有闭包引用，first 的环境记录不可达即被回收。

**执行阶段**：创建阶段把舞台搭好，执行阶段才逐行推进。这个分离的语义后果值得细品：声明在哪一行完全不影响可用性，但赋值与调用严格按行序——所以「提升后的 undefined」和「真正的值」有时间差，`console.log(a)` 写在赋值前读到占位值、写在赋值后读到真值。理解了这一点，提升相关的所有面试题都变成同一道题：登记发生在创建阶段，读写发生在执行阶段。

引擎层面，执行阶段由解释器（V8 的 Ignition）按字节码逐条推进：读变量沿环境记录的 `outer` 链逐级查找；读 `let/const` 时附带 TDZ 检查——绑定存在但未初始化，直接抛 `ReferenceError`；遇到函数调用则从头走一遍创建阶段、新上下文压栈，当前帧挂起等待。每次赋值都是对某个环境记录的一次写入——闭包之所以能「共享变量」，正因为两个函数读写的是同一条记录。

**回收阶段**：函数返回，栈帧弹出——但弹出销毁的只是栈帧这个壳，堆上的环境记录并不随之消失。这是刻意的分层设计：栈管执行位置（快进快出），堆管数据存活（按可达性）。两套生命周期分开管理，闭包才有存在空间——函数可以把环境记录的引用带出去，让数据活得比调用更久。

回收的裁决权在 GC 手里，标准只有可达性：环境记录没有被任何存活对象（比如被返回的闭包、注册出去的回调）引用，就在下一次 GC 中被回收；有引用，则连同名变量一起常驻内存。V8 的做法是：编译期分析哪些局部变量被内层函数引用，把只有这些变量装箱进堆上的 Context 对象，其余变量仍留在栈帧里随弹出消亡——闭包的内存成本因此是「按捕获变量付费」，不是整个作用域打包带走。

**动手验证：变量提升的三种表现**

三段代码各自独立运行（第三段抛错会终止脚本，实测 Node v22.17.0）。先自己推断输出，再看逐条解读：

```javascript
console.log(a); // undefined（不是 ReferenceError）
var a = 10;

foo(); // 'Hello'（函数声明整体提升，可以先调用）
function foo() {
  console.log('Hello');
}

console.log(b); // ReferenceError: Cannot access 'b' before initialization
let b = 20;
```

输出解读：

```text
undefined                                                ← var a
  var a 在创建阶段登记并初始化为 undefined，执行阶段读到的是这个占位值。
  提升给你的不是「还没声明」，而是「已声明未赋值」。
Hello                                                    ← 函数声明 foo
  函数声明的提升是整体提升：创建阶段就把函数对象赋给了 foo，
  调用语句写在声明之前完全合法。
ReferenceError: Cannot access 'b' before initialization  ← let b
  let b 同样被登记了（所以报错不是 is not defined），但创建阶段不初始化
  ——声明语句执行前处于暂时性死区（TDZ），读取触发引用错误。
```

TDZ 期访问的正误对照：

```javascript
// 以为提升 = 可以随便先访问
console.log(config);
// ReferenceError: Cannot access
// 'config' before initialization
let config = loadConfig();
```

```javascript
let config = loadConfig();
console.log(config); // 先声明再访问

// 需要「未初始化」语义时，显式写出来
let cache; // undefined，语义自明
```

let 提升但不初始化：声明语句执行前是 TDZ，访问直接抛错，且不会向外层同名变量「穿透」。`undefined` 是「已登记且已初始化为空」的占位语义——要占位就显式 `let cache;`，别赌提升行为。

**函数声明 vs 函数表达式**

两者语法形似，提升路径却完全不同，因为它们在创建阶段走的是不同的登记手续：函数声明走整体登记——声明与赋值在创建阶段一步到位，执行阶段那行「声明」实际上已经无事可做；函数表达式本质是一个 var 声明加一个赋值语句，被提升的只有 `var bar` 部分，函数值要等执行到那一行才诞生。

报错信息的差异因此成为诊断线索：`TypeError: bar is not a function` 说明变量已登记、值不是函数（`undefined()` 的必然结果）；`Cannot access before initialization` 说明是 `let/const` 的 TDZ；纯「未声明」则是第三种报错 `is not defined`。面试时能区分这三种报错对应的登记状态，是理解创建阶段的直接证据。

```javascript
// 错误：调用发生在赋值之前，等于调用 undefined
start();
// TypeError: start is not a function
var start = function () {
  console.log('started');
};
```

```javascript
// 正确：函数声明整体提升可以前置调用
start(); // 正常执行
function start() {
  console.log('started');
}

// 必须用表达式时：先定义，后调用
const run = function () { /* ... */ };
run();
```

同名冲突的优先级示例（辅助验证）：

```javascript
console.log(foo); // [Function: foo]

var foo = 'variable';
function foo() {
  return 'function';
}

console.log(foo); // 'variable'

// 等价推导：
// 1. 创建阶段：函数声明优先登记 → foo = <function>（var 的 undefined 占位被忽略）
// 2. 执行阶段：foo = 'variable' 照常执行，覆盖函数值
```

把三个演示合并成一句总纲：**创建阶段决定「登记成什么样」，执行阶段决定「读到什么值」**。var 登记即初始化（undefined 等着被覆盖）、函数声明登记即赋值（函数对象先于一切代码存在）、let/const 登记不初始化（TDZ 看守到声明行）。所有提升相关的争议——先访问、同名冲突、报错类型——都可以还原为「这两个阶段各自做了什么」，不需要背任何口诀。

**经典追问链**

**Q1：函数声明和变量声明同名，谁赢？**

*考察点：创建阶段登记的优先级——很多人背了「函数优先」，却说不清后续赋值照样能覆盖。*

创建阶段函数声明优先登记：`function foo` 的登记会取代 `var foo` 的 undefined 占位，提升结束后 foo 是函数。但进入执行阶段后，代码里的赋值语句 `foo = 'variable'` 照常执行，foo 会被覆盖成字符串——「提升谁赢」决定初始值，「执行阶段赋值」依然有效，两者别混为一谈。

延伸：同一作用域里 let 与 var 声明同名变量是 SyntaxError（重复声明），整个脚本都不执行——这条检查发生在任何代码运行之前，是最早暴露的一类错误。

**Q2：暂时性死区的范围怎么算？外层有同名变量能穿透吗？**

*考察点：TDZ 的作用域语义——「不穿透」这条反直觉，检验你是背了『声明前不能用』还是真懂块级环境记录。*

TDZ 从块级作用域开始到 let/const 声明语句执行完毕，且不穿透：块内的 `let x` 让这个块里所有对 x 的查找都绑定到块级环境记录，声明前访问一律抛 `ReferenceError: Cannot access 'x' before initialization`——即使外层有已初始化的同名 x 也一样（Node v22 实测）。作用域是词法的，遮蔽从登记那一刻就生效，与执行进度无关。

延伸：typeof 也不豁免：TDZ 内 `typeof x` 同样抛 ReferenceError——「typeof 检查安全」只对未声明变量成立，对未初始化的 let/const 不成立。

**Q3：bar is not a function 和 Cannot access 'b' before initialization，两种报错怎么定位？**

*考察点：能否从报错信息反推登记状态——工程里 90% 的提升事故是先看到报错再回头看代码。*

前者是 var 承载的函数表达式：名字已提升为 undefined，调用 `undefined()` 抛 TypeError——去查调用语句是否跑到了赋值前面。后者是 let/const 的 TDZ：绑定存在但未初始化，读取抛 ReferenceError——去查声明语句的位置。再叠加纯未声明变量的 `is not defined`，三种报错精确对应三种登记状态：已登记但值不对、已登记未初始化、从未登记。

延伸：把报错差异用作代码评审信号：函数表达式 + 模块顶层互相调用时，var 写法会拖出运行时 TypeError，改函数声明或 const + 箭头函数能把错误提前到语法检查期。

**Q4：提升是代码被物理移动了吗？引擎到底在哪一步完成登记？**

*考察点：区分「背口诀」与「懂流程」——答出解析阶段静态收集的，才真正理解为什么提升只在同一作用域内发生。*

不是移动。代码位置一字不变，登记发生在解析阶段：引擎在执行任何字节码之前先扫描整个作用域，收集所有声明并建好环境记录——V8 在解析期就生成作用域信息，字节码生成时据此确定每个变量的读写目标。这也直接解释了提升的边界：扫描不跨函数、不跨块，所以声明永远只在它所在的作用域内提升，跨作用域的「提升」从来就不存在。

延伸：V8 对函数体还有惰性编译：外层解析时对内层函数只做预解析（查语法错误、记录声明占位），真正被调用时才全量编译——启动开销与执行解耦，也让「提升看起来发生在调用之前」有了实现层的注脚。

延伸阅读：变量是怎么被找到的：作用域与作用域链、闭包到底是什么：词法环境的快照（见本章前文与后文）。

## this 绑定

### this 到底指向谁？

*难度：进阶 ｜ 标签：this、箭头函数、作用域、面试*

**核心结论**：this 不在定义时确定，也不是函数自己的属性——它是被调用时由调用方式注入的。四条绑定规则按优先级：**new > 显式（call/apply/bind）> 隐式（obj.fn()）> 默认（独立调用）**；箭头函数是唯一例外，词法捕获定义处的 this，call/bind 都改不动。三大丢失现场：方法当回调传出、链式赋值、解构取方法——修法一致：包箭头函数或提前 bind。

> **前置：** 作用域在定义时确定、this 在调用时注入——两套寻址系统先分开，本篇只讲后者。

**this 是什么：调用位置说了算**

理解 this 最重要的一步，是把「作用域」和「this」分开：作用域是词法的（写代码时就定了），this 是动态的（运行时由调用方式注入）。同一个函数对象，`obj.fn()` 里 this 是 obj、`fn()` 里是 undefined（严格模式）、`new fn()` 里是新实例——函数不变，调用方式变，this 就变。

四条绑定规则覆盖所有情况：**new 调用**——绑定到新创建的对象（new 四步的第二步就是「把 this 指向新对象」）；**显式绑定**——call/apply 立即执行并指定 this，bind 返回绑死 this 的新函数；**隐式绑定**——调用位置有没有 `xxx.` 前缀，有就绑到那个对象（只看最近一层，`obj.a.fn()` 绑到 a 不是 obj）；**默认绑定**——以上都不沾，非严格模式挂 window/globalThis，严格模式是 undefined。

this 判定顺序：

1. 有 new？→ 绑定新实例
2. 有 call/apply/bind？→ 绑定指定对象
3. 有 `obj.` 前缀？→ 绑定最近一层对象
4. 默认绑定 → window / undefined

> **记忆点：** this 优先级——new > 显式 > 隐式 > 默认。箭头函数跳过所有规则，直接看外层。判断 this 只需回答一个问题：这个函数是被谁、以什么形式调用的？

**箭头函数：唯一的例外**

箭头函数没有自己的 this——它不创建 this 绑定，在函数体内引用 this 时走词法作用域，找到定义处外层函数的 this。所以 call/apply/bind 对它的 this 全部无效，传参照常、this 装聋。同理它也没有 arguments（用 rest 参数替代）、没有 prototype、没有 `[[Construct]]` 内部方法——不能被 new。

选型经验：回调场景（事件处理、定时器、数组方法）用箭头函数省心，因为它「要的是外层 this」；对象方法和原型方法慎用箭头函数——方法要的恰恰是「调用者的 this」，写成箭头函数后 this 固定为定义处的值（模块顶层就是 undefined），`obj.method()` 反而拿不到 obj。class 里定义箭头函数类字段是唯一合理例外（自动绑定实例，见追问链第 5 问）。

| 对比项 | 普通函数 | 箭头函数 |
|-------|---------|---------|
| this 绑定 | 由调用方式决定（四条规则） | 词法捕获定义处外层的 this |
| arguments 对象 | 有 | 没有，用 rest 参数替代 |
| prototype 属性 | 有 | 没有 |
| 能否 new | 可以（有 [[Construct]] 内部方法） | 不能，new 直接抛 TypeError |
| call/apply/bind | 可改变 this | 对 this 无效 |
| 作回调传出 | this 丢失，需手动绑定 | this 保持为定义处的值 |

**丢失 this 的三大现场**

隐式绑定最脆弱——它只认「调用位置的点前缀」。三种最常见的丢 this 现场：**方法被抽出来当回调**：`setTimeout(obj.say, 100)` 传出去的是函数本体，定时器以普通函数形式调用它，点前缀没了，this 回落默认绑定；**链式赋值**：`(a.b = a.b)()` 赋值表达式返回函数本体再调用，同样脱离对象；**解构取方法**：`const { say } = obj; say()`——本质同第一种。

修复思路统一为「把动态绑定变词法/显式」：包一层箭头函数（`setTimeout(() => obj.say(), 100)`），或提前 bind（`this.say = this.say.bind(this)`——React class 组件时代的标准动作）。现代 class 语法给了第三种：箭头函数类字段，绑定在实例化时一次完成。

现场一：方法被抽走当回调。

```javascript
// 错误：定时器以普通函数形式调用回调
class Timer {
  seconds = 0;
  tick() { this.seconds++; }

  start() {
    setInterval(this.tick, 1000);
    // TypeError: Cannot read properties
    // of undefined (reading 'seconds')
  }
}
```

```javascript
// 正确：箭头类字段 / 包箭头 / bind
class Timer {
  seconds = 0;
  tick = () => { this.seconds++; }; // 箭头类字段

  start() {
    setInterval(this.tick, 1000);   // this 恒为实例
  }
}
// 等价修复：setInterval(() => this.tick(), 1000)
// 或构造函数里 this.tick = this.tick.bind(this)
```

方法本体被传走，调用时没有点前缀，默认绑定生效，this 不是实例（Node 22.17 严格模式实测）。修法一致：把动态绑定变词法（箭头）或显式（bind）。

现场二：链式赋值。

```javascript
const obj = {
  id: "obj",
  say() { return this.id; },
};

(obj.say = obj.say)();
// undefined —— 赋值表达式返回函数本体
// 再调用，点前缀消失
```

```javascript
(obj.say = obj.say.bind(obj))();
// "obj" —— 先绑死再赋值
// 或者干脆别用赋值表达式的返回值来发起调用
```

调用的是「赋值表达式的结果值」，与 obj 无关（严格模式实测）。

现场三：解构取方法。

```javascript
const { say } = obj;
say();
// undefined —— 等价于把函数赋给一个
// 全新变量再独立调用
```

```javascript
const say = obj.say.bind(obj);
say(); // "obj"

const shout = () => obj.say(); // 或箭头包一层
```

本质与现场一相同：函数离开对象，隐式绑定断裂。解构是高频语法（React 里 `const { setState }` 最常见），绑定要跟在解构后面补。

**经典追问链**

**Q1：严格模式和非严格模式下，独立调用函数的 this 分别是什么？call(null) 呢？**

*考察点：默认绑定的边界——严格模式与 null/undefined 传参这两个分支最容易被混成一谈。*

非严格模式独立调用 this 是 window/globalThis；严格模式是 undefined（访问 this.x 直接报错）。call/apply/bind 传入 null/undefined 时：非严格模式被替换为全局对象，严格模式原样使用（this 就是 null/undefined）。所以「用 call(null) 测试严格模式」是有效的调试技巧。

延伸：ESM 模块代码默认运行在严格模式——模块顶层的独立调用 this 是 undefined，这改变了老代码的默认行为。

**Q2：call、apply、bind 的区别？bind 之后再用 call 改 this 会怎样？**

*考察点：显式绑定三件套的细节——bind 的「一次绑定永久生效」与手写 bind 的 new 交互是常见追加点。*

call/apply 立即执行、只差传参形式（call 逐个列、apply 传数组，数组展开有参数上限与性能成本）；bind 不执行，返回永久绑定 this（并可预置参数）的新函数——且绑定不可覆盖：bind 之后再 call 另一个对象，this 仍是第一次绑定的。三者的手写版面试高频，bind 的完整版还要处理 new 调用优先级（见设计模式篇「手写 bind」）。

延伸：性能视角：apply 展开 super 大数组可能触发引擎参数上限（V8 约 12 万）；固定参数场景 bind 预置比每次 call 传参更快。

**Q3：setTimeout(this.tick, 0) 里的 this 为什么不是实例？怎么让它是？**

*考察点：默认绑定的触发路径——「异步不改变 this 规则，改变的是调用方式」这一层要讲透。*

定时器到点后，回调是被宿主以普通函数形式调用的——没有点前缀、没有 new、没有 call，命中默认绑定：非严格 window/globalThis、严格 undefined。异步机制本身不引入任何新 this 规则；变的是「谁在什么形式下调用它」。修复三选一：包箭头函数 `() => this.tick()`（推荐）、提前 bind、箭头函数类字段。

延伸：同理适用于事件监听器 `addEventListener(this.handler)`——DOM 事件里原生写法 this 是 currentTarget，而传出去的函数引用已脱离该机制。

**Q4：new 的优先级为什么高于 bind？箭头函数为什么不能 new？**

*考察点：绑定规则的引擎层依据——能说出内部方法（[[Construct]]/[[Call]]）的是懂规范的人。*

new 调用走函数的 `[[Construct]]` 内部方法：先创建新对象，再把 this 指向它执行——this 在进入函数体之前就已经被决定为实例，bind 的绑定只作用于 `[[Call]]` 路径。手写 bind 用 `this instanceof bound` 模拟这个优先级。箭头函数只有 `[[Call]]` 没有 `[[Construct]]` 内部方法，new 直接抛 TypeError——「没有 prototype」只是表象，「缺构造槽」才是根源。

延伸：原生 bind 返回的异质函数对象：调用走 `[[Call]]`（用绑定的 this），new 走 `[[Construct]]`（忽略绑定、用新实例）——一条规范条款同时解释了两个现象。

**Q5：类字段箭头函数和构造函数里 bind，哪种更好？**

*考察点：工程向收尾题，把 this 绑定接到真实代码决策——答出「函数引用稳定性」直通 React 性能话题。*

语义上等价（都是实例级绑定），差异在函数引用的创建成本：构造函数里 `this.handler = this.handler.bind(this)` 整个生命周期只创建一次；类字段箭头函数同样每次实例化创建一次——单实例无差别。真正要警惕的是 JSX 内联写法 `onClick={() => this.tick()}`：每次渲染创建新函数，子组件若被 memo 包裹会因 props 引用变化而白白重渲染——把绑定提升到渲染之外才是正解。

延伸：编译器视角：类字段箭头函数会被编译为构造函数里的赋值语句——「类字段」与「构造器 bind」的产物几乎一致，二选一的标准是团队约定与可读性，而不是性能。

延伸阅读：变量是怎么被找到的：作用域与作用域链（本章前文）、手写 bind 时，new 为什么能「打败」它（见设计模式篇）。

## 闭包

### 闭包到底是什么：词法环境的快照

*难度：进阶 ｜ 标签：闭包、作用域、内存*

**核心结论**：闭包 = 函数 + 它定义时所处词法环境的引用。函数创建的那一刻，`[[Environment]]` 内部槽就绑定了定义处的环境记录；之后无论被传到哪里调用，它读写变量的链永远从那里出发。函数在定义作用域之外被调用（或环境比调用更长寿）时，这个组合就是你看到的「闭包」。捕获的是变量绑定（引用）不是值的拷贝；只要函数可达，环境记录就不可回收——这是闭包能「记住」状态的原因，也是泄漏的根源。

> **前置：** 闭包是作用域链的延续：本节假设你已知道「函数的环境记录通过 outer 指向定义处环境」。

**闭包从哪来：词法作用域的必然产物**

把两个既有事实放在一起，闭包不是新机制，是推论。事实一：函数是一等公民——可以被赋值、进数组、当参数、当返回值，函数会不可避免地离开它书写的位置。事实二：作用域是词法的——函数能访问哪些变量由定义位置决定（见作用域链一节）。两者相加只有一个结论：函数离开定义处之后，定义处的环境必须还能被它访问到——否则词法作用域的承诺（「你定义在哪，就能看到哪」）在调用那一刻就违约了。闭包就是这个承诺的兑现方式：函数随身携带定义处环境的引用。

反过来看更容易记住：只要函数没有离开定义处去执行（或环境与函数同生共死），你根本意识不到闭包存在。日常代码里「闭包」作为术语被点名，几乎都发生在两个场景：回调在原作用域结束后才执行（定时器、事件监听、异步返回），或工厂函数把内层函数返回到外部。离开定义处 + 环境还在——识别闭包问题先识别这两个条件。

**捕获机制：[[Environment]] 与环境记录**

规范层面的时序很精确：函数对象创建时（不是调用时），引擎把「当前正在使用的环境记录」写进函数的 `[[Environment]]` 内部槽——这一步不可省略，因为它就是「定义处」的内存表示。调用时，引擎为这次调用新建一个环境记录，其 outer 指向函数的 `[[Environment]]`——变量查找的链条由此接回定义处。所谓「快照」，快照的是环境的引用而非变量值：外层变量后来被改了，闭包读到的是最新值；闭包自己改写变量，外层再读也拿得到——两边看的是同一条环境记录。

V8 的实现把这套模型落到堆上：编译期分析哪些局部变量被内层函数引用，只有这些变量被「装箱」进堆上的 Context 对象（规范里环境记录的实体），其余变量仍留在栈帧里随调用结束消亡。所以闭包的捕获粒度是按变量的，不是把整个作用域打包带走——但也要注意：只要一个变量进了 Context，它就脱离了栈的快速回收通道，生命周期完全交给 GC。下图是 `makeCounter` 返回后的内存结构——栈帧没了，环境记录还在。

```text
调用栈                              堆
┌────────────────────┐            ┌───────────────────────────────────┐
│ 全局上下文（栈底）    │            │ 全局环境记录                        │
│  [[LexicalEnv]] ───┼──→         │   makeCounter: <function>          │
└────────────────────┘            │   counter ──→ counter 函数对象       │
                                  └──────────────┬────────────────────┘
（makeCounter 的栈帧早已弹出）                     │
                                  ┌───────────────▼───────────────────┐
                                  │ counter 函数对象                    │
                                  │   [[Environment]] ──┐              │
                                  └─────────────────────┼──────────────┘
                                  ┌─────────────────────▼──────────────┐
                                  │ makeCounter 的环境记录（仍存活）       │
                                  │   count: 2                          │
                                  │   outer ──→ 全局环境记录              │
                                  └─────────────────────────────────────┘
```

说明：根（全局变量 counter）→ 函数对象 → 环境记录：整条链可达，count 就一直活着。把 counter 置为 null 且无其他引用时，函数对象与环境记录一起变得不可达、一起被回收——闭包没有「泄漏开关」，可达性就是一切。

**为什么 JS 设计成词法作用域**

词法作用域的核心收益是代码可以静态推理：只看文本就能确定每个标识符的查找链，不用执行、不用知道谁会调用它。这个性质是整条工具链的地基——打包器的 tree-shaking、压缩器的变量重命名、TS 的类型检查、IDE 的跳转定义，全都建立在「作用域离屏可算」之上。若换成动态作用域（按调用栈决定可见性），函数行为随调用方变化，读代码的人必须在脑内模拟所有调用点，上述工具全部失效。JS 沿袭 Scheme 的一等函数 + 词法作用域传统，选的是可推理的那条路。

引擎层面同样是这笔账：作用域链在创建时固定，查找路径静态可预测，V8 的内联缓存才能把「沿链逐级查找」优化成带形状校验的缓存命中，热点路径近似常数时间。动态的作用域（随调用栈变化）天然无法做这类缓存。不过 JS 也不是全然静态——`this` 就是留给动态性的唯一口子，它由调用方式注入、与作用域链无关（见 this 绑定一节）。理解「作用域词法、this 动态」的分工，很多混淆会自动消失。

> **记忆点：捕获引用，不是拷贝。** 闭包保存的是环境记录的引用：读到的永远是变量当前值，写入对外层可见。判断闭包相关 bug 时先问一句——这几个函数读的是不是同一条环境记录？

**经典输出题：循环里的闭包**

最经典的考点：`setTimeout` 的回调捕获的 `i` 到底是哪一个。两个循环只差一个声明关键字，输出完全不同——先自己推断，再看逐条解读（Node v22.17.0 实测）：

```javascript
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i));
}
// 3 3 3 —— var：整个循环只有一个 i，三个回调共享

for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i));
}
// 0 1 2 —— let：每轮迭代创建一个新的绑定
```

输出解读：

```text
3 3 3（var 版本）
  同步循环在主线程跑完时 i 已经是 3；三个回调共享 var i 这一个绑定，
  任何一个开始执行时读到的都是最终值——「捕获引用」在循环场景的必然结果。
  定时器回调只能进宏任务队列，永远晚于同步代码——它们「看到的」
  必然是循环结束后的世界。
0 1 2（let 版本）
  let 触发循环的特判机制：每轮迭代创建新的环境记录，本轮回调捕获的
  是记录着当轮值的那一条；第二轮的新绑定复制上一轮的值再加一——
  回调各拿各的记录，互不干扰。
```

`let` 版本不是闭包机制变了，而是绑定数量变了——规范给 `for` 头部的 `let` 加了每轮新建环境的特判。修复 `var` 版本的老办法（ES5 时代没有 `let`）是用 IIFE 手动制造这层独立作用域：`(function(j){ setTimeout(() => console.log(j)) })(i)`——把当轮的 `i` 作为参数 `j` 重新登记进一个新环境，每个回调拿到自己的 `j`。今天直接用 `let` 即可，但 IIFE 写法在存量代码和面试追问里仍然常见。

**闭包计数器：函数返回后状态仍在**

状态需要跨调用存活、又不想暴露成全局变量——闭包是这个需求的原始解：把变量登记在工厂函数的环境里，返回一个读写它的内层函数。外部没有任何路径直接触到 `count`，能做的只有调用 `counter()`——状态私有化是作用域规则的自然结果，不需要任何语法开关。

```javascript
function makeCounter() {
  let count = 0; // 被闭包捕获的私有状态
  return function counter() {
    count += 1;
    return count;
  };
}

const counter = makeCounter();
console.log(counter()); // 1
console.log(counter()); // 2 —— makeCounter 早已返回，count 却还在涨
```

`makeCounter()` 调用结束、栈帧弹出后，`count` 靠「返回的 `counter` 函数持有 `[[Environment]]`」继续存活（内存结构见上面的示意图）。每调用一次 `makeCounter()` 就产生一条全新的环境记录——两个计数器互不串账，这正是下文「闭包封装状态」各种工程模式的共同地基。

**边界陷阱**

闭包的坑几乎都是同一个根源的两种走向：持有得比预期久（该回收的回收不掉，内存被大对象拖住）或共享得比预期多（以为各拿一份，实际读写同一条记录）。前者的重灾区是定时器和事件监听——回调常驻，被它捕获的变量跟着常驻；后者的重灾区是循环与异步——回调共享同一个绑定。写代码时的自查口诀：这个回调被谁引用多久？它捕获的变量有多大？

循环里捕获循环变量：

```javascript
// 错误：异步回调引用 var 循环变量
for (var i = 0; i < tasks.length; i++) {
  fetch(tasks[i]).then(() => {
    retry(i); // 循环跑完后才执行：
    // i 永远是 tasks.length
  });
}
```

```javascript
// 正确：let 每轮独立绑定
for (let i = 0; i < tasks.length; i++) {
  fetch(tasks[i]).then(() => {
    retry(i);
  });
}

// ES5 环境用 IIFE 手动造新作用域：
// (function(j){ ... })(i)
```

闭包持有大对象：

```javascript
// 错误：闭包捕获整个大对象
function attach(el, bigData) {
  el.addEventListener("click", () => {
    render(bigData); // 闭包捕获整个大对象
  });
  // el 换页销毁时监听器没移除：
  // bigData 永远不可回收
}
```

```javascript
// 正确：只留需要的字段 + 提供解绑路径
function attach(el, bigData) {
  const summary = summarize(bigData); // 只留需要的
  const onClick = () => render(summary);
  el.addEventListener("click", onClick);
  return () => el.removeEventListener("click", onClick);
}
// 组件卸载时调用返回的解绑函数
```

工程上的防线因此有三条：显式清理（`clearInterval`、`removeEventListener`，现代浏览器还可以用 `AbortController` 一组信号批量解除监听）；收敛捕获面（回调只引用它真正需要的字段，而不是顺手把整个大对象写进闭包）；限制存活时长（能随组件卸载/请求结束释放的，就不要登记到全局结构里）。三条都做到位，闭包本身并不比普通函数更容易泄漏——泄漏的从来不是机制，是缺失的生命周期管理。

**经典追问链**

**Q1：闭包一定造成内存泄漏吗？**

*考察点：「有意持有」与「意外滞留」的区分——把闭包等同于泄漏的人，会在代码里无谓地回避正常模式。*

不一定。泄漏的定义是「不再需要却无法回收」；闭包持有状态是有意设计——计数器的 count 就该活着。只有当闭包本身已无用、却仍被引用链拽着（遗忘的定时器、未解绑的监听器、塞进全局数组的一次性回调）时，它捕获的环境才构成泄漏。判断标准始终是可达性：还从根摸得到吗？还需要它吗？

延伸：排查工具：Chrome DevTools 的 Memory 面板拍堆快照，按 retainer 链找「谁拽住了这个上下文」——多数闭包泄漏的元凶在监听器/定时器注册处，不在闭包本体。

**Q2：循环里 await 一个闭包变量，读到的是什么？**

*考察点：var/let 循环题的异步进阶版——把事件循环时序和绑定数量两个维度叠在一起考。*

let 声明的迭代变量每轮独立，await 恢复执行后读到的仍是当轮的值；var 则共享一个绑定，await 之后的代码执行时循环早已跑完，读到最终值。await 本身不改变绑定，它只是把「回调执行时」推迟到循环之后——shared binding 的延迟读取风险被 await 进一步放大。

延伸：forEach + async 回调也有同样的坑：forEach 不等待 async 回调，回调里的循环变量共享问题与 for(var) 同构——并发收集结果请用 for...of + await 或 Promise.all。

**Q3：闭包和 class 怎么选？**

*考察点：工程选型题——考你知道两者是同一需求（封装状态）的两条实现路线，而不是把闭包当炫技。*

状态少、操作少、要每实例天然隔离时，闭包工厂更轻：没有 this 问题、没有继承包袱、状态真私有（外部连 undefined 都摸不到）。状态多、需要子类型多态、需要 instanceof 判断、调试时要看实例结构时，用 class——ES2022 的 `#` 私有字段也补上了原生私有语义，选型的天平已向 class 倾斜，闭包工厂适合小而封闭的状态单元。

延伸：内存模型不同：闭包工厂的状态住在每实例的环境记录里，方法每次工厂调用重新创建；class 的方法在原型上共享一份、字段每实例一份——大量实例时 class 的方法共享是实打实的内存优势。

**Q4：React Hooks 和闭包什么关系？**

*考察点：闭包知识的迁移力——前端工程师最高频的闭包现场其实是框架。*

函数组件每次渲染就是一次函数调用，各自生成一份独立的闭包快照：当次渲染的 props、state、局部变量都登记在当次的环境记录里。「闭包陷阱」（useEffect 里读到旧 state）就是回调捕获了旧渲染的快照——机制与循环 var 题完全同构，只是共享/独立的判定对象从循环变量换成了渲染。对策也同构：让回调拿到最新值（依赖数组、函数式更新 `setState(prev => ...)`、useRef 跨渲染共享）。

延伸：useEffect 返回的清理函数也是闭包——它捕获的同样是当次渲染的快照，清理时读到的 props/state 是「那一轮」的值，这对写「仅当依赖变化时才清理」的逻辑至关重要。

**Q5：闭包变量存在栈还是堆？V8 具体怎么实现？**

*考察点：压轴硬核题，从规范模型下沉到引擎实现——能答出「装箱」和按需捕获的，说明真读过 V8 相关材料。*

堆。V8 在编译期做变量级分析：只把被内层函数引用的变量装箱进堆上的 Context 对象（ScopeInfo 描述哪些变量需要装箱），函数的栈帧弹出后 Context 交给 GC 管理。未被引用的变量仍留在栈帧里随弹出消亡。所以闭包的内存成本是「按捕获变量付费」，且每次访问捕获变量多一次堆间接寻址——这是闭包相对局部变量唯一的常规开销。

延伸：反向优化也存在：V8 的逃逸分析在「闭包不逃出当前调用」时可以不装箱、保持在栈上；热点代码里对 Context 字段的访问还有内联缓存加速——闭包不天然慢，但它确实改变了变量的内存布局与回收路径。

延伸阅读：闭包在工程里怎么用：私有状态与模块模式（见下节）、JS 是怎么释放内存的：GC 与泄漏排查（见本章后文）。

### 闭包在工程里怎么用：私有状态与模块模式

*难度：进阶 ｜ 标签：闭包、私有状态、模块模式、IIFE*

**核心结论**：闭包的工程价值收敛在一个母题：封装状态——把变量藏进函数作用域，只暴露操作入口。私有变量、计数器、模块模式是同一手法的三种规模；判断状态份数的口诀是「工厂被调用几次 = 几份状态」：工厂函数多次调用产生多份独立环境（每实例隔离），IIFE 只调用一次（单例共享）。闭包捕获的是变量绑定本身，所以返回的函数读写的是同一个活着的变量。

> **前置：** 本节不解释闭包的形成机制（[[Environment]] 与环境记录的存活），只谈工程化用法——先把地基打牢。

**你已经天天在用：事件回调里的闭包**

先把概念落地：闭包不是面试专用词，是每个前端项目的日常。初始化代码里注册了一个 `addEventListener`，回调引用了当时的配置对象；之后哪怕注册回调的那段代码早已执行完毕，事件触发时回调依然能读到那份配置——被捕获的变量跟着回调走，生命周期不再由原作用域决定，而由「是否还有引用」决定。

这一条已经包含了本节所有模式的原材料：回调（返回的函数）+ 原作用域变量 = 可持久的私有状态。差别只在组织方式——把「配置对象」换成计数器、把监听器换成返回值，就成了下面要拆的模式。识别自己代码里的闭包，从找「谁在原作用域结束后还握着这些变量」开始。

**一个母题：闭包封装状态**

把经典三模式（私有变量、独立计数器、模块模式）并排放开，会发现它们是同一个动作在不同规模上的重复：把状态变量登记在一个不会被外部触达的作用域里，返回（或暴露）一组操作它的函数。状态拿不到引用就改不干净——这是比命名约定（`_count`）强得多的封装，因为它是作用域规则保证的，不是君子协定。ES2022 的 `#` 私有字段出现之前，这就是 JS 唯一的真封装；今天它仍是「不引入 class 就要私有状态」时的默认解。

模式之间真正的分野是状态份数：工厂函数（`createXxx`）每次调用都执行一遍函数体，每次都产生全新的环境记录——调用 N 次就有 N 份互不相干的状态；而 IIFE 模块模式本质是「只调用一次的工厂」，私有成员全模块共享一份，天然单例。写代码前先回答「这里需要几份状态」，就不会再选错组织形式——这也是本节最重要的一个判断。

> **记忆点：状态份数 = 工厂调用次数。** `createCounter()` 调用两次 = 两份 count；`(function(){...})()` 只调用一次 = 单例。选模式前先答「需要几份状态」，形式跟着答案走。

**私有变量与计数器：工厂函数的独立状态**

私有变量是母题的最小形态：外部拿不到 `_name` 的引用，唯一入口是闭包暴露的 `getName/setName`——接口面积被压到最小，任何状态变更都必须经过你定义的操作，校验、日志、联动因此有了唯一的拦截点。

```javascript
function createPerson(name) {
  var _name = name; // 外部拿不到引用

  return {
    getName: function () {
      return _name;
    },
    setName: function (newName) {
      _name = newName;
    },
  };
}

var person = createPerson('Alice');
console.log(person.getName()); // 'Alice'
person.setName('Bob');
console.log(person.getName()); // 'Bob'
console.log(person._name);     // undefined - 外部拿不到引用
```

计数器在同一形态上多了一个关键观察点：两个实例的两份状态。每次调用 `createCounter()` 都新建一条环境记录，`counter1` 与 `counter2` 的方法各自闭包引用各自的 `count`——调用多少次互不串账。对照下面的输出顺序走一遍（Node v22.17.0 实测）：

```javascript
function createCounter() {
  var count = 0;
  return {
    increment: function () {
      return ++count;
    },
    getCount: function () {
      return count;
    },
  };
}

var counter1 = createCounter();
var counter2 = createCounter();

console.log(counter1.increment()); // 1
console.log(counter1.increment()); // 2
console.log(counter2.increment()); // 1 - 独立闭包，互不影响
console.log(counter1.getCount());  // 2
```

输出解读：

```text
1  counter1 的 increment 读写的是第一条环境记录里的 count：0 → 1。
2  同一个闭包环境，读改写同一条记录：1 → 2——「捕获引用」让跨调用累加成为可能。
1  counter2 是第二次 createCounter() 调用的产物，全新的环境记录，
   count 从 0 重新开始——实例隔离的本质是环境隔离。
2  回到 counter1 的 getCount：读到的仍是它自己那条记录的 count
   ——两个闭包互相不可见，谁也污染不了谁。
```

**模块模式：只调用一次的工厂**

模块模式把「工厂 + 闭包私有」组织到模块粒度：IIFE 创建一个立即执行、只执行一次的函数作用域，私有变量和私有函数登记在其中，返回对象的方法闭包引用它们。这是 ES Module 普及之前主流库（jQuery 时代的插件、各类 SDK）的标准模块化方案——读懂大量存量库源码的前提。

现代代码里它的角色已被取代，对应关系值得记住：模块作用域（`import/export` 的顶层）本身就是「只执行一次的作用域」，私有性由「不导出就不可见」天然保证，静态可分析的模块图还带来了 tree-shaking——模块模式是这套语法糖的运行时手工作坊。字段级私有则有了 `#` 私有字段。理解对应关系比背历史有用：什么时候还需要手写模块模式？——需要带参初始化的运行时封装（ES Module 是静态结构，做不到「调用时传入配置再成型」），以及没有模块系统的宿主环境。

```javascript
var Module = (function () {
  var privateVar = 'I am private';

  function privateMethod() {
    console.log(privateVar);
  }

  return {
    publicMethod: function () {
      privateMethod();
    },
  };
})();

Module.publicMethod();          // 'I am private'
console.log(Module.privateVar); // undefined
```

单例不是缺陷，是 IIFE 的语义——但要有意识地选择它：全局唯一的状态（配置中心、连接池、日志器）适合单例；「每个调用方一份」的状态写成了 IIFE，就会变成隐形共享。下面这个坑在真实项目里以「测试互相污染」「多实例串数据」的形式反复出现：

```javascript
// 错误：购物车逻辑写成了 IIFE 单例
const cart = (function () {
  let items = [];
  return {
    add: (x) => items.push(x),
    size: () => items.length,
  };
})();

// 第二个「购物车」是幻觉：
cart.add('a');
cart.add('b'); // 和上面的同一份 items！
```

```javascript
// 正确：需要多份状态就保留工厂，别急着执行
function createCart() {
  let items = [];
  return {
    add: (x) => items.push(x),
    size: () => items.length,
  };
}

const cartA = createCart(); // 独立
const cartB = createCart(); // 独立
```

IIFE 只调用一次：所有 import/引用方共享同一份私有状态——「以为每处用的是一个新实例」是错觉。状态份数由「工厂调用几次」决定：单例需求才用 IIFE，多实例需求必须保留可调用的工厂函数。

**边界陷阱**

除了单例误用，本域还有一类高频事故：循环中捕获循环变量。它的机制在「闭包基础」一节已完整拆解（共享绑定 vs 每轮独立绑定），工程里值得再强调的是它的变体形态：不止 `for(var)`，把回调存进数组、注册进事件表、挂到对象上——只要执行晚于循环结束，`var` 循环变量的共享绑定就会迟到爆雷。

```javascript
// 错误：回调被存进数组/事件表，执行必然晚于循环
const handlers = [];
for (var i = 0; i < 3; i++) {
  handlers.push(() => send(i));
}
handlers.forEach((h) => h());
// 3 3 3 —— 共享同一个 var i
```

```javascript
// 正确：let 每轮独立绑定
const handlers = [];
for (let i = 0; i < 3; i++) {
  handlers.push(() => send(i));
}
handlers.forEach((h) => h());
// 0 1 2

// forEach 本身也安全：参数是每轮独立的函数参数
```

还有一类静态陷阱值得点名：用 `eval` 或 `with` 动态改写作用域。它们让作用域链在运行时变得不可静态分析，引擎的绑定优化（内联缓存）全部失效，严格模式更是直接禁掉了 `with`。工程结论一句话：需要动态性就用显式的数据结构（Map、对象字典）+ 闭包，别让作用域本身变成可变状态。

> **提示（闭包状态的测试隔离）：** 单例闭包状态在单测里是隐形雷：模块加载即初始化、进程内全程共享，测试用例之间互相污染。需要可测性时把单例改成工厂（`createStore(config)`），由调用方决定生命周期与注入。

**防抖与节流：闭包视角一句话**

防抖/节流是「闭包记住状态、返回待触发函数」的代表性应用：`timer`、`lastTime` 这类必须跨调用存活的变量，全部活在返回函数的闭包里——放进返回函数内部则每次触发都是新变量，重置逻辑直接失效。完整实现（immediate/leading+trailing/cancel）、节奏语义、React 实例稳定性陷阱，见设计模式篇「防抖和节流到底差在哪」。

同属这一家族的还有柯里化：返回的函数把已收集的参数存进闭包里的 `args`，攒够参数个数才调用原函数。

```javascript
function curry(fn) {
  return function curried(...args) {
    // 参数收齐了就直接执行原函数
    if (args.length >= fn.length) {
      return fn.apply(this, args);
    }
    // 不够则返回新函数继续收集
    // —— args 存活在闭包里，跨调用递进累积
    return function (...moreArgs) {
      return curried.apply(this, args.concat(moreArgs));
    };
  };
}

function add(a, b, c) {
  return a + b + c;
}

var curriedAdd = curry(add);
console.log(curriedAdd(1)(2)(3)); // 6
console.log(curriedAdd(1, 2)(3)); // 6
console.log(curriedAdd(1)(2, 3)); // 6
```

**经典追问链**

**Q1：IIFE 单例和工厂函数，状态为什么一个共享一个独立？**

*考察点：「状态份数」的心智模型——答案不在闭包语法里，在「函数被调用几次」里。*

状态份数 = 工厂被调用的次数。IIFE 是「定义即调用一次」的工厂，函数体只执行一遍，私有变量只有一份，所有引用方共享；`createXxx` 留作可重复调用的工厂，每调用一次就新建一条环境记录，状态天然隔离。两种写法的闭包机制完全相同，差别只是调用次数。

延伸：推论：把 IIFE 赋给变量的写法可以让它「看起来像类」却拥有单例语义——评审代码时看到 `const X = (function(){...})()` 就该立刻问一句：这里真的只需要一份吗？

**Q2：模块模式和 ES Module 的本质区别是什么？**

*考察点：两条模块化路线的分界——答「一个旧一个新」只是年代，答不出静态/运行时之别说明没理解模块系统。*

模块模式是运行时手法：IIFE 创建一次性闭包，私有性靠作用域，成员关系在执行后才确定，还支持带参初始化。ES Module 是语法级静态结构：import/export 在解析期确定模块依赖图，私有性由「不导出就不可见」保证，静态化带来 tree-shaking、循环依赖的活绑定（live binding）与更早的错误检查。功能上现代项目一律用 ES Module，模块模式退守两个场景：无模块系统的宿主、需要运行时带参组装的封装。

延伸：活绑定是 ES Module 独有的语义：导出的是绑定的实时引用，导入方读到的值跟随导出方更新；IIFE 返回对象的属性只是导出那一刻的快照——这个差异在写状态模块时最容易被忽略。

**Q3：柯里化也是闭包吗？**

*考察点：模式识别的迁移力——能不能从「参数收集」这个陌生场景里认出「闭包记住状态」的母题。*

是。curry 返回的函数把已收集的参数存进闭包里的 args，每层调用把新参数 concat 进去，攒够参数个数才调用原函数——参数的持久化与递进收集全靠闭包持有同一个 args 绑定。它和计数器是同一道题：把「count」换成「已收集的参数列表」。

延伸：防抖（timer）、节流（lastTime）、柯里化（args）、记忆化（cache）可以合并成一句话记：高阶函数家族 = 闭包记住一种跨调用的状态。判断标准：函数返回函数、且内层引用外层绑定。

**Q4：闭包捕获的是变量还是值？防抖里的 timer 说明了什么？**

*考察点：回到机制本源——「捕获引用」若是背出来的，就解释不了 timer 为什么能被覆盖重写。*

捕获的是变量绑定（对环境记录的引用）而非值的拷贝。timer 能在下一次触发时被 clearTimeout 读到、能被新一轮 setTimeout 覆盖重写，恰恰证明闭包读写的是同一个变量——如果是值拷贝，重置逻辑根本碰不到旧的定时器句柄。所有「跨调用累积/重置」类模式，都建立在这个语义上。

延伸：实现粒度补充：V8 按变量装箱——外层作用域里只有被内层函数引用的变量才进堆上的 Context，「闭包捕获整个作用域」是模型简化。所以闭包的成本与「你引用了多大的变量」直接相关，大对象捕获前先收敛。

延伸阅读：发布订阅是怎么实现的：手写事件总线（见设计模式篇）、JS 是怎么释放内存的：GC 与泄漏排查（见下节）。

## 内存管理

### JS 是怎么释放内存的：GC 与泄漏排查

*难度：高级 ｜ 标签：垃圾回收、内存泄漏、标记清除、GC*

**核心结论**：现代 JS 引擎用标记清除：从根（全局对象、当前调用栈、宿主注册的引用）出发标记所有可达对象，清除不可达者——「能否从根访问到」决定生死，而不是引用数。泄漏的本质是对象已经没用、但仍然被一条从根出发的引用链挂着：意外全局变量、被遗忘的定时器、脱离 DOM 的引用、闭包的多余捕获——四类事故的共性都是「引用链没断」。

> **前置：** 闭包捕获的变量活在词法环境里——「泄漏是引用链没断」这件事，从闭包的视角最容易看懂。

**技术对照：JVM 的可达性分析**

V8 的标记清除与 JVM / .NET 的可达性分析同源，理解一个就理解了全部：GC 从根集合（全局对象、当前调用栈上各帧的局部变量、宿主注册的原生引用）出发，顺着引用链遍历——能摸到的对象打上「存活」标记；遍历结束后仍没被摸到的，整块回收。判断依据是「是否从根顺着摸得到」，而不是「还有几个人引用它」。

这套模型回收循环引用轻而易举：两个对象互相持有引用，但只要从根摸不到它们，双双标记为垃圾。对照之下，早期的引用计数（COM 的 AddRef/Release、Python 底层策略之一）给每个对象维护「被引用数」，归零立即释放——听起来更及时，却在循环引用上致命：互相引用的对象计数永远 ≥ 1，谁也到不了零。

```javascript
function circularReference() {
  var obj1 = {};
  var obj2 = {};

  obj1.ref = obj2;
  obj2.ref = obj1;
  // 函数执行完毕后，obj1 和 obj2 互相引用：
  // 引用计数永远不为 0（引用计数算法下会泄漏）
  // 现代浏览器使用标记清除，从根不可达即正常回收
}

circularReference();
```

**标记清除 vs 引用计数**

标记清除的代价是「批量」：回收发生在 GC 调度决定的那一刻，对象不可达后要等下一轮回收周期才真正释放，全量标记阶段还需要 stop-the-world。引用计数的优势恰好是「即时」：计数归零的瞬间就释放，延迟最低——但它为每次引用赋值都付出维护计数的开销，而且如前所述处理不了环。IE 6/7 时代的著名泄漏正源于此：JS 对象与 DOM 对象分属两套引用计数体系，互相引用时双方的计数都下不来，页面关掉才释放——这也是现代引擎全面转向标记清除的历史动因。

| 对比项 | 标记清除（主流） | 引用计数（已淘汰） |
|-------|----------------|------------------|
| 原理 | 从根集合出发遍历引用链：可达打标，遍历结束清掉未标记者 | 每个对象维护被引用计数：引用建立 +1、断开 −1 |
| 循环引用 | 正确回收——判断依据是可达性，互指但从根不可达照样清 | 致命弱点：互指双方计数恒 ≥ 1，永不归零，双双泄漏 |
| 实现方 | 现代 JS 引擎全部采用（V8 / JavaScriptCore / SpiderMonkey） | IE 时代的 BOM/DOM（COM 计数）；Python 与 COM 至今仍用、需配辅助环收集器 |
| 释放时机 | 批量：由 GC 调度决定，不可达后延迟到下一轮回收周期 | 即时：计数归零立刻释放，延迟最低，但每次赋值都有维护开销 |

> **记忆点：泄漏的定义。** GC 管「不可达」的对象，管不了「可达但没用」的对象——只要还挂着一条从根出发的引用链，再大的对象也不会被回收。排查泄漏 = 找出这条链。

补充：变量的生命周期视角——全局变量生命周期持续到页面卸载；局部变量从函数执行开始到函数执行结束；闭包中的变量只要闭包还在使用就不会被回收。

```javascript
function example() {
  var localVar = 'I will be collected'; // 局部变量
  console.log(localVar);
}
example(); // 函数执行完毕后，localVar 会被回收

function closureExample() {
  var closureVar = 'I will NOT be collected'; // 被闭包引用

  return function () {
    console.log(closureVar);
  };
}

var closure = closureExample();
// closureVar 不会被回收，因为闭包还在引用它
```

**四种经典泄漏场景**

以下场景均为浏览器环境行为（Chrome 最新稳定版验证），每个场景都值得用「引用链」的语言复述一遍——这是把「知道 leak」升级为「能修 leak」的分界线。

**1. 意外的全局变量**：非严格模式下给未声明变量赋值，引擎会顺手在全局对象上创建属性：函数里写 `name = 'Global leak'`，name 就挂到了 `globalThis` 上。引用链层面，全局对象本身就是 GC 的根——根直接可达意味着这个属性永远存活，与「还有没有用」无关，函数返回后也不会消失。

```javascript
function leak() {
  name = "Global leak"; // 非严格模式：漏写声明 → 挂到 globalThis
}
leak();
// 严格模式（ESM 默认开启）下这行直接抛 ReferenceError
```

防御在语言层就给好了：`'use strict'` 让这行直接抛 ReferenceError，ESM 模块代码默认运行在严格模式；ESLint 的 no-undef 规则能在提交前拦住。变体同样要警惕——非严格模式的普通函数里 `this` 指向全局对象，给 `this.xxx` 赋值是同一种事故的隐写法。

**2. 被遗忘的定时器**：模块里用 `setInterval` 周期刷新状态，闭包引用了大数组 data；后来节点从 DOM 移除、页面也不再需要刷新，但定时器从未清除。引用链层面：宿主环境维护着一张定时器表——表项持有回调函数，回调闭包引用词法环境，词法环境里躺着 data。这条链从「宿主注册的引用」这个根出发，全程强引用：只要表项还在，data 与回调就都不可达判定为「存活」。

```javascript
const data = new Array(1_000_000).fill("x");

const timer = setInterval(() => {
  const node = document.getElementById("status");
  if (node) node.textContent = String(data.length);
}, 1000);

// 节点移除后定时器仍在跑：定时器表 → 回调闭包 → data
// 收尾：clearInterval(timer)
```

容易误判的是「节点都移除了，定时器应该自己停了吧」——不会。DOM 子树的移除只断开节点与文档的关联，定时器链路完全不动；回调里的 `document.getElementById` 拿到 null 只是不再更新文本，data 照常被持有。收尾动作只有一种：`clearInterval(timer)`——把表项删掉，链条才断。

**3. 脱离 DOM 的引用（游离节点）**：把某个按钮的引用缓存在 JS 对象里，之后用 `removeChild` 把它从文档移除。树里已经没有这个节点了，但 JS 变量仍然持有它——这就是游离（detached）DOM 节点：从 DOM 树的视角它已经删除，从 GC 的视角它依然从根可达。

```javascript
const cache = { button: document.getElementById("submit") };

document.body.removeChild(document.getElementById("submit"));
// DOM 树里已无此节点，但 cache.button 仍整棵持有它

cache.button = null; // 用完置空，链条才断
```

引用链层面的代价常被低估：一个 DOM 节点持有的是整棵子树——子元素、监听器、关联的样式全算在内，实际占用远超「一个节点」的直觉。在 Memory 面板的堆快照里搜 Detached，能直接看到这些树外存活的节点；它们的 Retained Size 往往大得惊人。收尾：缓存用完置 `null`，或者从一开始就用 WeakMap 存「节点 → 元数据」的关联。

**4. 闭包的多余捕获**：回调只需要一个 `id` 字符串，却顺手引用了外层的 `element`——于是整个 DOM 节点被挂进了回调的可存活集。引用链层面：闭包捕获的是整个词法环境（实现上，同一作用域的内嵌函数共享同一个环境记录），而不是「用到的那个变量」——环境里任何一个变量被引用，环境里所有绑定都跟着延长寿命。

```javascript
function assignHandler() {
  const element = document.getElementById("big-panel");
  const id = element.id;

  element.onclick = () => {
    console.log(id); // 只用 id，闭包却把 element 带进了存活集
  };

  element = null; // 改进：切断不必要的引用链
  // 更稳：先提取字段再创建闭包，让大对象不进词法环境
}
```

两种改法：旧写法的解法是把不再需要的引用置空（`element = null`），手动切断链条；更稳的现代写法是先提取、再闭包——进入回调之前把需要的字段取到新局部变量，让大对象根本不进入回调的词法环境——链条从源头就不存在，无需事后清理。

**持有与清理对照**

四组最常见的「错误持有 vs 正确清理」，全部是同一条原理的变体：你注册出去的每一条引用，都要设计好它的断开时机。

定时器清理：

```javascript
// 错误：定时器不会随组件卸载自动消失——表项不删，引用链就在
useEffect(() => {
  setInterval(pollStatus, 5000);
  // 组件卸载后回调仍每 5 秒触发，
  // 闭包持有的 props/state 全部常驻
}, []);
```

```javascript
// 正确：注册与清理成对出现，把清理函数交给卸载流程
useEffect(() => {
  const id = setInterval(pollStatus, 5000);
  return () => clearInterval(id); // 卸载即断链
}, []);
```

事件监听清理：

```javascript
// 错误：监听器是节点对回调的强引用——回调闭包里的状态跟着节点寿命走
function mount(el) {
  el.addEventListener("resize", onResize);
  // 没有 removeEventListener 的对偶调用
}
```

```javascript
// 正确：AbortSignal 让「成组解绑」变成一行
function mount(el) {
  const ac = new AbortController();
  el.addEventListener("resize", onResize, {
    signal: ac.signal,
  });
  return () => ac.abort(); // 一次解绑该信号上的全部监听
}
```

闭包持有大对象：

```javascript
// 错误：词法环境整体被捕获，大对象为一个 byteLength 陪葬
function track(buffer) {          // 数十 MB 的 buffer
  window.addEventListener("quit", () => {
    report(buffer.byteLength);    // 只用一个小字段
  });
}
```

```javascript
// 正确：先提取到局部变量，从源头不建立引用链
function track(buffer) {
  const size = buffer.byteLength;
  window.addEventListener("quit", () => {
    report(size);
  });
}
```

游离 DOM 节点：

```javascript
// 错误：「树外还挂着」的缓存用强引用数组就是泄漏
const nodes = [];
function detach(el) {
  nodes.push(el);  // 强引用数组缓存了节点
  el.remove();     // 树里移除，但整棵子树被持有
}
```

```javascript
// 正确：给对象附加元数据用 WeakMap（弱引用不阻止回收）
const meta = new WeakMap();
function detach(el) {
  meta.set(el, { detachedAt: Date.now() });
  el.remove();
  // 其他引用断掉后，节点可被正常 GC
}
```

**GC 暂停的量级与工程边界**

标记清除需要 stop-the-world 的阶段是全量标记——标记时对象图不能被并发修改出歧义。V8 的 Orinoco 项目把这个停顿拆碎了：增量标记把标记切成小片穿插在脚本执行之间，并发标记交给后台线程、清除与整理部分并行——单次主线程停顿压到毫秒级。停顿时长强依赖堆大小与存活对象数，下表只用于建立直觉，不是基准数据：

| 回收类型 | 主线程停顿量级 |
|---------|--------------|
| 次要 GC（新生代） | 约 1ms |
| 增量标记单片 | 几 ms 内 |
| 并发回收主线程切片 | 约 5ms |
| 全量标记-清除（大堆/旧式） | 约 50ms |

对写代码的要求由量级反推：次要 GC 频繁但便宜，真正伤页面的是把对象养进老生代——一次性分配巨量对象、缓存只增不减，都会触发昂贵的全量回收。减压三板斧：数组清空用 `arr.length = 0` 复用对象；大对象用完置 `null` 解除引用；定时器/监听器注册与清理严格成对。高频创建大对象的热路径（动画、游戏循环）再考虑对象池复用。

减少 GC 压力的常用写法（辅助汇总）：

```javascript
// 数组：不重新赋值，原地清空复用对象
var arr = [1, 2, 3, 4, 5];
arr.length = 0; // 清空数组，不创建新对象

// 对象：大对象用完解除引用，便于回收
var obj = { a: 1, b: 2 };
obj = null;

// 避免意外的全局变量（全局对象是 GC 的根，挂上就常驻）
'use strict';
function foo() {
  bar = 'This will throw an error'; // ReferenceError，当场暴露
}

// 定时器与监听器：注册与清理严格成对
var timer = setInterval(function () {
  console.log('Running');
}, 1000);
clearInterval(timer); // 不再需要时清除

var element = document.getElementById('button');
var handler = function () {
  console.log('Clicked');
};
element.addEventListener('click', handler);
element.removeEventListener('click', handler); // 不再需要时移除
```

**经典追问链**

**Q1：标记清除的「根」具体指什么？**

*考察点：可达性分析的起点认知——「根」说不全，泄漏分析就是瞎猜。*

三处：全局对象（浏览器的 window/globalThis、Node 的 globalThis）；当前调用栈上所有帧的局部变量；宿主环境注册的引用（DOM 节点上的事件处理器、定时器表里的回调等）。从这些起点沿引用链能摸到的对象都算存活。泄漏排查的第一步永远是问：是哪条从根出发的链挂住了它？

延伸：引擎实现角度：V8 分新生代/老生代，次要回收（Scavenger）只扫新生代，跨代引用靠「记忆集」记录——不必每次回收都遍历全堆，这是停顿能压低的结构基础。

**Q2：setInterval 的回调到底被谁持有？不清除为什么会泄漏？**

*考察点：把「定时器泄漏」落到引用链上——说得出宿主定时器表的才是懂机制的。*

宿主环境维护一张定时器表：setInterval 注册后，表项持有回调函数，回调闭包引用词法环境，词法环境里躺着 data 等大对象——这条链从「宿主注册的引用」这个根出发，全程强引用。clearInterval 把表项移除，链条才断。组件卸载或节点移除不会自动清定时器，这正是定时器泄漏高发的原因。

延伸：setTimeout 未触发的回调同理持有闭包；防抖/节流实例在组件卸载时不清 cancel，是同一条引用链在工程层的变体。

**Q3：GC 运行时会卡住页面吗？**

*考察点：stop-the-world 与引擎演进——只答「会」说明没跟过现代回收器的增量/并发设计。*

会，但已不是全量长停顿：全量标记阶段必须 stop-the-world（标记时对象图不能被并发修改出歧义），而 V8 的 Orinoco 方案把一次长停顿拆碎——增量标记切成小片穿插在脚本之间、并发标记交给后台线程、清除与整理部分并行，单次主线程停顿压到毫秒级。对代码的要求不变：避免一次性分配巨量对象、避免内存持续涨进老生代频繁触发全量回收。

延伸：感知手段：Performance 面板主线程轨上的锯齿状短停顿就是 GC 事件；Node 侧加 `--trace-gc` 能看到每次回收的耗时、原因（scavenge/mark-compact）与前后堆大小。

**Q4：Chrome DevTools 里怎么定位一个真实泄漏？**

*考察点：工具链的实操深度——说得出三快照对比与 Retained Size 的，才是排查过现场的人。*

标准流程：Performance 面板录一段操作，看内存曲线锯齿是否只涨不跌——涨说明分配速率长期大于回收；Memory 面板拍堆快照（Heap Snapshot），用 Comparison 视图对比两次快照中持续增长的对象；按 Retained Size 排序找持有者——Retained Size 是「这个对象被回收后能连带释放的总内存」，比 Shallow Size 更接近泄漏的体感。

延伸：进阶：Allocation instrumentation on timeline 能记录每次分配的调用栈，直接定位高频分配点；游离节点在快照里搜 Detached 关键字——detached 却有 Retained Size 的节点就是树外存活的铁证。

**Q5：WeakMap/WeakSet 和内存泄漏什么关系？什么场景该用？**

*考察点：弱引用语义——「不参与可达性计算」这一句要能展开到使用场景，否则只是背名词。*

WeakMap 的键是弱引用：不参与 GC 的可达性判断——对象的其他引用都断掉后就会被正常回收，WeakMap 里的表项随之消失。适合「给对象附加元数据但不延长寿命」：DOM 节点的附加数据、组件实例的私有状态。用 Map 做同样的事就是经典泄漏：Map 活多久，键就被强引用多久。

延伸：配套 API：WeakRef 持弱引用、FinalizationRegistry 在对象回收后收通知——但官方文档明确提醒不应依赖它们的清理时机做资源管理逻辑（回收时机不确定），清理动作请放在代码路径里主动做。

延伸阅读：防抖和节流到底差在哪（见设计模式篇，定时器泄漏的工程变体）、闭包在工程里怎么用（本章前文）。

## 总结与最佳实践

### 关键要点

1. **作用域**是变量的有效访问范围，JavaScript 使用词法作用域——链在函数定义时定型
2. **作用域链**通过环境记录的 outer 引用物理串成，查找命中即停，内层遮蔽外层
3. **执行上下文**分创建/执行/回收三阶段：「提升」是创建阶段登记的副产品，不是代码搬移
4. **this** 由调用方式注入，优先级 new > 显式 > 隐式 > 默认；箭头函数词法捕获是唯一例外
5. **闭包** = 函数 + 定义处词法环境的引用，捕获的是变量绑定；状态份数 = 工厂调用次数
6. **垃圾回收**以可达性为唯一标准；泄漏 = 不再需要却仍被从根出发的引用链挂着

### 最佳实践

1. 优先使用 `let` 和 `const`，把 `var` 的函数级泄漏与共享绑定问题从源头排除
2. 理解闭包的工作原理：循环异步回调一律 `let`（或 IIFE），回调只捕获真正需要的字段
3. 定时器、事件监听、订阅的注册与清理严格成对；批量解绑可用 `AbortController`
4. 「给对象附加元数据」用 WeakMap 而不是 Map，避免延长对象寿命
5. 使用严格模式/ESM 避免意外的全局变量——它们挂在 GC 的根上，永远存活
6. 浮点比较用容差、深拷贝优先 `structuredClone`、单测里把单例闭包改成工厂
