# TypeScript 学习笔记

---

## 1. `any` / `unknown` / `never` 的区别

| 类型 | 含义 | 赋值限制 | 使用限制 |
|------|------|----------|----------|
| `any` | 任意类型，关闭类型检查 | 可赋给任何类型 | 无限制，不安全 |
| `unknown` | 未知类型，类型安全的 `any` | 只能赋给 `unknown` / `any` | 使用前必须做类型收窄 |
| `never` | 永不存在的值（空集） | 可赋给任何类型 | 没有值能赋给它 |

```typescript
// any：跳过类型检查，危险
let a: any = 42;
a.foo(); // 不报错，运行时可能崩溃

// unknown：使用前必须收窄
let u: unknown = "hello";
if (typeof u === "string") {
  u.toUpperCase(); // OK
}

// never：函数永不返回（抛出异常或死循环）
function fail(msg: string): never {
  throw new Error(msg);
}

// never 在联合类型中会被消除
type T = string | never; // => string
```

## 2. `bigint` 与 `number` 类型不兼容

`bigint` 和 `number` 是两种独立的原始类型，不能混用。

```typescript
const big: bigint = 100n;
const num: number = 100;

// big + num; // Error: 不能混合运算
const result = big + BigInt(num); // 需要显式转换

// 字面量类型
const x = 9007199254740991n; // bigint
const y = 9007199254740991;  // number
```

> `bigint` 用于表示超过 `Number.MAX_SAFE_INTEGER` 的整数。

## 3. `Symbol()` 与 `new Symbol()` 的区别

- `Symbol()` 是函数调用，返回一个唯一的 symbol 值 ✅
- `new Symbol()` 是构造函数调用，**会报错** ❌

```typescript
const s1 = Symbol("desc");   // OK，类型为 symbol
const s2 = Symbol("desc");
s1 === s2; // false，每次调用都唯一

// new Symbol(); // TypeError: Symbol is not a constructor

// unique symbol：需要 const 声明
const s3: unique symbol = Symbol();
// let s4: unique symbol = Symbol(); // Error，必须用 const
```

## 4. `object` 与 `Object` 的区别

| 类型 | 含义 |
|------|------|
| `object` | 小写，表示所有非原始类型（引用类型） |
| `Object` | 大写，几乎所有值都能赋给它（包括原始类型），因为原始类型有包装对象 |

```typescript
// object：只接受引用类型
let o: object = {};       // OK
let o2: object = [];      // OK
// let o3: object = 42;   // Error

// Object：接受几乎所有值（不推荐使用）
let O: Object = 42;       // OK（number 有包装对象）
let O2: Object = "str";   // OK
// let O3: Object = null; // Error（null/undefined 除外）

// 实践中推荐用 Record<string, unknown> 或具体接口代替
```

## 5. `type` 可以使用模板字符串嵌套

TypeScript 支持在类型层面使用模板字符串，可以组合和生成字符串字面量类型。

```typescript
type Direction = "top" | "bottom" | "left" | "right";
type CSSProperty = `margin-${Direction}`;
// => "margin-top" | "margin-bottom" | "margin-left" | "margin-right"

type EventName = "click" | "focus";
type Handler = `on${Capitalize<EventName>}`;
// => "onClick" | "onFocus"

// 嵌套组合
type Row = 1 | 2 | 3;
type Col = "a" | "b" | "c";
type Cell = `${Row}-${Col}`;
// => "1-a" | "1-b" | "1-c" | "2-a" | ...
```

## 6. `typeof` 运算符在 TypeScript 中的重写

TypeScript 中 `typeof` 有两种用途：

**① 运行时（JavaScript 原有行为）：** 返回字符串，用于类型守卫

```typescript
typeof "hello" // => "string"（运行时）
```

**② 类型层面（TypeScript 扩展）：** 获取变量/函数的类型

```typescript
const config = { host: "localhost", port: 3000 };
type Config = typeof config;
// => { host: string; port: number }

function greet(name: string) { return `Hello, ${name}`; }
type GreetFn = typeof greet;
// => (name: string) => string

// 常与 ReturnType、keyof 配合使用
type Keys = keyof typeof config; // => "host" | "port"
```

## 7. 数组类型获取元素类型：`Names[number]`

```typescript
const colors = ["red", "green", "blue"] as const;
type Color = typeof colors[number];
// => "red" | "green" | "blue"

// 普通数组类型
type Arr = string[];
type Item = Arr[number]; // => string

// 对象类型用 keyof 获取键，用 T[keyof T] 获取值类型
type Obj = { a: number; b: string };
type Values = Obj[keyof Obj]; // => number | string
```

## 8. 只读数组的声明方式

```typescript
// 方式一：readonly 修饰符
const arr1: readonly number[] = [1, 2, 3];

// 方式二：ReadonlyArray 泛型
const arr2: ReadonlyArray<number> = [1, 2, 3];

// 方式三：as const 断言（最严格，元素类型也变为字面量）
const arr3 = [1, 2, 3] as const;
// 类型为 readonly [1, 2, 3]，而非 readonly number[]

// arr1.push(4);  // Error
// arr1[0] = 10;  // Error
```

> `as const` 会递归地将所有属性变为 `readonly`，且值类型收窄为字面量类型。

## 9. 数组与元组的区别

| 特性 | 数组 `T[]` | 元组 `[T, U]` |
|------|-----------|--------------|
| 长度 | 不固定 | 固定 |
| 元素类型 | 所有元素同类型 | 每个位置类型独立 |
| 语义 | 同类数据集合 | 有结构的有序数据 |

```typescript
// 数组：长度不定，元素同类型
const arr: number[] = [1, 2, 3, 4];

// 元组：长度固定，每个位置类型明确
const tuple: [string, number, boolean] = ["Alice", 30, true];
tuple[0]; // string
tuple[1]; // number
```

## 10. 元组可选成员（后置 `?`）

元组中可以用 `?` 标记可选成员，但只能放在末尾。

```typescript
type Point = [x: number, y: number, z?: number];

const p1: Point = [1, 2];      // OK
const p2: Point = [1, 2, 3];   // OK

// 可选成员必须在必选成员之后
// type Bad = [x?: number, y: number]; // Error
```

## 11. 元组扩展运算符

元组支持 `...` 展开其他元组或数组类型，用于组合和可变参数。

```typescript
type Head = [string, number];
type Tail = [boolean, Date];
type Combined = [...Head, ...Tail];
// => [string, number, boolean, Date]

// 可变参数元组（rest 元素）
type StringsAndNumber = [...string[], number];
// 任意数量的 string，最后一个是 number

// 函数参数中使用
function log(...args: [string, ...number[]]): void {
  console.log(args[0], args.slice(1));
}
log("values:", 1, 2, 3); // OK
```

## 12. 元组成员别名

元组成员可以添加标签（别名），提升可读性，不影响类型兼容性。

```typescript
type Color = [
  red: number,
  green: number,
  blue: number
];

type Range = [start: number, end: number];

// 有别名和无别名的元组类型兼容
const c: Color = [255, 128, 0];
const r: [number, number] = c; // OK，别名不影响结构兼容
```

## 13. 获取元组元素的类型

与数组相同，使用索引或 `[number]`。

```typescript
type RGB = [red: number, green: number, blue: number];

type First = RGB[0];    // number

// 获取所有元素类型的联合
type AnyElement = RGB[number]; // number

// 获取元组长度
type Len = RGB["length"]; // 3
```

## 14. 函数类型的几种写法

```typescript
// 方式一：函数声明
function add(a: number, b: number): number {
  return a + b;
}

// 方式二：函数表达式
const add2 = function(a: number, b: number): number {
  return a + b;
};

// 方式三：箭头函数
const add3 = (a: number, b: number): number => a + b;

// 方式四：type 定义函数类型
type AddFn = (a: number, b: number) => number;
const add4: AddFn = (a, b) => a + b;

// 方式五：interface 定义（可描述重载）
interface AddInterface {
  (a: number, b: number): number;
}

// 方式六：泛型函数
const identity = <T>(x: T): T => x;
```

## 15. 函数重载的写法

TypeScript 函数重载需要先写多个重载签名，再写一个实现签名。

```typescript
// 重载签名（只声明，不实现）
function format(value: string): string;
function format(value: number, decimals: number): string;

// 实现签名（必须兼容所有重载）
function format(value: string | number, decimals?: number): string {
  if (typeof value === "string") {
    return value.trim();
  }
  return value.toFixed(decimals ?? 2);
}

format("hello ");       // OK => "hello"
format(3.14159, 2);     // OK => "3.14"
// format(3.14);        // Error，不匹配任何重载签名
```

> 实现签名对外不可见，调用时只能匹配重载签名。

## 16. `readonly` 与 `Readonly` 的区别

| | `readonly` | `Readonly<T>` |
|---|---|---|
| 类型 | 关键字修饰符 | 内置工具类型 |
| 作用范围 | 修饰单个属性或数组 | 将对象所有属性变为只读 |
| 深度 | 浅层 | 浅层（非递归） |

```typescript
// readonly：修饰单个属性
interface User {
  readonly id: number;
  name: string;
}

// Readonly<T>：批量将所有属性变为只读
type ReadonlyUser = Readonly<User>;
// => { readonly id: number; readonly name: string }

// 注意：两者都是浅层只读
interface Nested {
  inner: { value: number };
}
type R = Readonly<Nested>;
// inner 本身只读，但 inner.value 仍可修改

// 深度只读需要递归工具类型
type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends object ? DeepReadonly<T[K]> : T[K];
};
```

## 17. 对象类型的严格字面量检查与结构类型原则

**结构类型原则（鸭子类型）：** 类型兼容性基于结构，而非名称。

```typescript
interface Point { x: number; y: number; }

const p = { x: 1, y: 2, z: 3 }; // 多一个属性
const point: Point = p;           // OK，结构兼容
```

**严格字面量检查（Fresh Object Check）：** 直接赋值对象字面量时，不允许有多余属性。

```typescript
// 直接赋值字面量 => 触发严格检查
const point2: Point = { x: 1, y: 2, z: 3 }; // Error: 不允许多余属性

// 通过变量中转 => 绕过严格检查（结构兼容即可）
const obj = { x: 1, y: 2, z: 3 };
const point3: Point = obj; // OK
```

> 严格字面量检查只在对象字面量**直接赋值**时触发，目的是防止拼写错误。

## 18. `interface` 与 `type` 的区别

| 特性 | `interface` | `type` |
|------|------------|--------|
| 声明合并 | ✅ 支持（同名自动合并） | ❌ 不支持（重复声明报错） |
| 扩展语法 | `extends` | `&`（交叉类型） |
| 描述范围 | 只能描述对象/函数/类 | 可描述任意类型（联合、元组、原始类型等） |
| 计算属性 | ❌ 不支持 | ✅ 支持（映射类型） |
| 错误提示 | 通常更友好 | 复杂类型可能较难读 |

```typescript
// interface 声明合并
interface Window { title: string; }
interface Window { width: number; }
// 合并为 { title: string; width: number }

// type 不能重复声明
// type Foo = string;
// type Foo = number; // Error

// type 可以描述联合类型
type ID = string | number;
type Callback = () => void;
type Pair = [string, number];

// 扩展方式
interface Animal { name: string; }
interface Dog extends Animal { breed: string; }

type AnimalType = { name: string };
type DogType = AnimalType & { breed: string };
```

> **实践建议：** 公共 API 和库类型用 `interface`（支持扩展合并）；内部类型、联合/元组等复杂类型用 `type`。

## 19. 前端实际用得到多少 TS 功能？

*难度：入门 ｜ 标签：TypeScript、工具类型、const enum、namespace、学习路径*

**「功能很多、用得少」是对的，而且是设计使然**：日常书写九成以上只落到一小撮——类型标注、type/interface、联合与字面量联合、**泛型的使用**、收窄、`as const`、几个高频工具类型和 `import type`。类型系统的复杂度只服务两类消费者：给 JS 的动态模式找静态建模、让库作者把 API 契约写精确。应用前端是类型的**消费者**不是**生产者**——复杂度被库吸收了。实践守则一句话：一个类型三行内说不清意图，就简化它。

### 三层功能地图

把 TS 的全部功能按「日常书写频率」切成三层，边界比想象中清晰。判断标准不是「会不会写」，而是「谁在生产类型」——这决定了第三层的功能你几乎永远没有正当理由使用。

```text
┌─ 日常主力（九成书写）──────────────────────────────────────┐
│ 类型标注 · type/interface · 联合与字面量联合 · 泛型的使用      │
│ 收窄 · as const · Partial/Pick/Omit/Record · import type   │
├─ 读得懂为主（库作者主战场）─────────────────────────────────┤
│ 条件类型 + infer · 映射类型修饰符 · 模板字面量类型 · 可变元组   │
│ 递归类型——应用层需要能读懂库的报错，很少需要写                │
├─ 应用层基本不碰 ─────────────────────────────────────────┤
│ namespace（运行时已死）· const enum（被单文件转译器淘汰）      │
│ 装饰器（除非框架约定）· 主动 declaration merging · unique symbol │
└──────────────────────────────────────────────────────────┘
```

### 消费者与生产者

类型系统的复杂度只服务两类消费者。第一类：给 JS 的动态模式找静态建模——收窄让「鸭子类型」的世界可检查，泛型变体让「任意类型但保持关联」可表达；第二类：让库作者把 API 契约写精确——React 的类型、xyflow 的类型把成吨的类型体操吸收进了 `node_modules`。你标一个 props 就享受全链路检查，那份「类型完备」的体验是别人用条件类型换来的。

所以应用前端是类型的消费者：消费类型、读懂类型报错，而不是生产复杂类型。SQL 使用者不需要会写存储引擎，但要会写查询、看懂执行计划——定位完全同构。真正的安全增益也不在类型技巧里，而在你已打开的那些检查开关（`strict`、`exactOptionalPropertyTypes`、`noUncheckedIndexedAccess`）——它们拦的是真实世界的 bug，不是炫技场。

### 常用工具类型清单

第一层里最值得背下来的就是内置工具类型——它们全是**类型层的纯函数**：对已有类型做变换，编译后没有任何运行时对应物。按用途分四组：

| 组 | 工具类型 | 一句话 |
|----|---------|--------|
| 结构变换 | Partial / Required / Readonly | 全变可选 / 全变必选 / 全变只读 |
| 结构变换 | Pick\<T, K\> / Omit\<T, K\> | 从大类型里挑字段 / 剔字段 |
| 结构变换 | Record\<K, V\> | 键集到值类型的映射 |
| 提取 | ReturnType\<F\> / Parameters\<F\> | 拿函数返回值类型 / 参数元组 |
| 提取 | Awaited\<T\> / InstanceType\<C\> | 解开 Promise 拿值类型 / 拿类的实例类型 |
| 联合过滤 | Exclude / Extract / NonNullable | 从联合里剔除 / 留下 / 去 null undefined |
| 字符串 | Uppercase / Capitalize … | 字面量字符串的大小写变换 |

### 两个「已死」的边界

**const enum 的处境**：它的卖点是「不生成运行时对象，所有使用点直接内联成字面量」——但跨文件内联需要全程序视角：a.ts 里的 `Color.Red` 要内联成 0，编译器必须看到 b.ts 里的定义。tsc 天然有全程序视角，业务代码里的 const enum 正常内联（实测：跨文件内联成字面量、零运行时输出）；`isolatedModules` 只拦**ambient**（.d.ts 声明里的）const enum——声明文件没有实现面可看，直接报错（TS 7 实测错误码 TS2748）。真正的变数在单文件转译器：esbuild/Oxc 的 transform 模式一次只看一个文件，会把 const enum **静默降级**成普通 enum——生成运行时对象、失去内联，行为变了却没有任何报错。它被生态事实性淘汰的核心正是这份「行为随工具链漂移的不确定性」，替代写法是 `as const` 对象加推导类型——键做类型、值做运行时，任何工具链下行为一致。

**反例：const enum**

```typescript
const enum Color { Red = '#f00' }
let c = Color.Red;
```

isolatedModules 只拦 .d.ts 里的 ambient const enum；业务代码在 tsc 下正常内联，但被 esbuild/Oxc 类单文件转译器静默降级成普通 enum——生成运行时对象、失去内联，全程无报错。

**正例：as const 对象**

```typescript
const Color = { Red: '#f00' } as const
type Color = keyof typeof Color
```

值做运行时对象、键做类型——转译器无关，两端真实存在。

**namespace 的真假生死**：它前身叫 internal module，是 ES modules 诞生之前 TS 自己的模块方案。作为「运行时组织代码」的机制它已死——当代码都走 ES modules，用 namespace 包运行时逻辑失去存在理由，且单文件转译器只支持基础形态。但作为「类型与声明的组织空间」它活得好好的：`@types/node` 里的 `NodeJS.ProcessEnv`、React 18+ 类型的 `React.JSX`、.d.ts 里组织一坨相关类型，全是纯类型容器，不产生任何运行时代码。判断标准一句话：**里面只有 interface/type/declare 就活着；里面有会编译出 JS 的逻辑就该迁 ES modules**。

> **提示：你在别处看到大量 namespace？** 大概率在 .d.ts 声明层——那是合法且常见的用法。真正该警惕的只有「用 namespace 包业务逻辑」的存量代码：那是前模块时代的化石。

### 三个高频误区

- 把**类型体操当水平证明**——嵌套条件类型加多层 infer 在应用代码里是负资产：编译变慢、报错变天书、同事读不懂；
- 以为**类型会影响运行时**——工具类型编译后无对应物，类型标注转译即被擦除；
- 在 **Vite 项目里用 const enum**——单文件转译管线的毒药，用 `as const` 替代。

### 追问链

**Partial\<T\> 在运行时存在吗？**

不存在。所有工具类型都是类型层的变换公式，编译后的 JS 里没有任何对应物——它们只在编译期帮检查器理解你的意图。

**为什么说应用开发者是「类型的消费者」？**

因为类型系统的复杂度被库吸收了：React、路由、组件库的类型把条件类型、infer、模板字面量都用在了它们的类型定义里，换来你在应用层「标个 props 就全链路检查」。你消费这份精确，不生产它。推论：读懂库的类型报错（中层能力）比会写体操（生产能力）对应用开发者更实用——面试里能讲清一个第三方类型报错在说什么，比手写 ValueOf 深层嵌套更能证明水平。

**const enum 在 Vite 项目里会发生什么？**

tsc 一侧几乎不报错：业务代码里的 const enum 在全程序编译下正常内联，isolatedModules 只对 .d.ts 里的 ambient const enum 报错（TS 7 实测错误码 TS2748）。真正的变化在转译侧：esbuild/Oxc 的单文件 transform 会把它静默降级成普通 enum——生成运行时对象、不再内联，行为改变却无任何警告；带全程序视角的 bundler（esbuild bundle、rolldown）则能恢复跨文件内联。同一份代码行为随工具链漂移，这正是它的死刑判决——替代：as const 对象 + keyof typeof。

**什么信号出现时，才说明你「需要」写条件类型和 infer？**

当你在生产类型而不是消费类型时：写通用工具库、写组件库的类型签名、封装需要保持类型关联的泛型 API。应用代码里出现它的正当场景极少——多数时候一个联合类型加几行映射就够了。判断标准可操作化：这个类型三行内说不清意图就简化。类型是写给人看的合同，编译器不在乎它多优雅。

### 记忆点

- **应用层是类型消费者**——复杂度被库吸收——你标 props 享受的全链路检查，是库作者的体操换来的。
- **三行说不清就简化**——类型是写给人看的合同。应用代码里类型体操是负资产：编译慢、报错天书、可读性差。

## 20. TypeScript 的各个版本都迭代了什么？

*难度：入门 ｜ 标签：TypeScript、版本史、strictNullChecks、satisfies*

**TS 的大版本是六条性格完全不同的主线**：1.x 立项（带标签的 JS）、2.x **类型系统奠基**（strictNullChecks 与条件类型，今天的 TS 从这里开始）、3.x **工程化**（references、import type）、4.x 类型能力巅峰、5.x **现代化与性能**（面向构建管线集成）、6/7 原生化（Go 重写）。两条贯穿线：语言能力在 4.x 就基本造完，之后全力转向工具链；破坏变更永远走「5.x 废弃 → 6.0 警告 → 7.0 硬移除」三级火箭。

```text
1.x 立项        2.x 类型奠基     3.x 工程化       4.x 类型巅峰     5.x 现代化      6→7 原生化
2012-14   →    strictNullChecks → references  →   模板字面量   →   标准装饰器  →   过渡 · Go 重写
带标签的 JS     条件类型          import type       satisfies       提速
```

### 2.x：现代 TS 的地基（2016-2018）

这五年决定了今天 TS 的样子。2.0 的 `strictNullChecks` 是史上最大的单一变更：null 和 undefined 从「所有类型的合法成员」变成独立类型，JS 的空值问题第一次能被静态拦截——在此之前整个类型系统对最常见的运行时错误视而不见。同期控制流分析登场：`if (typeof x === 'string')` 之后 x 自动收窄，静态分析第一次「顺着代码的执行逻辑思考」，而不是孤立地看每一行标注。

同一时期铺开的还有类型系统的机器底座：2.1 的 keyof 加映射类型给了 `Partial`/`Pick` 底层机制，2.3 的 `strict` 把一堆严格检查打包成一个开关，2.8 的条件类型加 `infer` 让类型系统具备了「模式匹配」能力——这三块拼图日后演化出整个工具类型生态。生态侧，2.0 把 @types 迁到了 npm：类型分发从此搭上包管理的便车，DefinitelyTyped 的仓库形态让「给 JS 库补类型」第一次有了规模化分工。TS 从「贴标签的 JS」升级为一门真正的类型系统。

### 3.x：工程化与一个时代的落幕（2018-2020）

3.0 的 project references 与 `tsc -b` build mode 让大仓库和 monorepo 可以按依赖图增量构建——你 build script 里那个 `-b` 就诞生于此。3.0 还有 `unknown` 顶型。但真正值得记住的是 3.7：`?.` 和 `??` 的实现是「TS 抢跑 JS 语法」时代的尾声——此后官方明确退守**类型是主场，JS 语法只跟进 TC39 stage 3**。3.8 的 `import type` 则是一步伏笔：为几年后单文件转译器的普及提前铺路。

工程化不只指仓库结构，也指 tsc 自身的可扩展性：3.4 的 `--incremental` 把上次编译的形状信息存盘复用，大型项目的二次检查从全量重算变成增量追补——「按依赖图构建」（references）与「按时间增量构建」（incremental）在 3.x 凑齐，tsc 第一次能稳定伺候 monorepo 规模的代码库。

### 4.x：类型能力的巅峰（2020-2022）

4.0 可变元组、4.1 模板字面量类型与递归条件类型（「类型体操」时代的燃料）、4.3 的 `override`、4.5 的内联 `import { type Foo }`、4.9 的 `satisfies`（按目标校验但保留推断——DX 明星特性）。语言能力到顶的标志很直白：从这之后，每个版本的 release notes 一半是编辑器功能。这不是偷懒——TypeScript 的产品形态本来就是**编译器 + 语言服务双面**，语言造完了，重心自然移向消费它的工具。

巅峰的另一面是成本：模板字面量套递归条件类型的组合威力巨大也极易失控——类型体操的黄金年代与「编译器卡死」「内存爆炸」的事故报告同期出现，4.x 后半程的 release notes 开始频繁出现性能修复。这条曲线给 5.x 把重心转向性能与管线集成做了最直接的铺垫。

### 5.x → 7：现代化与原生（2023-）

5.0 换上标准 stage-3 装饰器、正式引入 `moduleResolution: "bundler"` 承认打包器语义、内部重写为 ESM 换来提速；5.2 的 `using` 对齐显式资源管理提案；5.5 的推断类型谓词让 `filter` 回调自动收窄；5.6 的 `noUncheckedSideEffectImports` 继续收紧边界。特征非常一致：**不再造新的类型机器，全力转向与现代构建管线的集成和编译性能**。6.0 则是纯粹的过渡版——最后一个 JS 实现的编译器，内容几乎全是拆除：大范围废弃、默认值向 7 对齐。7.0 换成 Go 原生二进制，故事翻页。

5.x 还有一条容易被忽视的支线：`isolatedDeclarations`（5.5 实验性）。它约束「声明导出的类型必须显式标注」，让转译器不跑全程序推断也能直接产出 .d.ts——和 3.8 的 `import type` 遥相呼应，都是为「类型可被单文件工具静态处理」补拼图。语言设计在给工具链让路，这条线贯穿了后半程。

### 破坏如何拆除：三级火箭

TS 向后兼容记录极佳的秘诀是把破坏集中在大版本、并且提前两级预告：先废弃（警告但可用），再改默认（给缓冲阀），最后硬移除。你的升级动作因此有章可循——读官方 breaking changes、按废弃清单提前清理，而不是等构建炸了再查。

这套机制的成本是**版本节奏被拆除任务占满**：每个破坏都要提前两个版本预告，6.0「几乎没有新功能」正是代价本身。换来的收益是升级路径永远有据可查——废弃警告本身就是迁移清单，生态可以在缓冲期内分批消化，而不是被一次大版本集体冲垮。

| 版本 | 同一选项的命运 |
|------|---------------|
| TS 5.x | 进入废弃名单：仍可用，文档标记弃用 |
| 6.0 | 改默认值并发出警告，`ignoreDeprecations: "6.0"` 可临时缓冲 |
| 7.0 | 硬移除：写了直接报错，缓冲阀失效 |

> **注意：三个升级误区。** ① 以为 minor 版本只有修 bug——**裁判型依赖的 minor 也可能新增检查**，lockfile 锁死才稳；② 以为废弃就能立刻删用法——6.0 的缓冲阀就是给存量代码留的时间窗；③ 拿二手 changelog 当真——「baseUrl 被移除」这类传闻要以自己仓库 `tsc -b --dry` 实测为准。

**反例：从 5.2 直接跳 6.0**

```bash
npm i -D typescript@latest
# 跑构建：47 个类型错误一次性砸下来
```

大版本跨度升级，breaking changes 全部堆积在升级当天。

**正例：升级前先清完中间版本的废弃警告**

```bash
tsc --noEmit                 # deprecation 提示逐条清理
npm i -D typescript@latest   # 再上大版本，构建仍绿
```

废弃警告本身就是迁移清单——缓冲期内分批消化，而不是被一次大版本集体冲垮。

### 追问链

**为什么说 strictNullChecks 是史上最大的单一变更？**

因为它改变了 null 和 undefined 的类型地位：从「所有类型的合法成员」变成独立类型。在此之前整个类型系统对 JS 里最常见的运行时错误（空值）视而不见；在此之后，忘记判空在编译期就报错。补充：控制流分析同期进场——if 里 typeof 收窄之后，TS 开始「顺着执行逻辑思考」而不是孤立地看每行标注，这是 narrowing 的起点。

**3.7 版本为什么是历史转折点？**

3.7 实现了尚未定案的 `?.` 和 `??`，是「TS 抢跑 JS 语法」时代的尾声。此后官方明确策略：类型是主场，JS 语法只跟进 TC39 stage 3——不再用编译器替标准委员会做实验。补充：3.8 的 import type 是同期的伏笔——它为「类型可被静态识别并擦除」提供了显式语法，几年后单文件转译器普及，这个先见之明兑现了。

**条件类型加 infer 到底解决了什么问题？**

给类型做模式匹配：`T extends Array<infer U> ? U : never` 让你能从既有类型里「提取」感兴趣的部分。没有它，映射类型只能变换已知结构，无法对未知形状做逆向推导——Promise 的返回值类型、函数参数类型都提不出来。

**6.0 这种「几乎没新功能」的版本，存在的意义是什么？**

为 7.0 扫清障碍：6.0 把大范围废弃落地、把默认值向 7 对齐、用 ignoreDeprecations 提供缓冲。等 7.0 硬移除时，受影响的存量项目已经在 6.0 阶段收到过警告——破坏是预告过的，不是突袭的。

**为什么近几年的 release notes 一半是编辑器功能？**

因为 TypeScript 的产品形态本来就是编译器加语言服务双面：语言能力在 4.x 基本造完，之后的性能优化、诊断改进、quick fix 全部落在消费类型的编辑器体验上。看 release notes 的构成变化，能看到产品重心的迁移。这也解释了为什么 5.x 的主线是「与构建管线集成」：moduleResolution bundler、ESM 内部重写、isolatedDeclarations——全是在为「类型系统如何嵌入现代工具链」服务。

### 记忆点

- **现代 TS 始于 2.x**——strictNullChecks、控制流分析、条件类型——今天写代码的每一刻都踩在 2.x 的地基上。
- **类型主场，语法跟 stage 3**——3.7 之后 TS 不再抢跑 JS 语法：它是类型系统，不是预言机。破坏走「废弃→警告→硬移除」三级火箭。

## 21. .d.ts 声明文件到底解决什么问题？

*难度：进阶 ｜ 标签：declaration、.d.ts、declare、类型声明*

`.d.ts`（d = declaration）是**只描述「有什么」、不含「怎么做」的合同文件**——类比 OpenAPI 规范之于 REST 服务，或 protobuf 的 .proto 之于 RPC。它为四个问题而生：给存量 JS 库补类型、充当 TS 库的标准发布形态（js + d.ts）、描述宿主环境（DOM/ES 全局）、给无类型模块挂声明。底层逻辑一句话：**文件级靠名字相邻匹配，内容级只有信任没有验证**——声明文件说模块长什么样，模块的类型面就是什么样。

### 四个存在理由

npm 上十年的包都是 JS，不可能全部 TS 重写；TS 库又不能把源码直接发给用户；浏览器和 Node 的全局对象更不可能由 TS「实现」——三类问题共用同一个解法：把「类型的描述」和「值的实现」拆开放。声明文件就是那个描述：

| 角色 | 场景 | 实例 |
|------|------|------|
| 给存量 JS 补类型 | 包本身是 JS、没有自带类型 | @types/react、@types/node（发布在 @types 作用域下） |
| TS 库的发布形态 | tsc 编译产出 .js + .d.ts，源码可不发 | @xyflow/react 的 dist 里 index.js 与 index.d.ts 并排 |
| 描述宿主环境 | 全局对象与标准库不是 JS 代码写的 | TS 自带的 lib.dom.d.ts、lib.es2022.d.ts 系列 |
| 声明无类型模块 | CSS、图片、私有语法后缀 | declare module '*.css'、vite/client 里的 declare module '*?raw' |

lib 文件的去向：TS 6.x 及之前，lib.d.ts 系列以 lib/*.d.ts 文件随 npm 包分发，可以直接打开翻阅；TS 7（原生）把 lib 内嵌进 Go 原生二进制——包里不再有 lib/*.d.ts 文件。变的只是分发的物理形态：这些「TS 自带的类型」内容没变，从可翻阅的文件变成了二进制内嵌资源。

为什么必须是「分离的描述」而不是「带上实现」？因为检查器需要的只有**形状**：你的代码调用了什么、传什么类型、返回什么——它从不执行被调用的代码。四类角色共享这个判断：给 @types/react 写声明的人不需要重新实现 React，描述宿主环境的人更不可能去实现浏览器。描述与实现分离之后，两者可以用不同的节奏、不同的语言、不同的发布渠道各自演进——这也是合同类比真正成立的地方：合同约束交互面，不约束双方内部。

### 文件级：名字相邻就配上对

匹配规则朴素到不像设计：**同名相邻**。解析落在 `Button.js` 上时，它的类型声明就是同目录的 `Button.d.ts`（模块格式变体同理：`.d.mts` 对 .mjs、`.d.cts` 对 .cjs）。包级则由 package.json 指路：`types`/`typings` 字段或 exports 的 types 条件，直接定位到 dist 里的声明入口。名字相邻匹配解释了一个现象——TS 库发布后你能在编辑器里跳转「实现」跳到 .d.ts：因为对消费者来说，声明文件就是这个模块的全部可见面。

这套朴素规则够用的原因，是它与 npm 的物理布局天然对齐：包发布成目录，声明就放在实现旁边——类型查找完全本地、零配置，不依赖任何中心化注册表。每个包自带合同，安装即生效；`types` 字段与 exports types 条件只是默认规则的「指路牌」，处理 dist 与源码不同名、多入口分包这类发布形态。规则越朴素，覆盖面反而越大。

### 内容级：信任，不验证

这是声明文件最重要也最反直觉的性质：TS **从不核对声明与实现是否一致**。.d.ts 说模块导出一个 `(a: string) => number` 的函数，检查器就信了——哪怕实现里参数是数字、返回的是 string。声明面即类型面，JS 文件的内容对检查器完全隐形。合同只被执行，从不被审计。

为什么设计成「信任」而不是「核对」？因为核对意味着对实现做完整的类型推导——消费任何一个库都要把它的实现纳入自己的检查范围：成本是天文数字，而且会逼着库作者把实现细节变成公共契约。信任模型把成本切干净：声明面是唯一检查对象，实现可以是 JS、可以打包成 wasm、甚至可以由别的语言实现。代价就是**漂移风险**——合同说谎时没有任何机制报警，只能靠发布流程（tsc 自产声明保证自洽）与集成测试兜底。

| 维度 | 声明制（默认） | 推导制（allowJs） |
|------|--------------|------------------|
| 类型从哪来 | 同名 .d.ts / types 字段指路的声明 | tsc 解析 .js 实现，从代码推导（JSDoc 可精化） |
| 与实现的关系 | 信任——从不核对 | 同源——天然一致 |
| 适用场景 | 消费第三方包、库发布 | JS 项目渐进迁移、checkJs 检查 JS 代码 |

> **注意：「类型全绿但运行时炸」的根因。** 声明写错（或过时）时，检查器依然按合同放行你的代码——类型完备不代表运行时正确。skipLibCheck 会进一步跳过对声明文件本身的检查，信任模型加深一层。@types 社区包与实现漂移的风险，正是从这条性质里长出来的。

### declare 家族与全局三姿势

`declare` 是「向检查器描述存在、同时禁止生成代码」的标记词，.d.ts 里的一切都隐式是 declare。家族成员按描述对象分：变量（`declare const/let`）、函数与类（`declare function/class`）、枚举与命名空间（`declare enum/namespace`）、模块（`declare module "x"`，支持 `'*.css'` 通配符）、全局作用域（`declare global`）。它只用于描述「无法用 TS 表达但确实存在的外部世界」——宿主注入的全局、非 TS 模块、环境变量：

```typescript
// 给 window 挂宿主注入的字段（模块文件内必须用 declare global）
declare global {
  interface Window {
    __APP_VERSION__: string;
  }
}

// 给无类型的私有模块挂声明（环境声明）
declare module "*.module.css" {
  const classes: Record<string, string>;
  export default classes;
}

export {}; // 让本文件成为模块，declare global 才合法
```

全局类型声明有三条姿势：**模块内 declare global**（最常用，按需扩展全局接口）；**脚本式文件天然全局**——没有任何顶层 import/export 的 .ts/.d.ts，声明自动进入全局作用域（传统声明文件都长这样）；**收录机制**——放进 tsconfig include 的目录、写进 `types` 白名单、或用三斜线 `/// <reference types="..." />` 指令。日常遇到的 `vite/client` 就是三种姿势的合订本。

**declare 的纪律：描述，不撒谎**

```typescript
// 反例：撒谎式的 declare
declare const config: ReadyConfig;
// 运行时根本没有 config 这个全局——类型全绿、运行时炸，且比没有类型更难排查

// 正例：只描述确实存在的外部世界
declare const __APP_VERSION__: string;
// 构建注入、宿主挂载；红线该用真实类型修，不用 declare 消
```

```typescript
// 反例：万能通配把整棵模块树变 any，检查形同虚设
// ambient.d.ts
declare module "*";

// 正例：只为真实缺失的包补声明
// types/legacy-lib.d.ts
declare module "legacy-lib" { /* 按真实 API */ }
```

### 追问链

**.d.ts 和 .ts 的语法差别是什么？**

只许声明、不许实现：可以有 interface/type/declare 系列，写函数体、赋值语句直接报错。它是 TS 语言内的正式机制（不是口头约定）——编译器专门识别 *.d.ts 扩展名并按声明文件处理，衍生变体 .d.mts/.d.cts 对应 ESM/CJS。

**Button.js 和 Button.d.ts 是怎么配上的？内容会互相校验吗？**

文件级靠名字相邻：同目录同名，解析落在 .js 上自动找同名 .d.ts 拿类型。内容级不校验：TS 从不核对声明的导出面和 JS 实际导出的是否一致——声明说模块长什么样，类型面就是什么样。例外开关是 allowJs/checkJs：让 tsc 解析 .js 实现本身来推导类型（JSDoc 精化），类型来源从「声明」变成「推导」，天然与实现同源。

**为什么 TS 库发布时不直接给 .ts 源码？**

可以但有代价：源码暴露实现细节、消费方被迫承担编译成本（把 tsc 拖进自己的构建）、版本与工具链被绑定。js + d.ts 是标准答案：消费者运行 js、获得类型、无需编译你的代码——contract 与 implementation 各自独立分发。

**tsc 自产的 .d.ts 为什么天然可信，社区的会有漂移风险？**

tsc 产出 .js 和 .d.ts 是同一次编译的两个产物——同一类型内核保证两者一致。而社区手写或维护的 @types 是「对着 JS 实现猜合同」：实现升级了合同没跟上，漂移就发生了。这不是能力问题，是「两份产物是否出自同一双手」的问题。

**「信任不验证」的模型有什么安全阀？**

四道阀：发布侧用 tsc 产出声明保证自洽；消费侧 skipLibCheck 关掉对合同的审计换性能（同时加深信任）；测试兜运行时的底——类型对了运行时照样可能炸，集成测试不可省；strict 系检查把「你自己的代码符合合同」盯死。信任模型不完美，但每一段都有明确的工程实践在补偿。更前沿的补法是运行时校验（zod 一类 schema 库）：类型与运行时各有一份描述、互相印证——本质上是在合同和实现之间补一层运行时的审计。

### 记忆点

- **.d.ts 是合同不是实现**——只描述「有什么」，零运行时代码——OpenAPI 之于 REST，proto 之于 RPC，声明之于 JS。
- **信任，不验证**——文件级名字相邻配对，内容级从不核对——「类型全绿但运行时炸」的根因都在这条性质里。
