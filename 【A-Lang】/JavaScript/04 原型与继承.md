# 原型与继承

## 面向对象编程

### 面向对象的三大特性

#### 1. 封装性

将数据和操作数据的方法封装在一起，隐藏内部实现细节，只暴露必要的接口。

```javascript
// 封装示例
function Person(name, age) {
  // 私有变量
  let _age = age;

  // 公共属性
  this.name = name;

  // 公共方法
  this.getName = function() {
    return this.name;
  };

  // 访问私有变量的方法
  this.getAge = function() {
    return _age;
  };

  this.setAge = function(newAge) {
    if (newAge > 0 && newAge < 150) {
      _age = newAge;
    }
  };
}

const person = new Person('Alice', 25);
console.log(person.name); // 'Alice'
console.log(person._age); // undefined (私有变量无法直接访问)
console.log(person.getAge()); // 25
```

#### 2. 继承性

子类可以继承父类的属性和方法，实现代码复用。

```javascript
// 继承示例
function Animal(name) {
  this.name = name;
}

Animal.prototype.eat = function() {
  console.log(`${this.name} is eating`);
};

function Dog(name, breed) {
  Animal.call(this, name); // 继承属性
  this.breed = breed;
}

// 继承方法
Dog.prototype = Object.create(Animal.prototype);
Dog.prototype.constructor = Dog;

Dog.prototype.bark = function() {
  console.log(`${this.name} is barking`);
};

const dog = new Dog('Buddy', 'Golden Retriever');
dog.eat(); // 'Buddy is eating' (继承自 Animal)
dog.bark(); // 'Buddy is barking'
```

#### 3. 多态性

同一个方法在不同对象中有不同的实现，允许不同类的对象对同一消息做出响应。

```javascript
// 多态示例
function Animal(name) {
  this.name = name;
}

Animal.prototype.makeSound = function() {
  console.log('Some sound');
};

function Dog(name) {
  Animal.call(this, name);
}

Dog.prototype = Object.create(Animal.prototype);
Dog.prototype.makeSound = function() {
  console.log(`${this.name}: Woof!`);
};

function Cat(name) {
  Animal.call(this, name);
}

Cat.prototype = Object.create(Animal.prototype);
Cat.prototype.makeSound = function() {
  console.log(`${this.name}: Meow!`);
};

// 多态体现
const animals = [
  new Dog('Buddy'),
  new Cat('Whiskers'),
  new Animal('Generic')
];

animals.forEach(animal => animal.makeSound());
// Buddy: Woof!
// Whiskers: Meow!
// Some sound
```

### 面向对象编程的优势

- 灵活性：通过继承和多态实现代码的灵活扩展
- 可复用性：通过继承避免重复代码
- 易维护：封装使得代码结构清晰，便于维护
- 适合大型项目：更适合多人协作的大型软件开发

## 对象的分类

### 原生对象（Native Objects）

由 ECMAScript 规范定义的对象，独立于宿主环境。

- `Object`、`Function`、`Array`、`String`、`Boolean`、`Number`
- `Date`、`RegExp`、`Error`
- `EvalError`、`RangeError`、`ReferenceError`、`SyntaxError`、`TypeError`、`URIError`

```javascript
// 原生对象示例
const obj = new Object();
const arr = new Array();
const str = new String('hello');
const num = new Number(42);
const date = new Date();
const regex = new RegExp('\\d+');
```

### 内置对象（Built-in Objects）

由 JavaScript 引擎内部实例化的对象，开发者无需显式创建。

- `Global`（在浏览器中是 `window`）
- `Math`
- `JSON`
- `Reflect`
- `Proxy`

```javascript
// 内置对象示例
console.log(Math.PI); // 3.141592653589793
console.log(Math.max(1, 2, 3)); // 3

const obj = { name: 'Alice' };
console.log(JSON.stringify(obj)); // '{"name":"Alice"}'
```

### 宿主对象（Host Objects）

由宿主环境（如浏览器、Node.js）提供的对象。

浏览器环境：

- BOM（Browser Object Model）：`window`、`navigator`、`location`、`history`、`screen`
- DOM（Document Object Model）：`document`、`Element`、`Node`

```javascript
// 宿主对象示例（浏览器环境）
console.log(window.innerWidth);
console.log(navigator.userAgent);
console.log(document.title);

const div = document.createElement('div');
```

## 原型基础

### 属性是怎么被继承的：原型链查找

*难度：高级 ｜ 标签：原型链、继承、class*

**核心结论**：JS 没有「类复制式」继承，只有对象到对象的链接。读属性时自身没有，就沿 `[[Prototype]]` 内部槽一路向上，直到 `null` 为止；写入则永远落在自身（遮蔽或新建，原型不动）。方法和原型放一份、所有实例共享——既省内存，也让「给已存在的实例补方法」成为可能。class 只是这套机制之上的语法糖。`constructor` 是惯例不是不变量：整体替换 `prototype` 后必须手动补上。

> **前置：** 变量查找沿作用域链、属性查找沿原型链——两条「逐级向上」的链是本节的分析框架。

**双槽辨析：[[Prototype]]、prototype 与 __proto__**

原型体系最容易混的是三个名字相似但完全不同的东西。设计动机先说清：链接的职责被分配给了两个角色——每个对象只有一个「我的原型是谁」的内部槽（`[[Prototype]]`，规范级，只能通过 `Object.getPrototypeOf`、`Object.create`、`new` 设置）；而「我 new 出来的对象该链到谁」被放在构造函数身上，成了函数特有的属性（`Fn.prototype`）。实例看链、函数带配置——一个记录关系，一个提供出厂设置。

- `[[Prototype]]`：每个对象都有的内部槽，指向它的原型；查找沿它进行。
- `.prototype`：只有函数有的属性；`new Fn()` 时新对象的 `[[Prototype]]` 被指向它。
- `__proto__`：历史遗留的 getter/setter，读它等价于读 `[[Prototype]]`；新代码用标准 API。

`new Fn()` 在引擎里最核心的一步就是把新对象的 `[[Prototype]]` 指向 `Fn.prototype`（另有以 `Fn.prototype.constructor` 为构造逻辑初始化 this、执行函数体两步）。理解「双槽分属两个对象」，下面这组实测结果全部可推导：

```javascript
const animal = { eat() { return "eating" } };
const dog = Object.create(animal);

dog.eat(); // "eating" —— 自身没有，沿原型链找到 animal
Object.getPrototypeOf(dog) === animal; // true

function Foo() {}
new Foo().__proto__ === Foo.prototype; // true（演示用，生产用 getPrototypeOf）
```

原型链的内存布局：

```text
堆（对象与原型）—— 整条原型链都长在堆上，函数也是对象

┌─────────────────────┐
│ dog（实例）           │
│   name: '旺财'       │
│   [[Prototype]] ────┼───┐
└─────────────────────┘   │
                          ▼
┌─────────────────────┐        ┌──────────────────────┐
│ Dog.prototype        │        │ Dog（构造函数）        │
│   bark: <function>   │◄──┐    │   prototype ─────────┘
│   constructor ───────┼───┘    └──────────────────────┘
│   [[Prototype]] ────┼───┐
└─────────────────────┘   │
                          ▼
┌─────────────────────┐
│ Object.prototype     │
│   toString: <function>
│   hasOwnProperty: <function>
│   [[Prototype]]: null（链到此为止）
└─────────────────────┘
```

说明：`dog.toString` 的查找：dog → Dog.prototype → Object.prototype 命中。Object.prototype 的 `[[Prototype]]` 是 null，链到此为止。constructor 不在实例身上，是沿链在 prototype 对象上找到的。

函数对象 vs 普通对象（辅助辨析）：

```javascript
// 函数对象：有 prototype 属性
function MyFunction() {}
console.log(typeof MyFunction.prototype); // 'object'
console.log(MyFunction.__proto__ === Function.prototype); // true

// 普通对象：没有 prototype 属性
const obj = {};
console.log(obj.prototype); // undefined
console.log(obj.__proto__ === Object.prototype); // true

// 特殊情况：箭头函数没有 prototype
const arrowFunc = () => {};
console.log(arrowFunc.prototype); // undefined
```

原型的动态性（辅助辨析）：查找发生在每次属性访问时，不是 `new` 的那一刻。运行时往 `Fn.prototype` 上加方法，已创建的实例立即可用——polyfill 与调试探针靠的都是这个时点。但重写整个 prototype 会断开已有实例的连接：

```javascript
function Person(name) {
  this.name = name;
}

const alice = new Person('Alice');

Person.prototype.sayHello = function() {
  console.log(`Hello, I'm ${this.name}`);
};
alice.sayHello(); // "Hello, I'm Alice" —— 增量扩展，已有实例立即可用

// 但是整体重写 prototype 换了新对象：
Person.prototype = {
  sayGoodbye: function() {
    console.log('Goodbye');
  }
};

const bob = new Person('Bob');
bob.sayGoodbye(); // 'Goodbye' (新实例可以访问)
alice.sayGoodbye(); // TypeError (旧实例的 [[Prototype]] 仍指向旧对象)
```

**属性查找算法：一步不少**

读取 `obj.prop` 的完整算法：先在 obj 自身做属性查找（规范里的 `OrdinaryGetOwnProperty`）；命中直接返回——数据属性给值，访问器属性调用 getter；未命中则取 `obj.[[Prototype]]`，在原型对象上重复同样的过程，如此逐级向上。终止条件只有两个：某一级命中，或走到 `null`（链的尽头，`Object.prototype.[[Prototype]] === null`）。整条链都未命中时，读取得 `undefined`、严格模式的写入抛 `TypeError`——这和变量查找的 `ReferenceError` 是两套报错逻辑。

两个容易漏掉的细节：一是访问器属性中途命中就直接调用，不再向上——原型链上更远的同名 getter 没有机会执行；二是写入永远落在自身：`obj.prop = x` 若自身与原型链都没有该数据属性，就在 obj 自身新建（遮蔽原型上的同名属性），原型不受影响。「读沿链、写落自身」的不对称，正是「方法放原型、状态放实例」这套惯例能成立的底层保证。

`dog.toString()` 的查找过程：

```text
第 1 步  自身：dog
         OrdinaryGetOwnProperty(dog, 'toString') 未命中
         —— dog 自身只有 name。取 [[Prototype]] 进入下一级。

第 2 步  第一环：Dog.prototype
         有 bark 和 constructor，没有 toString——未命中，
         继续沿 [[Prototype]] 向上。

第 3 步  第二环：Object.prototype
         命中 toString——数据属性直接返回函数值；
         若是 getter 此刻被调用，查找终止。

第 4 步  反着写一次：dog.toString = fn
         写入不走这条链：在 dog 自身创建遮蔽属性，
         此后实例读 toString 命中自身，原型上的函数不再可达。
```

原型链查找与终点验证（辅助代码）：

```javascript
function Person(name) {
  this.name = name;
}

Person.prototype.species = 'Human';

const alice = new Person('Alice');

// 属性查找过程
console.log(alice.name);      // 'Alice' - 在实例自身找到
console.log(alice.species);   // 'Human' - 在原型上找到
console.log(alice.toString()); // '[object Object]' - 在 Object.prototype 上找到
console.log(alice.notExist);  // undefined - 原型链上都没有

// 原型链的终点
console.log(Object.prototype.__proto__); // null

// 完整链条验证
console.log(alice.__proto__ === Person.prototype);            // true
console.log(Person.prototype.__proto__ === Object.prototype); // true
console.log(Object.prototype.__proto__ === null);             // true
console.log(Person.__proto__ === Function.prototype);         // true
console.log(Function.prototype.__proto__ === Object.prototype); // true
```

**为什么方法放原型上：内存与动态性**

先算内存账：方法挂在 `Fn.prototype` 上，一万个实例共享一份函数对象；若在构造器里 `this.bark = function () {...}`，一万个实例就有一万份函数对象——函数对象不小（闭包上下文、代码引用、隐藏类），实例量大的场景是实打实的内存差。原型方法的另一个红利是每实例行为一致：方法永远来自同一个对象，改一处全体生效，不存在「这批实例的方法是旧版」的分裂。

再说动态性：查找发生在每次属性访问时，不是 `new` 的那一刻。这意味着运行时往 `Fn.prototype` 上加方法，已经存在的实例立即可用——polyfill 给 `Array.prototype` 补方法、调试期给原型挂探针，靠的都是这个时点。但同一机制反过来就是坑：`prototype` 上放引用类型字段（如 `Fn.prototype.tags = []`），所有实例共享同一个数组，一处 `push` 全体可见——所以惯例是方法放原型、可变状态放实例（在构造器里赋值）。

**constructor 陷阱**

`constructor` 是惯例，不是被引擎维护的不变量。默认情况下 `Dog.prototype.constructor === Dog`——这个属性只是函数声明时顺手挂在原型对象上的一个普通属性。一旦整体替换 `Dog.prototype`（形如 `= { ... }` 的字面量），新对象身上没有 `constructor`，实例沿链查找就会越过它一路找到 `Object.prototype.constructor`，得到 `Object`——链条断了（下例 Node v22 实测）。而 `instanceof` 不受影响，因为它走 `[[Prototype]]` 链根本不查 `constructor`——两套判断机制独立，别用一个推断另一个。

```javascript
function Foo() {}
Foo.prototype = { say() {} };   // 整体替换原型对象

const f = new Foo();
f.constructor;                 // [Function: Object] —— constructor 链断了
f.constructor === Object;      // true —— 沿原型链一路找到 Object.prototype

// 正确姿势：替换前保留，或替换时补上
Foo.prototype = { constructor: Foo, say() {} };
```

输出解读：

```text
[Function: Object]
  f 自身没有 constructor，沿链查找：Foo.prototype（被整体替换后的新对象）
  没有 → Object.prototype 命中——拿到的是 Object 的构造函数。
true
  同一条查找链的结果：f.constructor === Object 是真值比较，
  印证「constructor 只是 prototype 对象上的普通属性」——原型一换，链条跟着换。
```

断链的实际影响面：依赖 `obj.constructor` 的代码（通用克隆/工厂、按类型分发的序列化重建、部分调试器的类型显示）会拿到错误的构造函数。修复惯例也简单：替换前保留原原型再扩展，或替换时在字面量里补回 `constructor: Fn`；更彻底的做法是干脆不整体替换，用 `Object.setPrototypeOf` 或 `Object.create(Fn.prototype)` 组织继承（后者同样记得补 constructor）。

```javascript
// 错误：整体替换，字面量里没有 constructor
function Foo() {}
Foo.prototype = { say() {} };

const f = new Foo();
f.constructor === Object; // true
// 依赖 constructor 的克隆/工厂
// 全部拿到错误类型
```

```javascript
// 正确：字面量替换必须补 constructor；能增量扩展就不整体替换
function Foo() {}
Foo.prototype = {
  constructor: Foo, // 补回指向
  say() {},
};

// 或不整体替换，增量扩展：
Foo.prototype.say = function () {};
// constructor 原封不动
```

`instanceof` 不受影响不代表没人读 constructor。

**原型链的应用（辅助）**

```javascript
function Person() {}
const person = new Person();

// instanceof 检查原型链
console.log(person instanceof Person); // true
console.log(person instanceof Object); // true

// isPrototypeOf 检查原型关系
console.log(Person.prototype.isPrototypeOf(person)); // true
console.log(Object.prototype.isPrototypeOf(person)); // true

// 获取和设置原型
const obj = { a: 1 };
console.log(Object.getPrototypeOf(obj) === Object.prototype); // true

const proto = { b: 2 };
Object.setPrototypeOf(obj, proto);
console.log(obj.b); // 2

// 创建指定原型的对象
const newObj = Object.create(proto);
console.log(newObj.b); // 2

// 属性位置判断
function Dog() { this.name = 'Buddy'; }
Dog.prototype.eat = function() {};
const dog = new Dog();
console.log(dog.hasOwnProperty('name')); // true  - 自身属性
console.log(dog.hasOwnProperty('eat'));  // false - 原型上的
console.log('name' in dog); // true
console.log('toString' in dog); // true - 原型链深处也算
```

原型链越长，属性查找的性能越差——超热路径上注意链深。

**边界陷阱**

原型链的坑有共同模式：共享的东西被当成私有，私有的东西被当成公共。前者是原型上的引用类型字段被所有实例共享；后者是往内置对象的原型上加方法——`Array.prototype.first = ...` 看似方便，实则污染所有数组、可能被 `for...in` 枚举到、与 polyfill/第三方库冲突，多次加载还会重复覆盖。另一个高频坑是 `__proto__`：它是 setter 而非真实属性，写入开销大且非标准；另外「跨 iframe/worker 的对象原型不共享」会让 `instanceof` 静默失效（见追问链第 2 问）。

原型引用字段这个坑值得单独点名，因为它最像「能跑的正常代码」：在 `Fn.prototype` 上放 `tags: []` 这类可变对象，每个实例读 `this.tags` 都沿链命中同一个数组——某个实例 `push` 一条，所有实例的 `tags` 都变了，而且序列化、比较、React 的引用比较会一起出诡异现象。判断标准一句话：原型上只放不可变共享物（方法、常量），每实例一份的可变状态一律在构造器里初始化。

扩展内置原型：

```javascript
// 错误：内置原型是全局公共命名空间，一处污染全站买单
Array.prototype.first = function () {
  return this[0];
};

[1, 2, 3].first(); // 1
// 代价：所有数组被改、for...in 多出键、
// 与其他 polyfill 冲突、升级 JS 后
// 与原生方法同名时行为分裂
```

```javascript
// 正确：收进自己的命名空间，不动内置原型
// 方案一：工具函数
const first = (arr) => arr[0];

// 方案二：子类或静态方法
class MyArray extends Array {
  first() { return this[0]; }
}
```

**经典追问链**

**Q1：class 的方法在实例上还是原型上？**

*考察点：确认你把 class 还原成原型机制——答「实例上」的人还没穿过语法糖这层皮。*

在原型上。class 声明的方法等同于挂在 `Foo.prototype`；只有实例字段（constructor 里的 `this.x = ...` 与类字段语法）落在实例自身。所以方法全类一份、字段每实例一份——class 的内存模型与「方法放原型、状态放实例」的惯例完全一致，它就是这套惯例的语法化。

延伸：静态方法（static）挂在构造函数自身（`Foo.staticFn`），不进原型也不随实例可达；私有 `#` 字段存在实例内部槽上，既不在原型也无法从外部访问——三种存放位置值得画成一张表记牢。

**Q2：instanceof 的原理？能被绕过吗？**

*考察点：「双机制」意识：instanceof 与 constructor 是两条独立链——混为一谈的人说不出跨 iframe 失效的原因。*

沿右侧函数的 prototype 在左侧对象的原型链上逐级查找，命中即 true——本质是链的成员资格判断。可以绕过：`Symbol.hasInstance` 允许自定义判断逻辑；跨 iframe/worker 场景原型不共享（两个 realm 各有一套 Array.prototype），instanceof 会静默失效，此时用 `Array.isArray`（查内部槽）代替。

延伸：`Object.prototype.toString.call(x)` 也跨 realm 可靠——它读内部槽标签（`[object Array]`）而非原型；三种判断的可靠度排序：内部槽 > 原型链（instanceof）> constructor 属性。

**Q3：extends 之后 super 是什么？**

*考察点：super 的派发机制——答「super 就是父类原型」在方法被混入/借用时会立刻露馅。*

super 不是指向父类原型的固定引用。`super.method` 绑定当前 this、但方法从 `[[HomeObject]]`（方法定义时记录的所属对象）的原型上取——本质是 HomeObject 元信息驱动的动态派发。这就是为什么方法被 `obj.method()` 调用时 this 是 obj，而方法体里的 super 仍按「定义位置」向上找：this 管接收者，super 管查找起点。

延伸：对象字面量里想用 super，方法必须是 shorthand 写法（`method() {}`）——`[[HomeObject]]` 只挂在方法上，普通属性函数没有它，写 super 直接语法错误。

**Q4：Object.create(null) 有什么用？**

*考察点：「无原型对象」的工程价值——知道字典用法是及格，说得出原型污染防御是加分。*

创建没有原型的「纯净对象」：没有 toString/hasOwnProperty 等继承成员，做字典/映射时不会被任意键名干扰（比如读 key 为 `'__proto__'` 或 `'toString'` 的值）。代价是连基础方法都没有——只能用 `Object.keys`、`Reflect.has` 这类静态方法操作它。

延伸：安全视角：`JSON.parse` 返回的对象原型是 Object.prototype，攻击者可通过 `'__proto__'` 键做原型污染；以 `Object.create(null)` 的字典承接外部输入、或解析后深拷贝到无原型对象，是常见的防御姿势。

**Q5：给实例写属性时引擎做什么？会写到原型上吗？**

*考察点：「读沿链、写落自身」这条不对称的规范细节——它支撑着整个「方法在原型、状态在实例」的工程惯例。*

不会写到原型上。OrdinarySet 的逻辑：自身有该数据属性就改自身；没有则沿原型链找 setter，找到就调用；都没有则在（非严格模式下）自身新建一个属性——这个新建就是对原型的「遮蔽」。此后实例读该属性命中自身，原型上的同名属性对它不再可见，但其他实例不受影响。

延伸：两个边界：严格模式下，原型存在同名只读属性时写入抛 TypeError（非严格静默失败）；对原始值（数字/字符串）的属性写入则完全静默丢弃——临时包装对象随即被扔掉，连遮蔽都不会发生。

### 原型的三个关键概念（速查）

- `prototype`：每个函数都有；是一个对象，包含可由该构造函数所有实例共享的属性和方法。
- `__proto__`：每个对象都有；指向创建该对象的构造函数的 `prototype`，是原型链的关键。推荐用 `Object.getPrototypeOf()` 代替。
- `constructor`：原型对象的构造函数引用；实例通过原型链访问它。

```javascript
function Animal(name) {
  this.name = name;
}
Animal.prototype.eat = function() {
  console.log(`${this.name} is eating`);
};

const animal = new Animal('Dog');

console.log(typeof Animal.prototype); // 'object'
console.log(Animal.prototype.constructor === Animal); // true
console.log(animal.__proto__ === Animal.prototype); // true
console.log(Object.getPrototypeOf(animal) === Animal.prototype); // true
console.log(animal.constructor === Animal); // true —— 沿原型链找到

// 可以通过 constructor 创建新实例
const anotherAnimal = new animal.constructor('Cat');
console.log(anotherAnimal.name); // 'Cat'
```

## 继承

### class 是语法糖吗：从原型链到 class

*难度：进阶 ｜ 标签：继承、原型链、class、面试*

**核心结论**：继承方案的演进是一部修补史：原型链继承（引用类型属性被所有实例共享）→ 借用构造函数（修了共享，丢了原型方法）→ 组合继承（两者结合，但父构造执行两次）→ 寄生组合式（用 Object.create 造中间原型——正解，也就是 `class extends` 的引擎层等价物）。理解一切的前提是 new 的四步语义：创建对象 → 挂原型链 → 以新对象为 this 执行 → 按返回值类型决定结果。

> **前置：** new 四步里的「挂原型链」与 [[Prototype]]/prototype/__proto__ 三者关系，是本节一切方案的地基。

**new 的四步语义：一切继承的地基**

`new Ctor(args)` 在引擎里做四件事：创建空对象；把它的 `__proto__` 指向 `Ctor.prototype`（挂原型链，instanceof 由此生效）；以该对象为 this 执行构造函数（this 绑定的 new 规则来源）；检查返回值——构造函数 return 一个引用类型则用它替换结果，return 原始值则忽略、仍用第一步的对象。

四步解释了两个高频怪象：为什么给构造函数 return 一个对象能「劫持」new 的结果（第四步），以及为什么实例能访问原型方法而不会共享 this 上的引用属性——属性写进 this（第三步，每实例一份），方法挂在 prototype（第二步，全体共享）。「属性进 this、方法进 prototype」正是后面所有继承方案反复权衡的分界线。

**方案演进：一部修补史**

每种方案都是为了修上一个方案的洞：原型链继承（`Child.prototype = new Parent()`）让实例共享父构造的 this 属性——引用类型一改全改；借用构造函数（`Parent.call(this)`）把属性搬回各实例，但方法只能定义在构造函数里，prototype 上的方法完全够不着；组合继承把两者叠加，功能齐了，代价是 `Child.prototype = new Parent()` 这一步让父构造执行了两次，原型上还留着一层多余的实例属性。

寄生组合式是终点：原型这一侧不再用「new Parent()」，改用 `Object.create(Parent.prototype)` 造一个干净的中间原型——不调用父构造、不带多余属性；实例这一侧照旧 `Parent.call(this)`。父构造只执行一次，属性各享、方法共享。class extends 在引擎层做的正是这件事，外加静态属性链——所以面试说「class 是语法糖」，指的就是它等价于寄生组合式的自动化版本。

方案演进脉络：

```text
原型链继承        借用构造函数       组合继承           寄生组合式
（引用类型共享） → （够不着原型方法） → （父构造执行两次） → （正解 = class 内核）
```

**引用共享问题**

```javascript
// 错误：原型链继承，hobbies 挂在共享的原型对象上
function Parent() {
  this.hobbies = [];      // this 上的引用类型
}
function Child() {}
Child.prototype = new Parent(); // 原型链继承

const a = new Child(), b = new Child();
a.hobbies.push("swim");
b.hobbies // ["swim"] ← 一改全改
```

```javascript
// 正确：寄生组合，属性走 Parent.call 各自创建，方法走中间原型共享
function Child() {
  Parent.call(this);  // 属性进各实例
}
Child.prototype = Object.create(Parent.prototype);
Child.prototype.constructor = Child;

const a = new Child(), b = new Child();
a.hobbies.push("swim");
b.hobbies // [] ← 互不影响
```

**父构造执行两次问题**

```javascript
// 错误：组合继承让父构造跑两遍
function Child(name, age) {
  Parent.call(this, name);      // 第 2 次执行
}
Child.prototype = new Parent(); // 第 1 次执行
// 原型上躺着多余的 name/hobbies
// （实测 Node 22.17：Object.keys(Child.prototype)
//   → ['name', 'hobbies', 'constructor']）
```

```javascript
// 正确：寄生组合消掉了第一次执行
Child.prototype =
  Object.create(Parent.prototype); // 不调用 Parent
Child.prototype.constructor = Child;
// 中间原型是空壳，父构造只在实例化时执行一次
```

**寄生组合式继承完整实现**

```javascript
function Parent(name) {
  this.name = name;
  this.hobbies = []; // 引用类型，必须在实例上创建
}
Parent.prototype.say = function () {
  return `I am ${this.name}`;
};

function Child(name, age) {
  Parent.call(this, name); // 借用构造函数：实例属性各自独立
  this.age = age;
}

// 寄生式：中间原型继承 Parent.prototype，但不调用 Parent
Child.prototype = Object.create(Parent.prototype);
Child.prototype.constructor = Child; // 修复 constructor 指回

const c = new Child("ada", 3);
c.say(); // 原型方法可用；hobbies 修改不影响其他实例
```

**constructor 修复**

```javascript
// 错误：少了修复行
Child.prototype =
  Object.create(Parent.prototype);

const c = new Child("ada");
c.constructor // Parent —— 沿原型链找到父类
// （实测 Node 22.17：c.constructor === Parent 为 true）
// 靠 constructor 做类型判断或 new c.constructor() 复制实例的代码会翻车
```

```javascript
// 正确：替换后指回，或直接用 class（语法糖自动维护 constructor）
Child.prototype =
  Object.create(Parent.prototype);
Child.prototype.constructor = Child; // 指回
```

**方法写在实例上的代价**

```javascript
// 错误：每个实例一份新函数
function Child(name) {
  Parent.call(this, name);
  this.say = function () {   // 每个实例
    return `I am ${this.name}`; // 一份新函数
  };
}
// 1000 个实例 = 1000 个函数对象，内存与创建成本双高
```

```javascript
// 正确：全体实例共享同一份
Child.prototype.say = function () {
  return `I am ${this.name}`;
};

class Child { say() {} } // class 默认挂原型
```

「属性进 this、方法进 prototype」不只是约定，也是性能决策。

> **记忆点：一句选型。** 手写场景直接背结论：`Object.create(Parent.prototype) + Parent.call(this) + 修复 constructor`——这是面试要求的「寄生组合式」，也是 class extends 的行为内核。写 class 的时代它仍是理解 super、静态继承与混入的底层模型。

**六种继承方式对比总结（保留速查）**

| 继承方式 | 优点 | 缺点 | 推荐度 |
|---------|------|------|--------|
| 原型链继承 | 简单易实现 | 引用类型共享、无法传参 | 极少用 |
| 构造函数继承 | 避免引用共享、可传参 | 无法继承原型方法 | 少用 |
| 组合继承 | 结合两者优点 | 调用两次父类构造函数 | 可用 |
| 原型式继承（Object.create） | 简单，不需要构造函数 | 引用类型共享 | 特定场景 |
| 寄生式继承 | 可在继承基础上增强对象 | 方法重复创建 | 特定场景 |
| 寄生组合式继承 | 完美解决所有问题 | 实现稍复杂 | 最佳 |

**class 是语法糖：等价与不等价**

`class A extends B` 在引擎层做了两条原型链：实例链（`A.prototype` 的 `__proto__` 指向 `B.prototype`——实例方法沿它查找）和静态链（`A` 自身的 `__proto__` 指向 `B`——静态方法因此可继承）。寄生组合式只覆盖了实例链，静态链是 class 的加赠。`super` 就是沿着这两条链向上找方法并把 this 绑向当前对象。

也有不等价的部分，面试常当辨析题：class 声明不会提升（有暂时性死区）、类体内部强制严格模式、方法默认不可枚举（构造函数手挂的方法是可枚举的）、class 必须用 new 调用（直接调用抛 TypeError）。这些差异让 class 不只是「好看的原型」，而是带约束的正式类型语义——理解了底层模型，这些约束就都成了可推导的结论而不是死记项。

**经典追问链**

**Q1：new 一个构造函数时，构造函数里 return 一个对象会发生什么？return 原始值呢？**

*考察点：new 四步语义的收尾规则——背过「创建对象挂原型」只是及格线，return 覆盖规则才是分水岭。*

new 的返回值由第四步决定：构造函数返回引用类型（对象/函数）时，用它替换第一步创建的实例——原型链、instanceof 全部跟着变；返回原始值则被忽略，正常返回 this。因此「单例缓存实例」「返回代理包装」这类模式都借道这一步实现。手写 new 的核心就是把四步 + 这个判断写全。

延伸：箭头函数不能 new 的根源在第一步之前：它没有 `[[Construct]]` 内部方法，引擎直接抛 TypeError——与「没有 prototype」是因果两件事。

**Q2：组合继承为什么说父构造执行了两次？多出来的那层是什么？**

*考察点：对中间产物的洞察——能指出「原型上多了一层无用的实例属性」才算真看懂了组合继承。*

组合继承 = 原型链 + 借用构造：`Child.prototype = new Parent()` 执行第一次（属性挂到了原型上，纯浪费）；实例化 Child 时 `Parent.call(this)` 又执行第二次（属性再挂到实例上，遮蔽原型同名属性）。副作用是原型对象上躺着一层永远用不到的 name/hobbies——它们只被实例属性遮蔽。寄生组合用 `Object.create(Parent.prototype)` 造空原型，第一次执行被彻底消掉。

延伸：遮蔽（shadowing）机制顺手解释了另一个现象：实例属性永远优先于原型属性——这也是「属性进 this、方法进 prototype」约定能和平共处的原因。

**Q3：Child.prototype.constructor = Child 这行不写会怎样？**

*考察点：constructor 的真实角色——多数人背了「要修复」，说不出不修的后果就是背的。*

替换整个 prototype 对象后，新对象上没有 constructor，沿原型链向上会找到 `Parent.prototype.constructor`——也就是 Parent。后果：`obj.constructor` 语义错误，靠它做类型判断或 `new obj.constructor()` 复制实例的代码会翻车；序列化/调试信息里类名错乱。语言运行本身不依赖 constructor（它只是 prototype 上的一个普通属性），所以不写也不报错——这正是它总被忘掉的原因。

延伸：更稳的替代：别整体替换 prototype，用 `Object.defineProperty` 往现有 prototype 上加方法，constructor 自然保留；或直接用 class——语法糖替你维护好了这条链。

**Q4：class A extends B 在引擎层建了几条原型链？super 是怎么找到方法的？**

*考察点：压轴题，考「双链」模型——只答得出实例链说明对静态继承与 super 没有完整认识。*

两条。实例链：`A.prototype.__proto__ === B.prototype`——实例方法沿它向上查找；静态链：`A.__proto__ === B`——静态方法与静态属性因此可被继承（`A.staticFn()` 找不到时沿静态链到 B）。super 的本质是沿对应链向上取值：实例方法里 `super.fn()` 从 B.prototype 取 fn 并以当前 this 调用；构造器里 `super()` 调 B 的构造函数并把 this（new.target 侧）传给它——所以 `super()` 之前不能碰 this 是规范级的顺序约束。

延伸：推论题：寄生组合式没有静态链——用 class 的项目里手写「继承静态方法」的老代码其实是无效操作，static 成员必须靠 extends 或显式 `Object.setPrototypeOf`。

**Q5：class 和构造函数写法还有哪些行为差异？为什么说它不只是语法糖？**

*考察点：收尾辨析题，考工程判断——列出不可枚举/强制严格模式/不提升三件套，说明你真的两边都写过。*

四个行为差异：class 声明不提升（暂时性死区，定义前访问直接 ReferenceError）；类体强制严格模式；类的方法默认不可枚举（构造函数手挂方法是可枚举的，影响 for...in 与浅拷贝展开）；class 只能 new、不能当普通函数调用。这些约束让 class 的行为更可预测——「语法糖」说的是原型模型等价，「不只是」说的是这层语义收紧。

延伸：工程影响最实际的是不可枚举：`Object.keys` 与 `{...instance}` 不会把方法拷出去——这也让 class 实例更容易安全地做 structuredClone 之外的数据提取。

延伸阅读：属性是怎么被继承的：原型链查找（本章前文）、手写 bind 时，new 为什么能「打败」它（见设计模式篇，new 四步第③步与显式绑定的优先级之争）。

```javascript
Object.setPrototypeOf(obj, proto); // 设置原型

// 属性描述符
Object.defineProperty(obj, 'c', { value: 3, writable: false });
Object.getOwnPropertyDescriptor(obj, 'a');

// 对象状态
Object.freeze(obj); // 冻结对象（不可修改、添加、删除）
Object.seal(obj); // 密封对象（不可添加、删除，可修改）
Object.preventExtensions(obj); // 阻止扩展（不可添加）

// 检查对象状态
Object.isFrozen(obj);
Object.isSealed(obj);
Object.isExtensible(obj);
```

## 总结与最佳实践

### 关键要点

1. **原型机制**：JS 只有对象到对象的链接；`[[Prototype]]`、`prototype`、`__proto__` 三者分工不同
2. **查找规则**：读沿链逐级向上、命中即停；写永远落在自身——「方法放原型、状态放实例」的底层保证
3. **constructor** 是惯例不是不变量，整体替换 prototype 后必须手动补上
4. **继承演进**：寄生组合式（`Object.create(Parent.prototype) + Parent.call(this)`）是手写正解，class extends 是它的自动化版本 + 静态链
5. **ES6 Class**：方法不可枚举、强制严格模式、不提升、必须 new——不只是语法糖

### 最佳实践

1. **优先使用 ES6 Class** 语法，代码更清晰，constructor 与原型链由引擎维护
2. **理解寄生组合式继承**：它仍是理解 super、静态继承与混入的底层模型
3. **避免直接修改 `__proto__`**，使用 `Object.getPrototypeOf()` 和 `Object.setPrototypeOf()`
4. **使用 `hasOwnProperty()`** 检查自有属性
5. **原型上只放方法与常量**，每实例一份的可变状态在构造器里初始化
6. **不要扩展内置原型**：工具函数或子类是更安全的命名空间
7. **注意原型链长度**对超热路径属性查找的影响

### 常见陷阱

1. 忘记在子类构造函数中调用 `super()`
2. 重写原型后忘记修正 `constructor`
3. 原型上的引用类型属性被所有实例共享
4. 混淆 `prototype` 和 `__proto__`
5. 在箭头函数中使用 `this`（箭头函数没有自己的 `this`）
6. 过长的原型链导致性能问题
