# HTTPS 握手过程

*类型：knowledge ｜ 难度：入门 ｜ 标签：HTTPS、TLS、握手、会话密钥*

**TLS 握手的目标是双方独立算出同一个会话密钥：客户端发协议版本、随机数和支持的加密方法；服务器回证书、确认的加密方法和自己的随机数；客户端验证证书后生成第三个随机数，用证书公钥加密发出；双方用三个随机数生成会话密钥，之后的通信全部对称加密。前四步用非对称加密保安全，最后一步用对称加密保效率。**

## 握手五步

1. 客户端发送：协议版本号、随机数、支持的加密方法
2. 服务器返回：确认加密方法、服务器证书、服务器随机数
3. 客户端验证证书有效性，生成新随机数，用证书公钥加密后发送；同时发送前面所有内容的 Hash 供服务器校验
4. 服务器用私钥解密随机数，发送前面所有内容的 Hash 供客户端校验
5. 双方用三个随机数生成会话密钥，后续通信均使用该密钥对称加密

```text
客户端                                   服务器
  │ ① 协议版本 + 随机数1 + 支持的加密方法 │
  │ ───────────────────────────────────▶ │
  │ ② 证书（含公钥）+ 加密方法 + 随机数2  │
  │ ◀─────────────────────────────────── │
  │ ③ 验证证书 → 随机数3（公钥加密）      │
  │    + 前面内容的 Hash                  │
  │ ────────────────────────────────────▶ │
  │ ④ 前面内容的 Hash（私钥解随机数3 后）  │
  │ ◀──────────────────────────────────── │
  │ ⑤ 双方用 随机数1+2+3 生成会话密钥      │
  │ ◀═══════════ 对称加密通信 ═══════════▶ │
```

## 关键点

- **三个随机数缺一不可**：其中两个明文传输（可被窃听），但第三个用证书公钥加密，只有持私钥的服务器能解——窃听者凑不齐生成会话密钥的材料
- **Hash 校验贯穿全程**：③④ 两步各自携带「前面所有内容的 Hash」，防止握手消息在中途被篡改
- **非对称只用在刀刃上**：仅用于传输随机数 3 与身份认证，大量数据传输交给对称加密，兼顾安全与性能
