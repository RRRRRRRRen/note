# 四次挥手

*类型：knowledge ｜ 难度：入门 ｜ 标签：TCP、四次挥手、TIME_WAIT*

**断开连接要四次，因为 TCP 全双工、两个方向要各自关闭：客户端发 FIN；服务器先回 ACK（此时客户端→服务器方向已关闭，但服务器还能继续发数据）；服务器把剩余数据发完再发自己的 FIN；客户端回 ACK 后进入 `TIME_WAIT` 持续 2MSL 才真正 `CLOSED`。中间两步不能合并——服务器收到 FIN 时往往还有数据没发完，ACK 和 FIN 必须分开。**

## 挥手过程

**第一次挥手**

客户端认为数据发送完成，向服务器发送连接释放请求。

**第二次挥手**

服务器收到请求后，发送 ACK 包，进入 `CLOSE_WAIT` 状态。此时客户端到服务器方向的连接已释放，但服务器仍可向客户端发送数据。

**第三次挥手**

服务器将剩余数据发送完毕后，向客户端发送连接释放请求，进入 `LAST_ACK` 状态。

**第四次挥手**

客户端收到释放请求后，发送确认应答，进入 `TIME_WAIT` 状态，持续 2MSL。若期间未收到服务器重发请求，则进入 `CLOSED` 状态。服务器收到确认后直接进入 `CLOSED` 状态。

```text
客户端                              服务器
  │ ── FIN（数据发完了）───────────▶ │  第一次挥手
  │ ◀────────────────── ACK ─────── │  第二次挥手
  │        （进入 FIN-WAIT-2）      │  （CLOSE_WAIT，仍可发数据）
  │ ◀──────────── FIN（我也发完了）─ │  第三次挥手
  │                                 │  （LAST_ACK）
  │ ── ACK ───────────────────────▶ │  第四次挥手
  │ （TIME_WAIT，持续 2MSL → CLOSED）│  （收到 ACK → CLOSED）
```

## 为什么需要四次挥手

建立连接时，服务器可以将 SYN 和 ACK 合并为一个报文发送。但关闭连接时，服务器收到 FIN 后可能还有数据未发完，只能先回复 ACK，等数据发送完毕后再单独发送 FIN，因此需要四次。

```text
握手可以合并：SYN+ACK 一份报文        挥手不能合并：ACK 与 FIN 之间
                                    服务器还有剩余数据要发
```

## TIME_WAIT 为什么等 2MSL

- **MSL**（Maximum Segment Lifetime）：报文在网络中的最大生存时间
- 确保最后一个 ACK 若丢失，服务器重发的 FIN 能在 2MSL 内到达并再次确认
- 让本连接的所有旧报文在网络中消亡，避免污染下一个相同四元组的新连接
