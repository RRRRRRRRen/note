# TCP 粘包

*类型：knowledge ｜ 难度：入门 ｜ 标签：TCP、粘包、Nagle 算法、消息边界*

**TCP 是字节流协议，本身没有「消息」边界：默认开启的 Nagle 算法会把短时间内多个小数据缓冲合并成一次发送，接收方一次 `read` 可能读到多条消息拼在一起（粘包）。传文件无所谓，传多条独立消息时必须自己划界——加等待时间、关闭 Nagle，或在应用层做封包拆包（长度前缀或分隔符）。**

## 原因

TCP 默认启用 Nagle 算法，会将短时间内的多个数据缓冲合并为一次发送，减少 IO 消耗。传输文件时无需处理，但传输多条独立消息时会导致粘包问题。

```text
发送方写出：MSG1、MSG2、MSG3

Nagle 合并后网络上实际传输：
┌──────────────────────────┐
│ MSG1 MSG2 MSG3           │  ← 一次 TCP 报文，边界信息丢失
└──────────────────────────┘
接收方一次读到：MSG1MSG2MSG3 → 无法区分消息边界
```

## 解决方案

- 多次发送之间间隔一个等待时间
- 关闭 Nagle 算法
- 进行封包拆包（在数据包中加入长度或分隔符）

```text
方案一：长度前缀（推荐）
┌─────────┬──────────────┬─────────┬──────────────┐
│ len = 5 │ hello        │ len = 3 │ abc          │
└─────────┴──────────────┴─────────┴──────────────┘
接收方先读长度字段，再按长度截取定长消息体

方案二：分隔符
┌───────────────┬───────────────┬───────────────┐
│ hello\n       │ abc\n         │ ...           │
└───────────────┴───────────────┴───────────────┘
按约定分隔符切分（需处理消息体内出现分隔符的转义问题）
```

## 方案对比

| 方案 | 思路 | 代价 |
| --- | --- | --- |
| 等待间隔 | 每条消息间 sleep，凑不成批 | 延迟增加，吞吐下降 |
| 关闭 Nagle | `TCP_NODELAY` 立即发送 | 小包增多，网络开销变大 |
| 封包拆包 | 应用层自定义消息边界 | 需约定协议格式（推荐做法） |
