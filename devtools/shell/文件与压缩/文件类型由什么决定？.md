# 文件类型由什么决定？

*类型：question ｜ 难度：入门 ｜ 标签：文件系统、魔数、MIME、编码、命令行 ｜ 更新：2026-09-10*

**文件类型由内容决定，不是名字。** 三层判定各司其职：**拓展名**是写在目录「花名册」里的标签，给人看、给图形界面用，一个 `mv` 就能改；**魔数**是内容开头几个字节的「正身暗号」，`file` 命令、`gunzip` 这类程序验的是它；**Content-Type** 是传输层的声明，浏览器信它而不信 URL 后缀。把 .gz 改名成 .txt，`gunzip -c` 照样解压出原文——验身看的是暗号，名字从头到尾没参与。

## 名字住在花名册里，内容才是那串字节

磁盘上的文件由两样互相独立的东西构成：**内容**是一串字节，**名字**是文件系统目录表里的一个条目。所谓「拓展名」只是名字里约定俗成的最后一段——它根本不存储在文件内容里。`mv a.gz a.txt` 改的只是花名册上的一行字，那串字节一个都不会动。

亲眼看一遍：`xxd` 显示 hello.txt 的字节是 `68 65 6c 6c 6f 0a`——正好是 h、e、l、l、o 加换行的编号，**第一个字节就是正文，没有任何「文件头」**。然后把它改名成 .md，再问 `file` 命令：

```bash
$ echo hello > nv-real.txt
$ file nv-real.txt
nv-real.txt: ASCII text
$ xxd nv-real.txt
00000000: 6865 6c6c 6f0a                           hello.
$ mv nv-real.txt nv-real.md      # 名字换了
$ file nv-real.md
nv-real.md: ASCII text           # 判定没变：它看的是内容
```

## 魔数：内容开头的正身暗号

结构化格式都会在内容最前面放几个固定字节，圈内叫**魔数**：gzip 是 `1f 8b`，PNG 是 `89 50 4e 47`，PDF 是 `25 50 44 46`（即 %PDF）。程序验身就是拿内容开头对照这张表——命中谁是 gzip 就是 gzip，与名字无关。把 gzip 内容套上 .txt 的名字，`file` 一眼认出原形；而 `gunzip` 直接带名字解压时拒绝它，拒绝理由也不是「类型不对」，而是**输入名里没有可砍的后缀、起不出输出文件名**——换成走标准输出的 `gunzip -c`，照样解：

```bash
$ printf 'AAA,' | gzip > nv-fake.txt       # gzip 内容，.txt 名字
$ file nv-fake.txt
nv-fake.txt: gzip compressed data, last modified: Thu Sep 10 13:55:00 2026, from Unix, truncated
$ gunzip nv-fake.txt
gunzip: nv-fake.txt: unknown suffix -- ignored    # exit 1：不是不认，是起不出名
$ gunzip -c nv-fake.txt
AAA,                                              # -c 走标准输出，照样解
```

反过来，纯文本文件**没有魔数**——从第一个字节到最后一个字节全是内容本身。所以 `file` 对文本的判定是**猜**：按内容风格判断「像不像文字」。猜就会出错：一个 GBK 编码的中文文件被它报成 `ISO-8859 text`——编码认错了，但「它只是个猜风格的家伙」这个行为本身是诚实的。魔数是写死的查表，文本是概率的猜测，这就是 `file` 输出里 gzip 那行笃定、txt 那行含糊的原因。

两种身份判定的对照（extension vs magic）：

| 维度 | 拓展名 .gz | 魔数 1f 8b |
|---|---|---|
| 存在哪里 | 目录花名册的条目里，在内容之外 | 内容的第 1~2 个字节，走到哪跟到哪 |
| 谁在消费 | 人眼、GUI 双击行为、服务端 MIME 映射表 | file 命令、gunzip、图片解码器等程序 |
| 改动成本 | mv 一下就变，零成本 | 得修改内容本体 |
| 伪造难度 | 无门槛 | 要精确构造字节序列 |
| file 的态度 | 不理会 | 查表命中即宣布结论 |

## 乱码是谁的错：cat 的字节接力

「`cat` 怎么知道要把字节变成字符？」——它不知道，也从来不做这件事。`cat` 只把字节**原样搬运**到输出通道；真正把字节翻译成字符的是**终端**：它拿着字节流逐个查 UTF-8 对照表，查到合法序列就画出字符。文本文件的字节恰好都是合法 UTF-8，所以显示正常；.gz 的字节大多是非法组合，终端硬着头皮查表，查不出来就用 `�` 占位符画上去——这就是乱码。**乱码是终端的解码失败，不是 cat 的失败**，cat 搬运字节这件事从来都成功了。

cat 显示文件的四棒接力（cat pipeline）：

```text
文件里的字节
   │  read()
   ▼
cat：原样搬运，不解释
   │  stdout，字节不变
   ▼
终端：按 UTF-8 查表
   ├─ 编码对上了 → 合法序列 → 画出字符
   └─ 编码对不上 → 非法序列 → � 占位（乱码）
```

编码不匹配的实验能同时验证「cat 不转码」和「终端只认死理」：造一个 GBK 字节的文件，`file` 猜错编码、`cat` 照搬字节、终端按 UTF-8 硬查——三连乱码；换用 `iconv` 指定「从 GBK 转 UTF-8」，同一个文件立刻还原。如果 cat 会「自动识别编码」，这一节的所有乱码都不该发生——它们发生了，恰好证明没人转码：

```bash
$ printf '你好世界' | iconv -f UTF-8 -t GBK > nv-gbk.txt
$ file nv-gbk.txt
nv-gbk.txt: ISO-8859 text, with no line terminators   # 猜错了（其实是 GBK）
$ cat nv-gbk.txt
������                     # 终端按 UTF-8 硬查的产物
$ iconv -f GBK -t UTF-8 nv-gbk.txt
你好世界                    # 用对对照表就还原
```

## Web 上的同款哲学：Content-Type

浏览器判断「服务器发来的是 HTML 还是图片」，同样不看 URL 的拓展名，而是看响应头 `Content-Type`。这和 `file` 命令看魔数是同一个原则：**别信名字，验内容或验声明**。拓展名真正「说了算」的地方其实在服务端配置层——nginx 的 `types` 表按拓展名映射出 Content-Type 响应头，再把声明发给浏览器。也就是说：拓展名决定 MIME 的路径是「服务端查表 → 生成声明 → 浏览器信声明」，浏览器从头到尾没看过你文件叫什么。

这也解释了一个安全常识的由来：Content-Type 本质是**声明**而不是验身——声明可以被伪造或配错，所以涉及内容处理的程序（图片解码器、压缩工具）最终都会落到字节层面再验一次。拓展名、Content-Type、魔数三层各有受众，谁也不能完全替代谁，但「程序验正身」的那一票永远投给内容本身。

上传校验（upload check）的正误对照：

错误做法：

```javascript
// 只看文件名后缀就放行
const ok = file.name.endsWith(".png");
```

- 拓展名是客户端可任意伪造的标签，改个名字就绕过

正确做法：

```javascript
// 服务端读文件头，比对魔数表
// 89 50 4E 47 0D 0A 1A 0A 才是 PNG
const head = await readHead(file, 8);
```

- 内容里的暗号伪造成本高，验身才有意义

遇到乱码（mojibake）的正误对照：

错误做法：

```bash
# 见乱码就反复转码碰运气
iconv -f UTF-8 -t GBK f.txt
iconv -f BIG5 -t UTF-8 f.txt ...
```

- 无对照地瞎转，只会把字节越搅越乱

正确做法：

```bash
# 先看真实字节，再定对照表
xxd f.txt | head        # c4e3 开头 → GBK 的「你」
iconv -f GBK -t UTF-8 f.txt
```

- 字节是事实，编码只是解读方式——先采集事实

记忆卡「验身看内容，别信名字」：

```text
┌────────────────────────────────────┐
│  验身看内容，别信名字               │
│  拓展名 → 花名册标签（给人看）       │
│  魔数   → 内容开头暗号（给程序验）   │
│  Content-Type → 传输层声明（给浏览器）│
└────────────────────────────────────┘
```

- 拓展名是花名册上的标签（给人看），魔数是内容开头的暗号（给程序验），Content-Type 是传输层的声明（给浏览器定）。
- 改名字动不了内容，验正身的程序就骗不到。

## 经典追问链

**cat 一个 .gz 文件满屏乱码，cat 是不是失败了？**

cat 没有失败。它的工作是把字节原样搬运到输出通道，这一步 100% 成功；乱码发生在下一环节——终端拿着这些字节查 UTF-8 对照表，查不出合法序列只能画 `�` 占位。cat 从头到尾不知道「这是 gz」，它对任何文件的动作都一模一样。

- 加分项：顺带恢复被二进制搞乱的终端显示——敲 reset 回车，控制字节被终端当指令执行后，reset 能把终端状态复位。

**file 命令认出 gzip 靠什么？它认 txt 也是同样的方法吗？**

认 gzip 是查表：内容开头命中魔数 1f 8b，直接宣布结论，笃定且可伪造性低。认 txt 没有表可查——纯文本没有文件头，file 只能按内容风格猜（输出含糊的 ASCII text）；猜就可能错，GBK 中文被它报成 ISO-8859 就是实证。结构化格式查表、纯文本靠猜，这是 file 输出语气差别的根源。

- 加分项：file 的判定库叫 magic file（/usr/share/file/misc/magic.mgc），社区持续维护魔数条目——它本质是一张可扩展的特征码对照表。

**拓展名在这个体系里什么时候真正「生效」？**

三处：人眼识别、GUI 的双击行为（Finder/资源管理器按拓展名选打开方式）、以及最重要的服务端 MIME 映射——nginx 的 types 表按拓展名查出 Content-Type 写进响应头。注意第三处拓展名也没直接面向浏览器：它先被服务端翻译成声明，浏览器信的是声明。程序级验身（解压、解码、杀毒扫描）从头到尾不看拓展名。

- 加分项：所以 nginx types 表配错（比如 .js 没映射成 text/javascript）时，文件内容完好但浏览器拒绝执行——拓展名的错误通过声明层传染。

**上传接口校验了拓展名和 Content-Type 请求头，双保险够吗？**

不够。拓展名和 Content-Type 请求头都是客户端可控的声明，攻击者把恶意脚本改名 photo.png、请求头写成 image/png，两层校验同时通过。唯一可靠的做法是服务端读取文件内容开头、比对魔数表，必要时再送到真实解码器里过一遍（解码失败即拒绝）——声明可以伪造，内容里的暗号伪造成本高得多。

- 加分项：更稳的组合拳——验魔数 + 存储时重编码/重打包（把字节彻底洗一遍）+ 存储域名与业务域名分离，让「万一漏网」也执行不了。

> **提示：把实验跑一遍** 本篇所有输出都在 macOS（Apple gzip / BSD file）实测采集。Linux 的 GNU 工具行为一致，仅输出措辞略有差异——魔数表、花名册模型、终端解码链路在所有 Unix 类系统上通用。
