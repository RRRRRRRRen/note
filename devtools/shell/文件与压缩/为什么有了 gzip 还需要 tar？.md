# 为什么有了 gzip 还需要 tar？

*类型：question ｜ 难度：入门 ｜ 标签：tar、gzip、打包、归档 ｜ 更新：2026-09-10*

因为 gzip 只会压缩**一条字节流**，而你要交付的往往是**一个目录**：tar 负责把目录树连内容带元数据（名字、权限、时间戳）装订成一条流，gzip 再把这条流压小。`.tar.gz` 就是先装订、后压缩的两层套娃，解开时倒着剥。还有一件反直觉的事：tar 自己不压缩，纯 `.tar` 打完包反而比原内容略大。

## gzip 的能力边界：它眼里只有一条流

复习一下 gzip 的世界观，它极其单纯：`1F 8B` 魔数开头，啃进一条字节流，吐出一条更小的字节流。除此之外它没有任何认识——目录、文件名、权限、修改时间，这些词在它的字典里统统不存在。多 member 拼接能看出一点点弹性（多条 gzip 流可以首尾相接），但那也只是「流和流拼接」，依然没有目录概念。

现实需求却是：「把这个项目目录发出去」——十几个文件、嵌套层级、每个文件各带自己的元数据。这对 gzip 是无从下嘴的一团。于是分工出现了：需要一个工具先把目录树**摊平成一条流**，gzip 才有得压。这个活儿就是 tar 的。

## tar：目录树的序列化

给一个前端味儿的对照：tar 之于文件系统，约等于 `JSON.stringify` 之于内存对象——都是把一棵树序列化成一条线性产物。区别只在对象：`JSON.stringify` 吃内存里的对象树、产出字符串；tar 吃文件系统的目录树、产出**一条字节流**，解包就是反序列化。名字本身是 Tape Archive 的缩写：磁带是顺序介质，只能从头读到尾，所以 tar 从出生就长成一条从头到尾的顺序流——这个出身一句话解释了它的全部性格。

关键在序列化范围：**元数据一并进流**。每个条目的名字、权限、属主、修改时间都写在流里，所以 `tar -tvf` 不解包就能列出完整清单——清单不是猜出来的，是流里本来就写着：

```bash
$ tar -tvf demo.tar                # 只列清单，不碰包里的数据
drwxr-xr-x  0 demo  staff     0 Sep 10 22:18 app/
-rw-r--r--  0 demo  staff    22 Sep 10 22:18 app/README.md
-rw-r--r--  0 demo  staff    42 Sep 10 22:18 app/package.json
drwxr-xr-x  0 demo  staff     0 Sep 10 22:18 app/src/
-rw-r--r--  0 demo  staff    25 Sep 10 22:18 app/src/index.js
```

tar 与 gzip 的分工（division of labor）：

| 维度 | tar：装订工 | gzip：压缩机 |
|---|---|---|
| 解决的问题 | 目录树 → 一条流 | 一条流 → 一条更小的流 |
| 输入 | 一棵目录树 | 一条字节流 |
| 元数据 | 记录并在解包时原样还原 | 完全不认识 |
| 压缩 | 不压缩 | DEFLATE 压缩 |
| 典型产物 | .tar（常比原内容大） | .gz |

## .tar.gz：两层套娃，顺序不能反

两件工具串起来：先 tar 装订、再 gzip 压缩。顺序不能反的原因藏在输入类型里——gzip 只吃「一条流」，而目录树还不是「一条」，必须先有 tar 这条流它才有得压。解开时倒着来：先剥 gzip 壳还原出 tar 流，再拆装订。后缀倒着读就懂：`.tar.gz` = 先 `.tar` 后 `.gz`，剥的时候反着剥。

.tar.gz 剥壳视图（onion view）：

```text
┌────────────────────────────────────────────────┐
│ gzip 压缩层（壳）                               │
│ 1F 8B 开头，整条 tar 流被 DEFLATE 压小           │
│ ┌────────────────────────────────────────────┐ │
│ │ tar 装订层（流）                            │ │
│ │ ustar 头部 + 数据块，一条从头到尾的字节流      │ │
│ │ ┌──────────────────────────────────────┐   │ │
│ │ │ 文件内容 + 元数据                     │   │ │
│ │ │ 名字、权限、属主、时间戳，解包时原样还原 │   │ │
│ │ └──────────────────────────────────────┘   │ │
│ └────────────────────────────────────────────┘ │
└────────────────────────────────────────────────┘
```

- gzip 压缩层（壳）：1F 8B 开头，整条 tar 流被 DEFLATE 压小。
- tar 装订层（流）：ustar 头部 + 数据块，一条从头到尾的字节流。
- 文件内容 + 元数据：名字、权限、属主、时间戳，解包时原样还原。

这个结构也解释了一个日常细节：图形界面解压软件打开 `.tar.gz` 常要「解两次」——先得到 `.tar`，再点一次才看到文件。因为那本来就是两种格式套在一起，不是一种格式。

打包顺序（order）的正误对照：

错误做法：

```bash
$ gzip demo/            # gzip 不认识目录，无从下手
```

- 压缩的输入必须是一条流，目录树得先经 tar 摊平

正确做法：

```bash
$ tar -czf demo.tar.gz demo/    # 先装订后压缩，-z 只是糖衣
```

- 一条命令完成两层，内部顺序依然是先 tar 后 gzip

## 眼见为实：89 字节如何变成 5120 又变回 315

造一个三个文件共 89 字节的最小目录，走完整链路：`tar -cf` 打包得到 5120 字节，gzip 后只剩 315 字节。先回答最反直觉的那件事——**打包为什么反而变大**？开销花在三处：每个条目前一张 512 字节的「元数据档案卡」、数据按固定块对齐补零、流末尾的收尾块。买 tar 买的是「目录树变成一条流」的能力，不是变小。

体积链（size chain）：

```text
原始内容（3 个文件）  ▏            89 字节
打包 .tar            ████████████  5120 字节
再压缩 .tar.gz       █             315 字节
（条形长度按比例示意）
```

- 原始内容（3 个文件）：89 字节
- 打包 .tar：5120 字节
- 再压缩 .tar.gz：315 字节

拿 `xxd` 对准这个 `.tar`，序列化现场直接可见（ustar 格式，节选关键三行）：

```bash
$ xxd app.tar
00000000: 6170 702f 0000 0000 0000 0000 0000 0000  app/............
00000060: 0000 0000 3030 3037 3535 2000 3030 3037  ....000755 .0007
00000100: 0075 7374 6172 0030 3072 656e 0000 0000  .ustar.00ren....
```

三个观察：第一行，流的最开头就是文件名 `app/` 的明文 ASCII（`61 70 70 2f`），所以不解包就能列清单；`0x60` 行，`000755`，八进制权限也是明文；`0x100` 行，偏移 257（`0x101`）处躺着 `ustar`——这就是 tar 的魔数，`file` 命令认出「POSIX tar archive」靠的就是它。

> **规范引用（IEEE Std 1003.1（POSIX）pax 工具规范 · ustar 头部）**：ustar 头部块的 magic 字段位于块内偏移 257 处，内容为 ustar\0，紧随的 version 字段为 00。

魔数藏这么深不是故弄玄虚：第一代 tar 格式根本没有魔数，后来标准化时只能在 512 字节头部的既定布局里找空位，落在了第 257 字节。对照 gzip 的 `1F 8B` 堂堂正正在第 1 字节——出生年代不同，格式习惯不同。

期待 .tar 变小（no compression）的正误对照：

错误做法：

```bash
$ tar -cf logs.tar big.log
$ ls -l        # 比原文件还大了？！
```

- tar 只装订不压缩，变大是常态（头部卡 + 补零）

正确做法：

```bash
$ tar -czf logs.tar.gz big.log   # 压缩交给外挂 gzip
```

- 要小就套压缩层；.tar 只负责「把一堆文件变成一件事」

## 对照组：zip 为什么不用两步

zip 是「打包 + 压缩」一锅炖：格式内建目录结构理解，压缩算法焊死在格式里（deflate）。tar + gzip 是分工：tar 只管装订，压缩层完全可插拔——今天 `-z` 配 gzip，明天 `-J` 配 xz，将来 `--zstd` 配 zstd，装订产物不变，换压缩机不用换装订工。这是 Unix「每个工具只做一件事」的典型取舍，代价是你得理解两层结构。

这套分工的现代身影到处都是：下载的源码包、`npm pack` 的 `.tgz`、`docker save` 导出的镜像包——里面每个镜像层还是一个 tar，套娃的第三层。认识一层，处处都是它。

记忆卡「tar 装订，gzip 压缩」：

```text
┌────────────────────────────────────────┐
│  tar 装订，gzip 压缩                    │
│  gzip 只认一条流                        │
│  tar 把目录树连元数据装订成那条流         │
│  .tar.gz = 先 tar 后 gzip，倒着剥       │
└────────────────────────────────────────┘
```

- gzip 只认一条字节流；tar 把目录树连元数据装订成那条流。
- .tar.gz = 先 tar 后 gzip，解开时倒着剥；纯 .tar 不压缩，反而略大。

## 经典追问链

**.tar.gz 的解压顺序是什么？为什么不能先解 tar？**

先剥 gzip 壳还原出 tar 流，再拆装订取出文件。因为 gzip 的输入必须是一条字节流，而目录树还不是「一条」——得先由 tar 摊平成流它才有得压。后缀倒着读就记住了：.tar.gz = 先 .tar 后 .gz，剥的时候反着来。

- 加分项：现代 tar -xf 一条命令完成两步剥——先偷看魔数认壳，自动调对应工具。顺序没变，只是工具替你走了。

**纯 .tar 打包后为什么比原内容还大？大在哪了？**

开销来自三处：每个条目前 512 字节的元数据头部（名字、权限、属主、时间戳）、数据按块对齐补零、流末尾的收尾块。实测 89 字节的三个文件打包出 5120 字节。买 tar 买的是「目录树变一条流」，不是变小。

- 加分项：gzip 能把 5120 压到 315，正是因为补零和重复模式是压缩算法最擅长吃掉的冗余——tar 无意中给 gzip 备好了粮。

**tar 和 zip 的本质区别是什么？**

zip 是打包 + 压缩一体：格式内建目录结构，压缩算法焊死（deflate）。tar + gzip 是分工：tar 只管装订成流，压缩交给外挂，所以压缩层可插拔——gzip、bzip2、xz、zstd 换个字母的事，zip 没这个自由。

- 加分项：zip 的中央目录在文件末尾，支持随机访问单个文件；tar 是纯顺序流，只能从头读到尾——这是磁带出身的痕迹，也是容器镜像选它当层格式的原因之一：顺序流的读写逻辑最简单。

**不解包怎么知道 .tar.gz 里有哪些文件？依据是什么？**

tar -tvf。清单本来就在流里：tar 流的每个条目前面有一张头部块，文件名在其中是明文，顺序读完头部就能列出全部路径，一个数据块都不用碰。这和「文件类型看魔数」是同一条设计哲学——元数据就在字节里，工具只是读出来。

- 加分项：同理 tar -xOf 包内路径 可以不解包直接打印包内某个文件——抠 docker 镜像包里的 manifest.json 就靠它。
