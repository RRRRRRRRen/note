# 设计原则

*类型：knowledge ｜ 难度：进阶 ｜ 标签：设计原则、SOLID、单一职责、开放封闭、里氏替换、接口隔离、依赖倒置、迪米特法则*

**结论：设计模式是「术」，设计原则是「道」，其中 SOLID 五原则是骨架：单一职责（一个类只有一个变化原因）、开放封闭（对扩展开放、对修改封闭——最重要的一条，几乎所有模式都在为它服务）、里氏替换（子类必须能无感替换父类）、接口隔离（不强迫依赖用不到的接口）、依赖倒置（面向抽象编程，高层与低层都依赖抽象）。补充两条：最少知识原则（迪米特法则，只和直接朋友通信，减少链式依赖）与合成复用原则（优先组合而非继承）。判断代码是否要重构，看的不是「用了几个模式」，而是「变化来时改动是否收敛」。**

## SOLID 原则

### 单一职责原则（Single Responsibility Principle）

一个类应该只有一个引起它变化的原因——一个模块只负责一件事。

```js
// 违反：User 类同时承担「数据 + 持久化 + 邮件」三个职责
// 任何一块变化都要改这个类
class User {
  constructor(name, email) {
    this.name = name;
    this.email = email;
  }
  save() {
    // 保存到数据库
  }
  sendEmail() {
    // 发送邮件
  }
}

// 遵循：按职责拆分，数据库逻辑变了只改 Repository
class User {
  constructor(name, email) {
    this.name = name;
    this.email = email;
  }
}

class UserRepository {
  save(user) {
    // 保存到数据库
  }
}

class EmailService {
  send(user, message) {
    // 发送邮件
  }
}
```

### 开放封闭原则（Open-Closed Principle）

软件实体应该对扩展开放、对修改封闭——加新功能靠新增代码，而不是改老代码。

```js
// 违反：每加一种形状，calculate 里就要多一个 if 分支
class Rectangle {
  constructor(width, height) {
    this.width = width;
    this.height = height;
  }
}

class AreaCalculator {
  calculate(shapes) {
    let area = 0;
    shapes.forEach(shape => {
      if (shape instanceof Rectangle) {
        area += shape.width * shape.height;
      }
      // 添加新形状需要修改这里
    });
    return area;
  }
}

// 遵循：定义统一抽象，新形状 = 新增一个子类，计算器零改动
class Shape {
  area() {
    throw new Error('子类必须实现 area 方法');
  }
}

class Rectangle extends Shape {
  constructor(width, height) {
    super();
    this.width = width;
    this.height = height;
  }
  area() {
    return this.width * this.height;
  }
}

class Circle extends Shape {
  constructor(radius) {
    super();
    this.radius = radius;
  }
  area() {
    return Math.PI * this.radius ** 2;
  }
}

class AreaCalculator {
  calculate(shapes) {
    // 多态分发，calculate 永远不需要改
    return shapes.reduce((total, shape) => total + shape.area(), 0);
  }
}
```

### 里氏替换原则（Liskov Substitution Principle）

子类对象必须能够替换父类对象，而程序逻辑不变——子类不能破坏父类的行为约定。

```js
// 遵循：Sparrow 替换 Bird 后，调用方行为完全兼容
class Bird {
  fly() {
    console.log('飞行');
  }
}

class Sparrow extends Bird {
  fly() {
    console.log('麻雀飞行');
  }
}

function makeBirdFly(bird) {
  bird.fly(); // 调用方只依赖父类约定
}

makeBirdFly(new Bird());   // 飞行
makeBirdFly(new Sparrow()); // 麻雀飞行
```

反面教材是经典的「企鹅问题」：让不能飞的 Penguin 继承带 fly 的 Bird，替换后 `makeBirdFly` 抛异常，就违反了里氏替换——应该重新设计继承层次（如把 fly 下沉到 FlyingBird），而不是硬继承。

### 接口隔离原则（Interface Segregation Principle）

客户端不应该依赖它不需要的接口——胖接口应拆成小接口。

```js
// 违反：Robot 被迫实现用不到的 eat/sleep
class Worker {
  work() {}
  eat() {}
  sleep() {}
}

class Robot extends Worker {
  work() {
    console.log('机器人工作');
  }
  eat() {
    // 机器人不需要吃饭，只能空实现
  }
  sleep() {
    // 机器人不需要睡觉，只能空实现
  }
}

// 遵循：接口按能力拆细，谁需要谁实现
class Workable {
  work() {
    throw new Error('必须实现 work 方法');
  }
}

class Eatable {
  eat() {
    throw new Error('必须实现 eat 方法');
  }
}

class Human extends Workable {
  work() {
    console.log('人类工作');
  }
}

class Robot extends Workable {
  work() {
    console.log('机器人工作');
  }
}
```

### 依赖倒置原则（Dependency Inversion Principle）

高层模块不应该依赖低层模块，两者都应该依赖抽象——具体实现通过注入替换。

```js
// 违反：UserService 直接 new 具体数据库，换库必须改高层代码
class MySQLDatabase {
  save(data) {
    console.log('保存到 MySQL');
  }
}

class UserService {
  constructor() {
    this.database = new MySQLDatabase(); // 直接依赖具体实现
  }
  saveUser(user) {
    this.database.save(user);
  }
}

// 遵循：依赖抽象接口，实现通过构造函数注入
class Database {
  save(data) {
    throw new Error('必须实现 save 方法');
  }
}

class MySQLDatabase2 extends Database {
  save(data) {
    console.log('保存到 MySQL');
  }
}

class MongoDatabase extends Database {
  save(data) {
    console.log('保存到 MongoDB');
  }
}

class UserService2 {
  constructor(database) {
    this.database = database; // 依赖抽象
  }
  saveUser(user) {
    this.database.save(user);
  }
}

// 组装期才决定用哪个实现，测试时还能注入 mock
const userService = new UserService2(new MySQLDatabase2());
```

## 其他重要原则

### 最少知识原则（迪米特法则）

一个对象应该对其他对象保持最少的了解——只和「直接朋友」通信，减少链式依赖。

```js
// 违反：客户端被迫了解 Person 内部的 Wallet 结构
class Wallet {
  constructor(money) {
    this.money = money;
  }
  getMoney() { return this.money; }
  setMoney(money) { this.money = money; }
}

class Person {
  constructor(wallet) {
    this.wallet = wallet;
  }
  getWallet() { return this.wallet; }
}

// 链式调用暴露了内部结构，Wallet 变更会波及所有调用方
const person = new Person(new Wallet(100));
const money = person.getWallet().getMoney();

// 遵循：Person 封装支付细节，客户端只认识 Person
class Person2 {
  constructor(wallet) {
    this.wallet = wallet;
  }
  getMoney() {
    return this.wallet.getMoney();
  }
  pay(amount) {
    const money = this.wallet.getMoney();
    if (money >= amount) {
      this.wallet.setMoney(money - amount);
      return true;
    }
    return false;
  }
}

const person2 = new Person2(new Wallet(100));
person2.pay(50);
```

### 合成复用原则

优先使用对象组合，而不是继承——继承是强耦合的「is-a」，组合是灵活的「has-a」。

```js
// 继承的问题：能力组合爆炸（会飞的动物、会游泳的动物……类层次失控）
class Animal {
  eat() {
    console.log('吃东西');
  }
}

class FlyingAnimal extends Animal {
  fly() {
    console.log('飞行');
  }
}

// 组合：能力做成独立模块，按需拼装
class Eatable {
  eat() {
    console.log('吃东西');
  }
}

class Flyable {
  fly() {
    console.log('飞行');
  }
}

class Bird {
  constructor() {
    this.eatable = new Eatable(); // has-a
    this.flyable = new Flyable(); // has-a
  }
  eat() {
    this.eatable.eat();
  }
  fly() {
    this.flyable.fly();
  }
}
```

## 原则速查

| 原则 | 一句话 | 典型症状（违反时） |
|------|--------|--------------------|
| 单一职责 | 一个类只有一个变化原因 | 上帝类，改一处动全身 |
| 开放封闭 | 扩展加代码，不改老代码 | 满屏 if/else instanceof |
| 里氏替换 | 子类可无感替换父类 | 继承后行为破坏、抛异常 |
| 接口隔离 | 不依赖用不到的接口 | 大量空实现、被迫实现 |
| 依赖倒置 | 面向抽象编程 | 高层直接 new 低层实现 |
| 最少知识 | 只和直接朋友通信 | `a.getB().getC().do()` |
| 合成复用 | 优先组合而非继承 | 继承层次爆炸、能力无法拼装 |

## 实践要点

- 五条 SOLID 中开放封闭是目标，依赖倒置与接口隔离是实现开放封闭的主要手段
- 原则的落地判据：**新增需求时改动是否收敛在新增代码里**，而不是代码行数或类数量
- JS 无接口语法时，用「抛错基类方法」「鸭子类型（约定同名方法）」表达抽象约定
- 组合优先于继承，与「优先用工厂/策略替代子类化」一脉相承
