# 属性是怎么被继承的：原型链查找

*类型：knowledge ｜ 难度：高级 ｜ 标签：原型链、继承、class ｜ 更新：2026-09-10*

**结论：JS 没有「类复制式」继承，只有对象到对象的链接。读属性时自身没有，就沿 `[[Prototype]]` 内部槽一路向上，直到 `null` 为止；写入则永远落在自身（遮蔽或新建，原型不动）。方法和原型放一份、所有实例共享——既省内存，也让「给已存在的实例补方法」成为可能。 class 只是这套机制之上的语法糖。`constructor` 是惯例不是不变量：整体替换 `prototype` 后必须手动补上。**

前置篇目（见文末延伸阅读）：变量查找沿作用域链、属性查找沿原型链——两条「逐级向上」的链是本篇的分析框架。

## 双槽辨析：[[Prototype]]、prototype 与 **proto**

原型体系最容易混的是三个名字相似但完全不同的东西。 设计动机先说清：**链接的职责被分配给了两个角色**——每个对象只有一个「我的原型是谁」的内部槽（`[[Prototype]]`，规范级，只能通过 `Object.getPrototypeOf`、`Object.create`、`new` 设置）； 而「我 new 出来的对象该链到谁」被放在构造函数身上，成了函数特有的属性（`Fn.prototype`）。 实例看链、函数带配置——一个记录关系，一个提供出厂设置。

- `[[Prototype]]`：每个对象都有的内部槽，指向它的原型；查找沿它进行。
- `.prototype`：只有函数有的属性；`new Fn()` 时新对象的 `[[Prototype]]` 被指向它。
- `__proto__`：历史遗留的 getter/setter，读它等价于读 `[[Prototype]]`；新代码用标准 API。

`new Fn()` 在引擎里最核心的一步就是把新对象的 `[[Prototype]]` 指向 `Fn.prototype`（另有以 `Fn.prototype.constructor` 为构造逻辑初始化 this、执行函数体两步）。 理解「双槽分属两个对象」，下面这组实测结果全部可推导：

```javascript
const animal = { eat() { return "eating" } };
const dog = Object.create(animal);

dog.eat(); // "eating" —— 自身没有，沿原型链找到 animal
Object.getPrototypeOf(dog) === animal; // true

function Foo() {}
new Foo().__proto__ === Foo.prototype; // true（演示用，生产用 getPrototypeOf）
```

原型链的内存布局（prototype links）：

```text
堆（对象与原型，整条原型链都长在堆上，函数也是对象）

  dog（实例）                        Dog（构造函数）
  ├─ name = '旺财'                   └─ prototype ─────┐
  └─ [[Prototype]] ──────┐                             │
                         ▼                             ▼
                    Dog.prototype ◄────────────────────┘
                    ├─ bark = <function>
                    ├─ constructor ──► Dog（构造函数）
                    └─ [[Prototype]] ──────┐
                                           ▼
                                  Object.prototype
                                  ├─ toString = <function>
                                  └─ hasOwnProperty = <function>
                                  （[[Prototype]] = null，链到此为止）
```

- dog.toString 的查找：dog → Dog.prototype → Object.prototype 命中。
- Object.prototype 的 [[Prototype]] 是 null，链到此为止。
- constructor 不在实例身上，是沿链在 prototype 对象上找到的。

## 属性查找算法：一步不少

读取 `obj.prop` 的完整算法： 先在 obj 自身做属性查找（规范里的 `OrdinaryGetOwnProperty`）；命中直接返回——数据属性给值，访问器属性调用 getter； 未命中则取 `obj.[[Prototype]]`，在原型对象上重复同样的过程，如此逐级向上。 终止条件只有两个：**某一级命中**，或走到 `null`（链的尽头，`Object.prototype.[[Prototype]] === null`）。 整条链都未命中时，读取得 `undefined`、严格模式的写入抛 `TypeError`——这和变量查找的 `ReferenceError` 是两套报错逻辑。

两个容易漏掉的细节： 一是**访问器属性中途命中就直接调用，不再向上**——原型链上更远的同名 getter 没有机会执行； 二是**写入永远落在自身**：`obj.prop = x` 若自身与原型链都没有该数据属性，就在 obj 自身新建（遮蔽原型上的同名属性），原型不受影响。 「读沿链、写落自身」的不对称，正是「方法放原型、状态放实例」这套惯例能成立的底层保证。

dog.toString() 的查找过程（lookup trace）：

```text
① 自身：dog
   OrdinaryGetOwnProperty(dog, 'toString') 未命中——dog 自身只有 name。
   取 [[Prototype]] 进入下一级。

② 第一环：Dog.prototype
   有 bark 和 constructor，没有 toString——未命中，继续沿 [[Prototype]] 向上。

③ 第二环：Object.prototype
   命中 toString——数据属性直接返回函数值；若是 getter 此刻被调用，查找终止。

④ 反着写一次：dog.toString = fn
   写入不走这条链：在 dog 自身创建遮蔽属性，此后实例读 toString 命中自身，
   原型上的函数不再可达。
```

## 为什么方法放原型上：内存与动态性

先算内存账：方法挂在 `Fn.prototype` 上，一万个实例共享**一份**函数对象； 若在构造器里 `this.bark = function () {…}`，一万个实例就有一万份函数对象——函数对象不小（闭包上下文、代码引用、隐藏类），实例量大的场景是实打实的内存差。 原型方法的另一个红利是每实例行为一致：方法永远来自同一个对象，改一处全体生效，不存在「这批实例的方法是旧版」的分裂。

再说动态性：查找发生在**每次属性访问时**，不是 `new` 的那一刻。 这意味着运行时往 `Fn.prototype` 上加方法，**已经存在的实例立即可用**——polyfill 给 `Array.prototype` 补方法、调试期给原型挂探针，靠的都是这个时点。 但同一机制反过来就是坑：`prototype` 上放引用类型字段（如 `Fn.prototype.tags = []`），所有实例共享同一个数组，一处 `push` 全体可见——所以惯例是**方法放原型、可变状态放实例**（在构造器里赋值）。

## constructor 陷阱

`constructor` 是惯例，不是被引擎维护的不变量。 默认情况下 `Dog.prototype.constructor === Dog`——这个属性只是函数声明时顺手挂在原型对象上的一个普通属性。 一旦**整体替换** `Dog.prototype`（形如 `= { ... }` 的字面量），新对象身上没有 `constructor`，实例沿链查找就会越过它一路找到 `Object.prototype.constructor`，得到 `Object`——链条断了（下例 Node v22 实测）。 而 `instanceof` **不受影响**，因为它走 `[[Prototype]]` 链根本不查 `constructor`——两套判断机制独立，别用一个推断另一个。

断链的实际影响面： 依赖 `obj.constructor` 的代码（通用克隆/工厂、按类型分发的序列化重建、部分调试器的类型显示）会拿到错误的构造函数。 修复惯例也简单：替换前保留原原型再扩展，或替换时在字面量里**补回 `constructor: Fn`**； 更彻底的做法是干脆不整体替换，用 `Object.setPrototypeOf` 或 `Object.create(Fn.prototype)` 组织继承（后者同样记得补 constructor）。

```javascript
function Foo() {}
Foo.prototype = { say() {} };   // 整体替换原型对象

const f = new Foo();
f.constructor;       // [Function: Object] —— constructor 链断了
f.constructor === Object; // true —— 沿原型链一路找到 Object.prototype

// 正确姿势：替换前保留，或替换时补上
Foo.prototype = { constructor: Foo, say() {} };
```

输出解读（constructor lookup）：

```text
[Function: Object]
true
```

- `[Function: Object]`（同步）：f 自身没有 constructor，沿链查找——Foo.prototype（被整体替换后的新对象）没有 → Object.prototype 命中，拿到的是 Object 的构造函数。
- `true`（同步）：同一条查找链的结果——f.constructor === Object 是真值比较，印证「constructor 只是 prototype 对象上的普通属性」，原型一换，链条跟着换。

替换 prototype 的姿势（prototype swap）正误对照：

**错误写法：**

```javascript
function Foo() {}
Foo.prototype = { say() {} };
// 整体替换，字面量里没有 constructor

const f = new Foo();
f.constructor === Object; // true
// 依赖 constructor 的克隆/工厂
// 全部拿到错误类型
```

问题：constructor 是 prototype 对象上的普通属性，整体替换即丢失——沿链向上找到 Object.prototype 的那份。

**正确写法：**

```javascript
function Foo() {}
Foo.prototype = {
  constructor: Foo, // 补回指向
  say() {},
};

// 或不整体替换，增量扩展：
Foo.prototype.say = function () {};
// constructor 原封不动
```

要点：字面量替换必须补 constructor；能增量扩展就不整体替换——instanceof 不受影响不代表没人读 constructor。

## 边界陷阱

原型链的坑有共同模式：**共享的东西被当成私有，私有的东西被当成公共**。 前者是原型上的引用类型字段被所有实例共享（上文已展开）； 后者是往内置对象的原型上加方法——`Array.prototype.first = …` 看似方便，实则污染所有数组、可能被 `for...in` 枚举到、与 polyfill/第三方库冲突，多次加载还会重复覆盖。 另一个高频坑是 `__proto__`：它是 setter 而非真实属性，写入开销大且非标准； 另外「跨 iframe/worker 的对象原型不共享」会让 `instanceof` 静默失效（追问链第 2 问展开）。

原型引用字段这个坑值得单独点名，因为它最像「能跑的正常代码」： 在 `Fn.prototype` 上放 `tags: []` 这类可变对象，每个实例读 `this.tags` 都沿链命中**同一个数组**——某个实例 `push` 一条，所有实例的 `tags` 都变了，而且序列化、比较、React 的引用比较会一起出诡异现象。 判断标准一句话：原型上只放**不可变共享物**（方法、常量），每实例一份的可变状态一律在构造器里初始化。

扩展内置原型（builtin pollution）正误对照：

**错误写法：**

```javascript
Array.prototype.first = function () {
  return this[0];
};

[1, 2, 3].first(); // 1
// 代价：所有数组被改、for...in 多出键、
// 与其他 polyfill 冲突、升级 JS 后
// 与原生方法同名时行为分裂
```

问题：内置原型是全局公共命名空间——一处污染，全站买单，这是「原型动态性」的反面用法。

**正确写法：**

```javascript
// 方案一：工具函数
const first = (arr) => arr[0];

// 方案二：子类或静态方法
class MyArray extends Array {
  first() { return this[0]; }
}
```

要点：需要新方法时收进自己的命名空间（工具函数/子类），需要通用能力时提 TC39 提案——不动内置原型。

## 面向对象的三大特性

面向对象的封装、继承、多态在 JS 里都有原型机制下的对应实现：封装靠闭包私有变量，继承靠原型链，多态靠子类重写原型方法。

### 封装性

将数据和操作数据的方法封装在一起，隐藏内部实现细节，只暴露必要的接口。

```javascript
function Person(name, age) {
  // 私有变量：闭包持有，外部无法直接访问
  let _age = age;

  // 公共属性
  this.name = name;

  // 公共方法
  this.getName = function() {
    return this.name;
  };

  // 通过公共方法访问私有变量，可加校验逻辑
  this.getAge = function() {
    return _age;
  };

  this.setAge = function(newAge) {
    if (newAge > 0 && newAge < 150) {
      _age = newAge;
    }
  };
}

const person = new Person('Alice', 25);
console.log(person.name);    // 'Alice'
console.log(person._age);    // undefined —— 私有变量无法直接访问
console.log(person.getAge()); // 25
```

### 继承性

子类继承父类的属性和方法，实现代码复用（借用构造函数继承属性 + 原型链继承方法）。

```javascript
function Animal(name) {
  this.name = name;
}

Animal.prototype.eat = function() {
  console.log(`${this.name} is eating`);
};

function Dog(name, breed) {
  Animal.call(this, name); // 继承属性：在子构造器里以 this 执行父构造
  this.breed = breed;
}

// 继承方法：用 Object.create 挂上父类原型，再修正 constructor
Dog.prototype = Object.create(Animal.prototype);
Dog.prototype.constructor = Dog;

Dog.prototype.bark = function() {
  console.log(`${this.name} is barking`);
};

const dog = new Dog('Buddy', 'Golden Retriever');
dog.eat();  // 'Buddy is eating' —— 继承自 Animal.prototype
dog.bark(); // 'Buddy is barking'
```

### 多态性

同一个方法在不同对象中有不同的实现——子类重写原型方法后，同一调用出现不同行为。

```javascript
function Animal(name) {
  this.name = name;
}

Animal.prototype.makeSound = function() {
  console.log('Some sound');
};

function Dog(name) {
  Animal.call(this, name);
}
Dog.prototype = Object.create(Animal.prototype);
Dog.prototype.makeSound = function() { // 重写父类方法
  console.log(`${this.name}: Woof!`);
};

function Cat(name) {
  Animal.call(this, name);
}
Cat.prototype = Object.create(Animal.prototype);
Cat.prototype.makeSound = function() { // 各自重写
  console.log(`${this.name}: Meow!`);
};

// 多态体现：同一消息，不同响应
const animals = [
  new Dog('Buddy'),
  new Cat('Whiskers'),
  new Animal('Generic')
];

animals.forEach(animal => animal.makeSound());
// Buddy: Woof!
// Whiskers: Meow!
// Some sound
```

面向对象范式的优势：灵活性（继承与多态支持灵活扩展）、可复用性（继承避免重复代码）、易维护（封装让结构清晰）、适合多人协作的大型项目。

## 对象的分类：原生、内置、宿主

JS 对象按来源分三类：规范定义的原生对象、引擎实例化好的内置对象、宿主环境提供的宿主对象。

### 原生对象（Native Objects）

由 ECMAScript 规范定义的对象，独立于宿主环境存在。

- `Object`、`Function`、`Array`、`String`、`Boolean`、`Number`
- `Date`、`RegExp`、`Error`
- 各类错误子类：`EvalError`、`RangeError`、`ReferenceError`、`SyntaxError`、`TypeError`、`URIError`

```javascript
// 原生对象大多需要实例化
const obj = new Object();
const arr = new Array();
const str = new String('hello');
const num = new Number(42);
const date = new Date();
const regex = new RegExp('\\d+');
```

### 内置对象（Built-in Objects）

由 JS 引擎内部实例化好的对象，开发者无需显式创建、直接使用。

- `Global`（浏览器中对应 `window`）
- `Math`
- `JSON`
- `Reflect`
- `Proxy`

```javascript
console.log(Math.PI);             // 3.141592653589793
console.log(Math.max(1, 2, 3));   // 3

const obj = { name: 'Alice' };
console.log(JSON.stringify(obj)); // '{"name":"Alice"}'
```

### 宿主对象（Host Objects）

由宿主环境（浏览器、Node.js）提供的对象，规范管不到、随环境变化。

- 浏览器 BOM：`window`、`navigator`、`location`、`history`、`screen`
- 浏览器 DOM：`document`、`Element`、`Node`

```javascript
// 浏览器环境特有，Node 中不存在
console.log(window.innerWidth);
console.log(navigator.userAgent);
console.log(document.title);

const div = document.createElement('div');
```

## 经典追问链

**追问一：class 的方法在实例上还是原型上？**

考察点：热身题，确认你把 class 还原成原型机制——答「实例上」的人还没穿过语法糖这层皮。

在原型上。 class 声明的方法等同于挂在 Foo.prototype；只有实例字段（constructor 里的 `this.x = …` 与类字段语法）落在实例自身。 所以方法全类一份、字段每实例一份——class 的内存模型与「方法放原型、状态放实例」的惯例完全一致，它就是这套惯例的语法化。

- 加分项：静态方法（static）挂在构造函数自身（Foo.staticFn），不进原型也不随实例可达；私有 #字段存在实例内部槽上，既不在原型也无法从外部访问——三种存放位置值得画成一张表记牢。

**追问二：instanceof 的原理？能被绕过吗？**

考察点：考「双机制」意识——instanceof 与 constructor 是两条独立链，混为一谈的人说不出跨 iframe 失效的原因。

沿右侧函数的 prototype 在左侧对象的原型链上逐级查找，命中即 true——本质是链的成员资格判断。 可以绕过：Symbol.hasInstance 允许自定义判断逻辑； 跨 iframe/worker 场景原型不共享（两个 realm 各有一套 Array.prototype），instanceof 会静默失效，此时用 Array.isArray（查内部槽）代替。

- 加分项：Object.prototype.toString.call(x) 也跨 realm 可靠——它读内部槽标签（[object Array]）而非原型。三种判断的可靠度排序：内部槽 > 原型链（instanceof）> constructor 属性。

**追问三：extends 之后 super 是什么？**

考察点：考 super 的派发机制——答「super 就是父类原型」在方法被混入/借用时会立刻露馅。

super 不是指向父类原型的固定引用。 `super.method` 绑定当前 this、但方法从 [[HomeObject]]（方法定义时记录的所属对象）的原型上取——本质是 HomeObject 元信息驱动的动态派发。 这就是为什么方法被 `obj.method()` 调用时 this 是 obj，而方法体里的 super 仍按「定义位置」向上找：this 管接收者，super 管查找起点。

- 加分项：对象字面量里想用 super，方法必须是 shorthand 写法（`method() {}`）——[[HomeObject]] 只挂在方法上，普通属性函数没有它，写 super 直接语法错误。

**追问四：Object.create(null) 有什么用？**

考察点：考「无原型对象」的工程价值——知道字典用法是及格，说得出原型污染防御是加分。

创建没有原型的「纯净对象」：没有 toString/hasOwnProperty 等继承成员，做字典/映射时不会被任意键名干扰（比如读 key 为 `'__proto__'` 或 `'toString'` 的值）。 代价是连基础方法都没有——只能用 Object.keys、Reflect.has 这类静态方法操作它。

- 加分项：安全视角——JSON.parse 返回的对象原型是 Object.prototype，攻击者可通过 `'__proto__'` 键做原型污染；以 Object.create(null) 的字典承接外部输入、或解析后深拷贝到无原型对象，是常见的防御姿势。

**追问五：给实例写属性时引擎做什么？会写到原型上吗？**

考察点：压轴题，考「读沿链、写落自身」这条不对称的规范细节——它支撑着整个「方法在原型、状态在实例」的工程惯例。

不会写到原型上。 OrdinarySet 的逻辑：自身有该数据属性就改自身；没有则沿原型链找 setter，找到就调用；都没有则在（非严格模式下）自身新建一个属性——这个新建就是对原型的「遮蔽」。 此后实例读该属性命中自身，原型上的同名属性对它不再可见，但其他实例不受影响。

- 加分项：两个边界——严格模式下，原型存在同名只读属性时写入抛 TypeError（非严格静默失败）；对原始值（数字/字符串）的属性写入则完全静默丢弃，临时包装对象随即被扔掉，连遮蔽都不会发生。
