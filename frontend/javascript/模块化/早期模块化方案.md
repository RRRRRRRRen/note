# 早期模块化方案

*类型：knowledge ｜ 难度：基础 ｜ 标签：模块化、全局变量、命名空间、IIFE、依赖注入*

**结论：ES Module 出现之前，JS 没有语言级模块系统，多个 `<script>` 共享全局作用域，变量互相覆盖（全局污染）。社区按「作用域隔离 → 私有成员 → 依赖管理」三步演进：命名空间用对象收拢变量（仍全局可见、内部可被改写）；IIFE 用函数作用域实现真正的私有变量（但导出接口仍挂全局、依赖靠加载顺序）；IIFE + 依赖注入把依赖显式写成参数（依赖明确了，但顺序仍靠手工维护）。这套演进逻辑解释了 CommonJS/ES Module 每个设计点存在的理由。**

## 问题：全局变量污染

没有模块系统时，每个加载的 JS 文件都共享同一个全局作用域，同名变量互相覆盖。

```html
<body>
  <script src="./index.js"></script>
  <script src="./home.js"></script>
  <script src="./list.js"></script>
</body>
```

```js
// index.js
var name = '不要秃头啊';
```

```js
// home.js
var name = [1, 2, 3]; // 覆盖了 index.js 中的 name
```

```js
// list.js
console.log(name); // [1, 2, 3] —— 不是预期的值
```

除了覆盖问题，`<script>` 标签的加载顺序还隐式决定了「谁能用谁」，依赖关系完全不可见。

## 解决方案 1：命名空间

用单个全局对象收拢模块的变量与方法，减少全局标识符数量。

```js
// moduleA.js
var moduleA = {
  name: 'Module A',
  sayHello: function() {
    console.log('Hello from ' + this.name);
  }
};

// moduleB.js
var moduleB = {
  name: 'Module B',
  sayHello: function() {
    console.log('Hello from ' + this.name);
  }
};

moduleA.sayHello(); // 'Hello from Module A'
moduleB.sayHello(); // 'Hello from Module B'
```

缺点：

- 仍然污染全局作用域（`moduleA`、`moduleB` 本身是全局变量）
- 模块内部状态可以直接被外部改写（`moduleA.name = 'x'` 无任何防护）
- 依赖关系依然不明确

## 解决方案 2：IIFE（立即执行函数）

利用函数作用域隐藏内部实现，只把公开接口挂到全局。

```js
// module.js
(function() {
  var name = '私有变量';        // 函数作用域内，外部无法访问

  function privateMethod() {
    console.log('私有方法');
  }

  function publicMethod() {
    console.log('公共方法');
    privateMethod();
  }

  // 只暴露公共接口
  window.myModule = {
    publicMethod: publicMethod
  };
})();

myModule.publicMethod();      // '公共方法' '私有方法'
console.log(myModule.name);   // undefined（私有成员不可见）
```

优点：

- 创建独立作用域，内部变量真正私有
- 可自由选择哪些成员对外公开

缺点：

- 导出容器本身仍挂在全局（`window.myModule`）
- 模块间依赖不明确，仍靠 `<script>` 的书写顺序保证
- 大型项目里依赖链条难以管理

## 解决方案 3：IIFE + 依赖注入

把依赖作为 IIFE 的入参显式传入，依赖关系第一次变得可见。

```js
// moduleA.js
var moduleA = (function() {
  var name = 'Module A';

  return {
    getName: function() {
      return name;
    }
  };
})();

// moduleB.js —— 依赖 moduleA，通过参数显式声明
var moduleB = (function(moduleA) {
  var name = 'Module B';

  return {
    getName: function() {
      return name + ' depends on ' + moduleA.getName();
    }
  };
})(moduleA);

console.log(moduleB.getName()); // 'Module B depends on Module A'
```

优点：

- 依赖关系在代码中一目了然
- 依赖通过参数传入，便于测试时替换

缺点：

- 依赖的加载顺序仍需手工在 HTML 中保证
- 没有按需加载与缓存机制，大型项目难以维护

## 演进对比

| 方案 | 作用域隔离 | 私有成员 | 依赖管理 |
|------|-----------|---------|----------|
| 全局变量 | 无 | 无 | 无 |
| 命名空间 | 部分（收拢） | 无 | 无 |
| IIFE | 有 | 有 | 无（靠加载顺序） |
| IIFE + 依赖注入 | 有 | 有 | 显式声明，顺序仍手工 |

## 实践要点

- 三步演进的每一步都在补上一步的短板：隔离 → 私有 → 显式依赖，理解这条主线即可理解现代模块规范的设计动机
- CommonJS 的「模块缓存 + require 依赖」、ES Module 的「静态 import/export」正是把这三件事交给语言与工具
- 老代码里看到的 IIFE 模块（如 jQuery 插件 `(function($){})(jQuery)`）就是依赖注入形式的活化石
