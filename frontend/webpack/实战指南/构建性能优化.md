# 构建性能优化

*类型：practice ｜ 难度：进阶 ｜ 标签：webpack、构建性能、cache、DllPlugin、并行*

**构建性能优化分通用环境、开发环境、生产环境三张清单，通用环境的大头是：缩小 loader 作用范围、收窄 resolve 搜索面、开启持久化缓存、把重 loader 丢进 worker pool。** 生产环境的原则是「不要为了很小的性能收益，牺牲应用程序的质量」——关 source map、类型检查挪到独立进程，宁可构建慢一点也不降产物质量。

## 通用环境

- 使用新版本的 webpack 和 Node 有助于提升性能。
- 每个额外的 loader/plugin 都有启动时间，尽量少地使用工具。

### 限制 loader 作用范围

将 loader 应用于最少数量的必要模块：

```js
const path = require('path');

module.exports = {
  // ...
  module: {
    rules: [
      {
        test: /\.js$/,
        // 使用 include 只解析指定文件夹内的内容，node_modules 不再过 babel
        include: path.resolve(__dirname, 'src'),
        loader: 'babel-loader',
      },
    ],
  },
};
```

### 收窄解析范围，提高解析速度

- 减少 `resolve.modules`：减少解析 import 路径时的搜索范围，默认值为 `['node_modules']`。
- 减少 `resolve.extensions`：减少被省略扩展名的搜索范围，默认值为 `['.js', '.json']`。
- 减少 `resolve.mainFiles`：减少被省略文件名的搜索范围，默认值为 `['index']`。
- 减少 `resolve.descriptionFiles`：减少被搜索的描述文件范围，默认值为 `['package.json']`。

### 减少编译结果的整体大小

- 使用数量更少、体积更小的 library。
- 在多页面应用程序中使用 `SplitChunksPlugin`，并开启 `async` 模式。
- 移除未引用代码。
- 只编译你当前正在开发的那些代码。

### 其他手段

- `DllPlugin`：将不频繁变化的依赖（如第三方库）打包成单独的 dll 文件，供后续构建过程使用，但需要手动维护 dll 文件。
- worker pool：把非常消耗资源的 loader 分配给一个 worker pool，加速构建编译；但过多的 worker 可能导致系统负载过高。
- 持久化缓存：使用 webpack 配置中的 `cache` 选项开启持久化缓存，大型项目中可将构建时间从数分钟减少到数秒。
- `ProgressPlugin`：在控制台输出构建进度，关闭它可以带来些许提升，非必要可权衡。

## 开发环境

- 编译时使用增量编译，即 webpack 的 watch mode（监听模式）。
- 使用内存中编译，例如 `webpack-dev-server`。
- 使用 Node API 输出编译信息时，用 `stats.toJson` 加速。
- 选择合适的 source map 配置，多数情况下最佳实践为 `eval-cheap-module-source-map`。
- 避免使用生产环境才需要的工具，如代码压缩插件 `TerserPlugin`。
- 确保生成 entry chunk 时尽量减少其体积以提高性能。
- 大型代码库中避免额外的优化步骤以提高编译速度。
- 禁止输出结果携带路径信息：打包数千个模块的项目中，路径信息会造成垃圾回收性能压力。
- 编译时跳过 TS 类型检查，但不建议在生产环境中这样做。

## 生产环境

> 不要为了很小的性能收益，牺牲应用程序的质量！

- 关闭 source map。
- 配置单独的进程进行 TS 类型检查。
- 避免 sass 解析时 `node-sass` 中来自 Node.js 线程池的阻塞线程 bug。
- 最小化项目中的 preset/plugin 数量。
